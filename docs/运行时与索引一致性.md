# 运行时与索引一致性（P0/P1 落地记录）

日期：2026-10-18。对应计划：P0-1 索引生命周期、P0-2 在线问答 runtime、
P0-3 端到端 trace、P1-4 薄 runtime facade、P1-5/6 覆盖与上下文、P1-7 JUDGE。

## 一、当前形态

```
MySQL（业务真源）
  └─ kb_index_outbox（期望状态）
       └─ temporal-worker: kb_outbox.loop
            ├─ INDEX → Temporal kb-index → MySQL 切片 + PG（pgvector dense + BM25）
            └─ DELETE → purge_source（PG/MySQL 派生数据）

PostgreSQL（ParadeDB PG17）
  ├─ kb.chunk_search：pgvector dense + BM25（jieba）
  └─ langgraph：在线问答 checkpoint（CHAT_CHECKPOINT_ENABLED=1）

Redis：限流/预算 + chat:events:{message_id} SSE 事件流
```

### 读侧双保险

1. `kb_service.search_knowledge` 对最终 hit 批量核对：
   - MINUTES 必须 `CONFIRMED`；
   - TRANSCRIPT 必须 `SUCCEEDED`；
   - `KbDocument.status` 必须 `SUCCEEDED`（失败版本的半成品不返回）。
2. outbox/reconcile 负责把派生存储最终清理干净；即使它落后，旧切片也不会被交给模型。

### 在线问答 runtime

- `ChatMessage` 增加 `run_status / thread_id / checkpoint_id / trace_id /
  charged_tokens`；`last_event_id` 从未被读取，已在 7 号迁移删除。
- `chat_graph` 的 `call_model/tools` 不再写入 checkpoint，改由
  `ChatRuntime` 通过 contextvar 注入；`thread_id=chat-turn-<assistant_id>`。
- 断线重连：`Last-Event-ID` 从 Redis Stream 回放已发事件；回放到 done/error 即结束，
  否则从 PostgreSQL checkpoint 继续；`charged_tokens` 保证不重复扣预算。
- 客户端断开仍会落库为 `INTERRUPTED`，前端显示"继续生成"按钮。

### trace

- 应用级 `trace_id` 由 HTTP 中间件/SSE 生成，不依赖 OTLP 是否启用。
- 模型调用写 `ai_call_log.trace_id/span_id`；工具调用发 `chat.tool` span；
  Temporal workflow/activity 透传 trace_id；`ChatMessage` 保存本轮 trace_id。

### P1 组件

- `services/agent_runtime.py`：只保留实际被调用的 `ToolRegistry` / `GuardrailChain`；
  trace 由 `common/tracing.py` 承担。
- `services/coverage.py`：`CoveragePlan` / `EvidenceState`（跨来源、槽位缺口）；
  由图内 `coverage` 节点在每次工具执行后观察，缺口存在时注入一次提示。
- `services/context_assembler.py`：显式字符预算；system 与当前问题永远保留。
- `services/model_config.py`：`JUDGE` 用途，未配置时回退 `AGENT`。

## 二、默认值与门禁

| 开关 | 默认 | 说明 |
|---|---|---|
| `KB_BM25_TOKENIZER` | `jieba` | 可换 `chinese_lindera` / `chinese_compatible`；换分词器必须重建索引并重跑检索指标 |
| `CHAT_CHECKPOINT_ENABLED` | `0`（`.env`）/ `1`（compose backend） | 生产 compose 默认开；无 PG 时不启用 checkpoint |
| `JUDGE_MODEL` | 空 | 空 = 自检支撑复核回退 `AGENT` |

**检索口径**：PG 一张表承载 pgvector dense + BM25；不再有第二个向量库。PG 不可用时两路检索都不可用，
`/chat/status` 报告 `pg_kb_reachable=false`；不再维护第二个向量库或稀疏实现。
2026-10-18 的 95 题 A/B（Qdrant sparse 臂 vs PG BM25 臂）过门禁后，双后端开关与
sparse 臂已一并删除，当前实现不再可切回——见第四节的**历史**读数。

## 四、历史：BM25 后端 A/B（2026-10-18）

> 这是**清理前**的双后端对比。A/B 通过后，项目只保留 PG BM25，
> 旧的 Qdrant sparse 臂与切换开关已删除；下面读数仅作历史依据，不能用来切换实现。

同一索引、同一批 `qa_seed.json` 有金标来源的 **95 题**，`limit=5`、rerank 开，
直接调用 `kb_service.search_knowledge`（不生成答案），只差词法臂：

| 端点 | 旧 Qdrant sparse 臂 | PG BM25 臂 | 差值 |
|---|---:|---:|---:|
| recall@k | 95.70% | 95.70% | 0 |
| MRR | 0.9228 | 0.9228 | 0 |
| nDCG@k | 0.9332 | 0.9341 | **+0.09pp** |
| recording coverage | 96.12% | 96.12% | 0 |

逐题只有 q62 的 nDCG 不同（0.92→1.00），其余 94 题完全一致；PG 不劣于 Qdrant
超过 1pp，门禁通过。口径限制：只测检索侧（rerank 后的 top-3），不测答案质量；
95 题来自单一语料，17 道无金标片段/不可答题未计入分母。

**清理后复跑（2026-10-18，当前实现）**：删除 sparse 臂、Qdrant 合入 PostgreSQL 后，
用同一批 95 题、同一 `limit=5`、rerank 开复跑：

| 指标 | 读数 |
|---|---:|
| recall@k | **95.70%** |
| MRR | **0.9228** |
| nDCG@k | **0.9341** |
| recording coverage | **96.12%** |

与上表的 PG BM25 臂逐项一致，没有因删除 sparse 回退。产物：`evaluation/results/retrieval_after_cleanup.json`（清理后首跑）、
`retrieval_after_fixes.json`（修复包复跑）、`retrieval_pgvector.json`（Qdrant 合并后复跑）与对应 `*_metrics.json`；三次读数逐项一致。

## 五、已知边界

- PG 里的 BM25/pgvector 检索索引都是派生存储；`ParadeDB pg_search` 为 AGPL-3.0，分发/商用前确认许可证。
- 上述 A/B 只覆盖检索侧；PG BM25 臂的答案质量（context precision/faithfulness）
  尚未跑判定式复测。
- `CoveragePlan/EvidenceState` 已落地并接入图内 `coverage` 节点：工具执行后更新
  来源/槽位覆盖，缺口存在时注入一次定向提示；默认不额外调模型。该节点改变了一次
  工具轮的图步数（recursion limit 已同步放大），效果仍需在 27/68 题上复测。
