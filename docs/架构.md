# 架构

这份文档回答两个问题：**系统由哪些部分构成**（以及数据怎么流动），
以及**为什么它不是一堆各自为政的模块**——后者靠五处"一处定义、多处派生"的收敛点，
下文逐一说明每处收敛前是几份实现、现在谁在用。

（图的讲解版见 `架构图/MeetingBot项目全景讲解.html`：24 张图按"根约束 → 数据旅程 →
每个机制为什么长这样"的顺序展开，本文件是它的文字骨架。）

---

## 一、根约束

> **模型可以建议，不能成交；无证据，不判定。**

几乎每个机制都是它的推论：

| 推论 | 落在哪 |
|---|---|
| 纪要只有"人工确认"后才算数 | 状态机：`DRAFT → CONFIRMED`；草稿永远不进知识库 |
| 断言必须能回指原文 | 契约层：类型化槽位 + 来源闭合 + 证据策略表 |
| 自检是"审 → 改 → 复审"的环，不是一次生成 | LangGraph 反思环 + 轮数上限由代码兜住 |
| 检索到的内容要能点回原句 | 引用编号由宿主分配、答案写 `[n]`；引用卡片带会议/说话人/时间 |
| 答案不许引到无权看的会议 | 权限判在工具内部（`common/access` 唯一口径），不靠提示词 |

## 二、分层与数据流

```
浏览器（Vue 3 + TS）
   │  HTTP（token 头）/ SSE
   ▼
FastAPI（backend，多 worker）
   ├── api/           路由层：鉴权、参数校验、把领域错误翻成页面提示
   ├── services/      领域层：契约 / 模型工厂 / 反思环 / 知识库 / 问答编排
   └── common/        基础设施：认证 / 可见性 / 限流 / 日志指标 / 供应商能力表
   │
   ├── MySQL 8        业务真源（18 张表）
   ├── Qdrant         切片向量（dense + sparse），服务端 RRF 融合
   ├── Redis          滑动窗口计数与预算（fail-open）
   └── Temporal       四类长任务的持久执行（每类一个队列）
        └── temporal-worker（独立进程，按类型注册 activity）

MCP 客户端 ──/mcp──▶ 同一组工具（services/kb_tools）
```

一条会议数据走完全程：

1. **上传** 会议资料 → 按内容哈希去重 → `meeting_material`
2. **转写** Temporal `transcription` 队列 → ASR → `transcript_segment`（逐段带时间轴）
   → 转写成功**自动**入 `kb-index` 队列（转写全文 → RAW 切片）
3. **纪要** 单遍长上下文生成六字段 → 契约校验 →（可选）自检反思环
   → 人工确认 → **自动**入 `kb-index`（纪要条目 → CONFIRMED 切片）+ 可导出
4. **问答** 提问 → 检索（Qdrant 混合）或结构化事实查询 → 单 Agent 环
   → 逐 token SSE → 引用卡片点回原句
5. **观测** 每一次模型调用写一行 `ai_call_log`（含成本）→ 观测页 + `/metrics` + span

## 三、五处统一串联

这五处的共同点：**同一件事曾经在多个地方各写一遍，而重复的后果不是"代码丑"，
是"某个副本漏改"**——可见性漏改是越权，契约漏改是前端拿到读不懂的数据，
记账漏改是成本算错。收敛之后，每处只有一个实现、一张表或一个出口。

### 1. 可见性口径 → `common/access.py`

- **收敛前**：5 处各写一遍（会议下拉框、会议列表、纪要列表、转写列表、知识库检索）
- **现在**：`visible_meeting_query()`（未执行的查询条件）、`visible_meeting_ids()`
  （id 列表，`None`＝不过滤／空列表＝无可见会议）、`has_meeting_access()`（布尔）
- **谁在用**：五个接口 + 知识库工具层 + MCP 工具（同一份判据）
- **为什么关键**：这两种 `None` / 空的语义一旦混用，"没有权限"就变成"没有限制"

### 2. 契约 → `services/contracts.py`

- **收敛前**：schema、校验器、展示渲染各写一份，必然漂移
- **现在**：`SLOT_KINDS` / `BASE_ITEM_FIELDS` / `ISSUE_EVIDENCE_POLICY` 是唯一真源，
  由它派生 JSON Schema（模型看到的）、Pydantic 模型（落库校验的）、展示字符串（前端的）
  与校验器（判违规的）
- **谁在用**：纪要生成、自检、详情页、导出、知识库切块、问答工具
- **关键性质**：新增字段或槽位**不需要新检测代码**，只在表里加一行

### 3. 工具层 → `services/kb_tools.py`

- **收敛前**：（潜在）HTTP 与 MCP 各写一份工具实现——权限检查会在其中一份上漏掉
- **现在**：四个工具在一处声明（名称/描述/参数模型/实现），参数 schema 由 pydantic
  派生给模型看，执行走同一个 `execute_tool`，权限在同一处按 `Actor` 判
- **谁在用**：聊天（LangGraph `ToolNode`）与 MCP（`/mcp`）——**两种传输，一份逻辑**
- **工具只有四个**：业界建议 3–5 个，每多一个都降低模型的选择可靠性

### 4. 模型出入口 → `services/model_factory.py`

- **收敛前**：模型调用散在各服务里，记账、重试、失败分类各写一份
- **现在**：`invoke_json`（结构化）与 `stream_chat`（流式 + 工具）两条路径，
  **记账（`ai_call_log` 一行＝一次真实调用）、失败分类、重试策略、输出预算、
  成本换算、指标上报、span 属性**全都在这一处
- **谁在用**：纪要、自检、说话人匹配、嵌入、问答、会话摘要
- **为什么关键**："一行＝一次真实调用"是全部成本与可靠性数字的地基，只靠约定守不住

### 5. 问答编排 → `services/chat_service.py`

- **收敛前**：（潜在）SSE 层与 MCP 层各拼一套记忆、引用、审核
- **现在**：会话与记忆（滑窗 + 滚动摘要）、引用登记、内容审核、图与工具的注入
  全部在这一处装配；`api/chat.py` 只负责把事件包成 SSE 帧
- **谁在用**：SSE 接口；MCP 走工具层，不需要回答编排

### 附：各自的"统一"清单（不在这五处，但同一原则）

| 机制 | 唯一实现 | 说明 |
|---|---|---|
| 令牌校验 | `common/auth.user_from_token` | HTTP 依赖与 MCP 工具共用（含密码指纹 `pv`） |
| 限流与预算 | `common/ratelimit.py` | 内存 / Redis 两后端同形；Redis 故障 fail-open |
| 长任务调度 | `services/task_queue.py` | 每类一个队列 + 并发上限，另起兼容 worker 消费旧队列 |
| 引用编号 | `services/citations.py` | 登记表按身份去重、编号只增不改、越界编号如实计数 |
| 日志与指标 | `common/metrics.py`、`common/tracing.py` | 同一出口上报（模型出口），日志/指标/span 三读一份源 |

## 四、不变量怎么"下沉"到结构里

规矩写在文档里会被遗忘，写进结构里不会：

| 不变量 | 结构上的落点 | 违规如何被拦下 |
|---|---|---|
| 模型可以建议，不能成交 | 草稿状态机 + 知识库只收 `CONFIRMED` | 非确认纪要进库直接被拒；修订稿必须人工采纳 |
| 无证据不判定 | 契约类型化槽位 + 证据策略表 | 缺证据的断言/意见在校验与门控处被挡 |
| 引用必须能落回原文 | 宿主编号 + 答案 `[n]` + 引用卡片 | 零调用不变量每次 `make smoke` 复查（可定位率、不越权） |
| 检索不得越权 | `allowed_meeting_ids` 的两种语义 + 向量库 payload 过滤 | 解析层与工具层各判一次；空集合恒返回空 |
| 记账不得漏 | 模型调用只有一个出口 | 新增调用类型必须登记（`CALL_TYPE_OWNERSHIP`，测试逐条钉住） |
| 评测不得自说自话 | 宪法六条 + 预注册 + 零调用优先 | CI 只跑零调用检查；`--authorized-llm-calls` 是硬闸 |

## 五、明确不做什么（有理由，不是遗漏）

| 不做 | 为什么 |
|---|---|
| 多 Agent | 无并行子任务、无信任边界、工具只有 4 个——多 Agent 只带来上下文丢失与调试成本 |
| 自由文本转 SQL | 同时带来注入面与幻觉 SQL；事实类问题用具名参数查询 |
| 索引附件文档（PDF/白板等） | 解析质量需要独立评测轴，应单独立项 |
| 长期记忆 / 用户画像 | 会话本身短，滑窗 + 滚动摘要够用；长期记忆要一套独立的写入与过期策略 |
| GraphRAG / LLM Wiki | 跨会议多跳关系不是当前真实需求 |

## 六、还能往哪扩

- **检索质量**：rerank 是已知可选增强（当前混合检索 + RRF）；加之前先按轴 5 建基线
- **引用正确的自动判定**：目前零调用只能判"可定位"，"确证支撑"需要授权判定
- **附件文档进知识库**：单独立项（含独立的解析质量评测轴）
- **多副本**：backend 可多 worker（限流计数已在 Redis）；worker 按类型分队列独立扩
