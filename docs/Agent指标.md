# Agent 侧指标盘点（2026-10-17）

这份文档回答一个问题：**除了轴 5 的四个 RAG 指标，Agent 相关的指标现在到底测了什么、
没测什么。** 数字都连口径；n 小的一律标"方向信号"。

## 一、已经测的

### 1. 意图识别（逐类 F1，零调用评分）

- 样本：`gold/qa_seed.json` 的 **100 条**（q01–q100）；意图标签**全部由代理起草**
  （含 27 条人工题的意图字段），**待人工确认**。
- 分类法：四类，每类对应一个不同动作——`single_fact`（检索）、`aggregation`
  （先列清单）、`cross_meeting`（分别检索多来源）、`smalltalk`（不检索）。
- 当前读数（`make smoke` 的「意图识别」一节，零模型调用）：

| 意图 | 支持数 | precision | recall | F1 |
|---|---:|---:|---:|---:|
| single_fact | 55 | 93.9% | 83.6% | **88.5%** |
| aggregation | 32 | 70.7% | 90.6% | **79.5%** |
| cross_meeting | 8 | 100% | 62.5% | **76.9%** |
| smalltalk | 5 | 100% | 100% | **100%** |
| 宏平均（类等权） | 100 | — | — | **86.2%** |

- 混淆矩阵的主要形态：single_fact→aggregation 9 条；aggregation→single_fact 3 条；
  cross_meeting→aggregation 3 条（8 条支持，样本太小）。
- 置信度/弃权：100/100 有 `confidence`（均值 0.85），**弃权 7 条**；21 题被判为
  并列多问句（提示式分解）。
- **边界**：`cross_meeting` 的标签不能从问题本身判定（"答案落在哪段录音"是语料布局），
  已降级为诊断维度；四类 F1 只作方向信号，不能当强制路由的依据。

### 2. 查询规划的检索效果（两臂，100 题，零判定调用）

| 端点 | 规划关 | 规划开 |
|---|---:|---:|
| 多检索轮次（分解/改写起作用） | 8/100 | **22/100** |
| recall@k | 0.846 | **0.897** |
| MRR | 0.627 | **0.673** |
| nDCG@k | 0.668 | **0.709** |

**只测了检索侧**，没有测"规划对答案质量（faithfulness/relevancy）的影响"。
当前标准配置里规划**默认关**；这组数只说明"开着不比关着差、检索覆盖更高"。

**答案质量 A/B（2026-10-17，27 题）**：

| 臂 | precision | recall | faithfulness 内容级 | AR |
|---|---:|---:|---:|---:|
| 规划关（A4） | **78.9%** | 98.4% | 94.2% | 100% |
| 规划开（C） | 76.1% | **100%** | **98.2%** | 100% |

规划开把 recall/faithfulness 拉高，但 precision 降 2.8pp；预注册要求 precision 或
faithfulness **≥ +4.8pp** 才开启，实际 faithfulness +4.0、precision −2.8，
**不达标，保持默认关**。这组数说明规划是“更全但更宽”，不是无条件更好。

### 3. Agent 行为端点（27 条人工题，P1 标准配置）

| 量 | 读数 | 口径 |
|---|---:|---|
| 轮级失败 / 空答案 | **0/27** | `stop_reason=stalled` 或空答案 |
| 首轮工具调用 | **27/27** | 首轮 `tool_choice=required` 生效 |
| 工具调用总数 | **32**（search 28 + list_facts 4） | 27 轮；4 轮多工具 |
| 引用可定位 / 未越权 | **100%（54/54）/ 100%（74/74）** | 零调用；编编号 0 |
| 每轮 CHAT token | 207,067 / 27 ≈ **7.7k** | 产品 `chat_message.token_count` |
| 每轮延迟（仅 CHAT 调用） | p50 **4.6s**、p90 **6.2s**、p95 **6.7s**、max **9.1s** | `ai_call_log` 按轮求和；不含 rerank/嵌入 |
| rerank | 28 次、平均 **295ms**、**0.0556 元** | 24 候选；单价 500 微元/千 |
| q26 三条金标 | **3/3** | 用 `recorded_at=14:00` 定位 task 7 |

**工具选择的分布（诊断，不是准确率）**：首轮 24 次 `search_knowledge`、3 次
`list_facts`；按意图分，single_fact 16 次 search / 1 次 list_facts，aggregation
8 次 search / 2 次 list_facts。**没有"哪个工具才是对的"的金标**，所以这只是行为分布，
不能算工具选择准确率。

### 4. 扩展集（68 条代理起草，2026-10-17）

这是比 27 条人工集更接近"普遍水平"的读数（仍未人工确认、单一会议）：

| 指标 | 改动前 | 5 步改动后 |
|---|---:|---:|
| context_precision | 39.0%（144/369） | **60.7%（173/285）** |
| context_recall | 88.8%（111/125） | **95.2%（119/125）** |
| faithfulness 内容级 | 90.3%（308/341） | **91.0%（342/376）** |
| answer relevancy | 98.5%（67/68） | **100%（68/68）** |

按来源类型拆 context_precision（改动前→改动后）：chunk（搜索窗口）69.4%→65.9%、
fact（list_facts/get_minutes）18.3%→**42.9%**、segment（get_transcript_excerpt）
1.8%→**34.4%**。按意图：single_fact 51.5/89.7→57.8/93.1、aggregation
59.4/98.0→64.9/98.0、cross_meeting **12.9/56.2→60.0/93.8**。检索侧：全 68 条
0.825/0.713/0.747→**0.915/0.788/0.817**。

**5 步改动后的复测（同一批 68 条）**：precision **60.7%**、recall **95.2%**、
内容级 **91.0%**、AR **100%**；按意图 single_fact 57.8/93.1、aggregation 64.9/98.0、
**cross_meeting 60.0/93.8**；8 条跨录音**全部覆盖两段**（q94 缺 1 条）。
按来源：fact 18.3%→42.9%、segment 1.8%→34.4%、chunk 69.4%→65.9%。
引用：202 条被引、155 条可定位 100%、未越权 100%、unknown 0、missing 0。
CHAT 680,886 token（34+34 两批）。

**结论**：搜索路径本身没问题；改动前的精度塌在“工具返回的东西太多”
（get_minutes 22 条、list_facts 一批、get_transcript_excerpt 112 条）和跨录音只答一段。
5 步改动把整体 precision 从 39.0% 拉到 60.7%、跨录音从 12.9/56.2 拉到 60.0/93.8；
但 68 条仍是代理起草、单会议、单裁判，不能外推成普遍水平。

### 5. 首轮工具选择（50 题诊断，2026-10-17）

金标是**代理起草的启发式**（single_fact→search、aggregation→先列清单、cross_meeting→
分别检索），不是人工金标；只衡量第一步，不衡量多来源覆盖或答案正确性。

| 口径 | 值 | 说明 |
|---|---:|---|
| strict（首轮工具完全匹配） | **60%（30/50）** | aggregation 只有 4/17 用 list_facts |
| acceptable（允许枚举题用检索起步） | **92%（46/50）** | 主要缺口是跨录音题用 list_facts/excerpt 起步 |

逐意图：single_fact **92% / 92%**；aggregation **23.5% / 94.1%**；
cross_meeting **37.5% / 87.5%**。误配 4 条：q90（先 `get_transcript_excerpt`）、
q12（单条负责人题先 list_facts）、q28/q56（先 get_minutes）。后三条里
get_minutes/list_facts 对问题本身未必错，是启发式金标的边界；q90 是真实的工具顺序问题
（先摘录后检索，导致 112 段上下文）。

### 6. 实体核查抽样（95 条答案，2026-10-17）

用产品自己的 `entity_check` 跑 27+68 条答案：**17/95 轮被标注**（17.9%）。
逐条读后**多数是误报**：
- 中文数字改写：答案 `17:00`，原文"下午五点"（q15）；
- 录音/会议元数据：`2026-09-10`、`14:00` 来自录音清单，不在引用正文（q26/q28/q71/q72）；
- 正则残片：`求量`、`关系`、`紧接着`；
- 定位区间：`89-94`、`58-77`（秒数区间被当成数字）。
本轮已修两处明显误报（`负责人为王工` 的前缀、`224s–293s` 的定位秒数），并把
**实体标注从"失败"改成"警告"**：以前标注会让 SSE 走 error、没有 done，与"只标注不拦截"
矛盾；现在 `stop_reason=finished`，标注进 `error_message` 与 `done.entity_flags`。
**结论**：实体核查目前只能当**诊断**，不能当用户面前的红色告警；要上线需先用人工标注
估误报率，再决定阈值/展示。已知漏检：`李婷负责…` 这种没有角色词/前置动词的写法。

### 7. 拒答与编造（12 条不可答题）

| 量 | 读数 | 口径 |
|---|---:|---|
| 拒答率 | **100%（12/12）** | 负样专用 `refused=true`（label g） |
| 编造率 | **0%（0/12）** | `fabricated=true` |
| 负样上下文 useful 率 | **22.2%（8/36）** | 检索仍带回同主题噪声 |

通用 `answered` 字段不是拒答检测器（实测把 12 条"资料不足"全判成 answered=true）；
负样必须用 `refused/fabricated`。

## 三、下一步（按 ROI）

1. **人工确认意图标签**：把 100 条导成盲判包（`gold/annotation.py --export-intent-csv`），
   人工确认后把 `intent_source` 改成 `human`，F1 才能从"方向信号"升格。
2. **工具选择金标（50 题）**：为每题的"第一步该用哪个工具"标一个期望值，算首轮
   工具准确率；这是比"意图 F1"更直接的 Agent 指标。
3. **规划 A/B 加答案质量**：如果要把规划开默认，必须补 faithfulness/relevancy，
   不能只看 recall/MRR。
4. **实体核查抽样**：从 27/68 轮答案里抽 30 条带人名/数字的断言，人工判"该拦没拦/
   不该拦却拦"，估误报/漏报。
5. **把延迟/成本进 smoke**：从 `ai_call_log` 零调用汇总 p50/p95 与每轮成本，
   让 Agent 的体验指标随每次改动复算。
