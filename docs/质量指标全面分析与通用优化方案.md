## 0. 结论先行（TL;DR）

### 0.1 一句话判断

**质量闸 PASS ≠ 质量达标**：冻结基线就是当前读数，全部 delta = 0.00pp；真正的问题是三类——
**(A) 尺子不合格**（金标污染、组装集、单裁判、口径不一致、pass^k 不可评）；
**(B) 证据通道不合格**（工具已返回的元数据没有进入引用快照/判定上下文）；
**(C) 少数机制型短板**（cpCER、检索 precision、工具 over-call、纪要抽取步）。
**答案侧"多写/删除"不是主杠杆**——本轮预注册实验证明：生成后证据校验+有界修复只 +0.5/+1.7pp，
远低于 +5pp 成功线，且低分题被"删不动"的上游问题卡住。

### 0.3 优化总原则（本项目评测宪法 + 本轮审计新增）

1. **先修尺子，再修系统**：P0 只做"让读数可信"的事（金标分层、单次运行、人工锚点、口径统一），不急着调参。
2. **先上游，后下游**：cpCER/说话人归属 → 检索覆盖 → 证据通道 → 生成 → 后处理。答案侧修复只能修"措辞"，修不了"答错"。
3. **每次只改一个机制 + 预注册 + 配对 + 护栏**：任何机制必须同时报"主指标升 + 至少一个护栏不降"，否则登记为"换指标"不下线。
4. **优先数据契约/后处理，而不是继续加长 prompt**：证据边界 prompt 已证明 faith +6.2 / precision −8.2 不是双赢；结构化校验/回执/修复不动检索分母。
5. **不报加权总分**：逐轴、逐指标、带 n/CI/口径；"系统整体质量"只能分层陈述（smoke / realistic / hard / real+human）。

### 1.3 质量闸的真实含义

`evaluation/quality_gate.py` 复算 **PASS**：**旧口径 17 条冻结行 + recall-v2 4 条主指标行全部过线**，另有 4 条 smoke 行（无冻结基线）也全过；每个比例同时打印 **Clopper-Pearson 95% CI**，并校验冻结基线里 7 个产物 + `fact_classes.json`（规范化内容）的 **sha256**（产物/清单变了而基线未重冻 → FAIL；标准重建不误报）。
但 `evaluation/baselines/quality_gate_baseline.json` 的 `frozen_at=2026-10-22`，**frozen 值就是当前 packet 读数**，所以全部 Δ=0.00pp。
它是**防退化护栏**，不是"质量达标证明"。此外报告里的阈值（p0 precision ≥0.58、cross30 ≥0.60 等）与代码 `FLOORS`（0.55/0.55…）**不一致**，引用必须以代码为准（P05）。

## 2. 不合格指标根因分析（R1–R7）

### R1｜评测金标/口径缺陷把 RAG recall 读数压低（影响最大、误读风险最高）

- `cross30_fresh` 的 14 条缺失事实里 **11 条是"系统元数据/否定性结论"**：supersedes_id 为空、CONFIRMED vs DRAFT、工具 notice 原文、"系列只含会议 2"。`context_recall` 只统计**检索上下文**，这些事实按定义不可能出现在上下文里。
- 剔除后按题型：cm 跨录音 **94.74%**、ct 单点 **90.00%**、cs 系列 **42.11%**。
- 结论：**不是"跨录音检索坏了"**；是系列题的 gold 把系统状态写成了 expected fact，且系列状态题本身缺少"系列范围/状态快照"的检索维度。**本轮已换仪器（P0-1，单审计归因待复核）**：分类清单 + recall-v2 主指标 + 质量闸双行（`evaluation/gold/fact_classes.json`、`evaluation/lib/recall_quality.py`、`evaluation/quality_gate.py`）。
- 同类风险：`mixed100` 是组装集；`new_meeting scoped 100%` 只是 smoke；`pass^3` 不可评；人工金标为 0。

### R2｜引用归属/生成约束是答案层首要缺口

- 数字规则 cited-gap 18.31%、any-gap 9.39%；引语 any-gap 18.31%；深判折算真 unsupported 方向约 3.7–7.3%（仅量级）。
- 典型案例：ct06/ct08 "9:00 发布 vs 10:00 公告" 时间对象绑错；m011 引语/发言人归属；m019 notice 原文；m030"回滚无需动数据"与转写相反；m060 两个事项时间被合并推断。
- 机制：模型把 tool metadata（meeting_id/recorded_at/notice）、DRAFT 纪要、检索摘要写成确定事实；引用编号 [n] 只保证"有编号"，不保证"这句话在 ref n 的上下文里"。
- 现状：`rag_quality` 只标注不拦截；长 prompt 约束实验（faith +6.2 / precision −8.2）不是双赢，默认关。

### R3｜检索 precision 与时间绑定

- cross30 fresh precision 63.64%；extended68 67.24%（<68% 目标）；fact 有用率 57.14%（<65%）。
- 机制：top-3 截断 + 单 query；300 字窗口切断跨句事实；复合时间线/清单型问题需要多个窗口（ct02 四个时间节点只召回一个；cm08 补充验收缺口）。
- 精度的改善多来自"分母变小"而非"分子变大"（500×5 → 300×3 的核心结论仍成立）。

### R4｜工具策略：低 F1 的主因是 over-call，不是选错

- first strict 14/27；**12 题只多调、3 题既漏又多、0 题只漏调**；18 次 extra 里 7 次无引用贡献，`query_meeting_state` **5/5 无贡献**。
- 所有"按数量/意图压"的实验（全量路由/选择性路由/仅 hint/仅 budget/强制首工具）都改善部分 F1，但 cross30 faithfulness 齐降（88.63%→73.53–83.69%）。
- 机制：意图边界（cross/aggregation/state 措辞重叠）→ 先调错；不确定 → 多调一个确认；工具返回不告诉模型"覆盖已足够"。

### R5｜裁判与人工锚缺失

- 判定族不是单一：65 个 packet 中 **52 个 deepseek、11 个 qwen、43 个无 `adjudicator_disclosure` 字段**（其中 `citation_packet` 的 citation precision 65.38% 为 qwen 判）；跨族标签翻转历史 26–34%；`JUDGE_CARD.md` 校准 pending；`judge_spotcheck_20.csv` 存在但无 κ 落盘。因此"单裁判"要写成"单族/单次为主、且族不统一"。
- 已知 judge 漏判 4 类（见第 0.2 表第 5 行）；faithfulness 89% 不能当答案正确率。
- 影响：所有"±2–3pp 级"机制效应都落在裁判噪声内；决策必须人工锚或双族一致。

### R6｜上游 ASR 仍是结构第一约束（旧基板）

- c3600 cpCER 30.09%、Δcp +5.06pp；参考/假设长度差异史（假设短 20–40%）说明**内容没进转写 → 下游全错**。
- 剩余 Δcp 已证为**端到端分离固有归属误差**（不是切块），继续压只能换更强的 SA-ASR（MOSS 路线）。
- 轴 2–4 的绝对数都在旧 ASR 基板上，不能与轴 5 当前链路拼"当前系统质量"。

### R7｜评测设计：口径与可重复性（P01–P13）

## 3. 联网调研：可用的通用机制与外部证据

> 完整机制目录（含 61 条文献、66 个 URL、证据分级、不可外推注记）见两篇调研文档；本节只给**结论级摘要**。

### 3.1 检索召回与覆盖（F1/F5）

- **结构化查询分解**：IRCoT（arXiv:2212.10509，4 个多跳集同时提升检索与 QA）证明"检索什么取决于已推导出什么"；Least-to-Most（2205.10625）、Self-Ask（2210.03350）为同族。**通用机制，但必须做成工具参数/逐子查询回执**，而不是全局 prompt（本项目已试全局 plan 提示：检索↑、答案 precision −2.8）。
- **时间/元数据硬过滤**：把"能表达为条件"的限定放 filter 是向量库通用能力（Qdrant filtering、Azure AI Search filters 文档）；相对时间归一（FreshLLMs, 2310.03214）是时间敏感问答的通用前置。
- **自适应检索深度**：Adaptive-RAG（2403.14403）、FLARE（2305.06983）、DRAGIN（2403.10081）用"问题复杂度/信息增益"决定检索次数与停止。
- **融合函数校准**：Bruch et al. TOIS 2023（2210.11934）指出 RRF 对参数敏感、凸组合常优于 RRF；Elastic RRF 文档为工程依据。

### 3.2 上下文精度（F3）

- **句级裁剪/压缩**（保留引用 span）：Provence（2501.16214）、LLMLingua（2310.05736）、Chain-of-Note（2311.09210）；**Lost in the Middle**（ACL 2024 TACL）证明长上下文位置/冗余普遍伤害生成。
- **不要重复已失败的 dedupe**：项目实测"删掉的 10 条相邻窗口全部有用"（precision 81.0→78.4）——冗余窗口不等于噪声，裁剪必须**按是否含新事实/是否可回答问题**，并保留引用身份。

### 3.3 忠实度与引用归属（F2）

- **引用归属是通用未解问题**：ALCE（EMNLP 2023, 2305.14627）报告最好模型仍有 ~50% 引用不完整；AttributionBench（2402.15089）fine-tuned GPT-3.5 归因仅 ~80 macro-F1；RAGTruth（2401.00396）~18k 人工标注显示微调小模型可近大模型 prompt 的幻觉检测。
- **生成后校验/修复**：CoVe（2310.11495）、RARR（2210.08726）、SelfCite（2502.09604）、CiteFix（2504.15629，生产 RAG 后处理引用校正，报告整体准确率相对 +15.46%）。
- **claim 级评测**：FActScore（2305.14251）、SAFE（2403.18802）、RAGChecker（2408.08067）——把长答案拆原子事实再核验，与人类判断相关性更好。
- **本项目的对应实验**：生成前 prompt 约束失败（faith +6.2 / precision −8.2）；生成后"校验+有界修复"安全但增益小（+0.5/+1.7pp）——与本项目失败模式（上游答错、证据通道缺失）一致，不能只靠后处理。

### 3.4 工具调用效率（F4）

- **τ-bench**（2406.12045）用数据库终态 + **pass^k** 衡量可靠性（强模型单次成功 ≠ 多次成功）；**Sufficient Context**（2411.06037）说明模型普遍不会在证据不足时弃答；**ToolBeHonest**（2406.20015）把"任务可解性判断"列为最大错误源；BFCL 榜单把 irrelevance 作为独立类别。
- 结论：工具契约应返回**状态/充分性**（coverage/slot/provenance/empty_reason），按"是否有贡献"而不是"按数量/意图"抑制 over-call。

### 3.5 会议转写与纪要（轴1–轴4）

- **SA-ASR**：MOSS-Transcribe-Diarize 0.9B（Apache-2.0）单次前向输出"谁-何时-说了什么"，模型卡 AliMeeting cpCER **22.17**（CER 24.86、Δcp −2.69）；本项目云端单块 30.09%——方向一致约 8pp。
- **cpCER 口径**：M2MeT/AliMeeting 官方指标；MeetEval cpWER；必须同时报 CER 与 Δcp（改善可能来自"归属对了"而非"字听对了"）。
- **纪要忠实**：HHEM-2.1 擅长精确率侧（RAGTruth-Summ recall 仅 31.86%），不能当唯一裁判；整篇 HHEM 会被"写短/写泛"刷低（项目内 passthrough 0% vs reflected 7.7% 即此现象）。
- **完整性**：FineSurE（ACL 2024）清单法与人工相关 0.677 vs 自由打分 0.295；QMSum（NAACL 2021）query-focused 摘要；项目损失在**抽取步**（0.242），合并步 ≈0。
- **行动项**：AMC-AID（ICASSP 2023）正类 F1；字段级校验 + timex 归一（SUTime/HeidelTime 家族）是通用做法。
- **反思环边界**：Self-Refine（2303.17651）在**有外部可核验反馈**时有效；无反馈时收益不稳（本项目"审查意见相对多调一次模型无额外增益"的负结果与之吻合）。

### 3.6 评测方法（F6/F7）

- **人工锚点 + 双族 judge + 校准**：MT-Bench（>80% 人类一致）、ARES（PPI + 少量人工标注给 CI）、G-Eval、Prometheus；LLM judge 有位置/长度/自我偏好偏差。
- **统计**：配对 bootstrap CI、Clopper-Pearson（小样本比例）、pass^k（多 trial 可靠性）；n=30 的 CI 半宽约 ±14pp，要检出 5pp 需 ≥150–200 配对。
- **防污染/防过拟合**：冻结 holdout、检索式重叠检测、预注册主结局（本项目评测宪法已写）。

## 4. 通用泛化优化方案（按 ROI 分层）

> 每条：**机制 → 为什么通用（不是只对本项目语料）→ 影响哪个失败模式/指标 → 平衡性（哪升可能哪降）→ 验证与门禁 → 默认状态**。
> 所有"预期"都是**可检验假设**，不承诺收益；上线前必须过预注册与配对验证。

### P0（1–2 周，先修尺子与证据通道；零或极低模型成本）

#### P0-1 评测金标清洗与分层（owner：评测侧；零模型调用）——**本轮已落地**

- **机制**：给 `cross30` / `eval100` / `new_meeting` 的 expected_facts 增加 `fact_class`：`retrievable` / `metadata` / `absence` / `fixture` / `conflict`；`context_recall` 主指标只对 `retrievable` 报，其余类单独报"系统元数据一致性"或排除；报告强制同时给 pooled 与逐 case 均值。
- **通用性**：任何"系统状态型 QA"的 gold 都会混入不可检索事实；这是评测构念效度问题，不是本语料特有。
- **实测（更正后）**：cross30 recall 从旧口径 75.86% 改为可检索口径 **88.00%（44/50）**，消除最大误读；仍有 2pp 距 90% 改进目标，且 4 条分类错误已按独立验证改正。
- **验证**：重跑 `evaluation/analysis/quality_gap_report.py`（零调用）；gold 改动 diff 需 2 人复核；quality gate 基线随之重述（新 gold 新基线，旧读数标"旧口径"）。
- **默认**：直接落地（评测资产，不是产品行为）。

#### P0-2 单次 100 题 fresh 运行替换组装集（1 次付费运行）——**本轮已执行，按预注册判定未通过、保留组装集**

- **机制**：用 `evaluation/benchmarks/ask_fresh_sessions.py` 同配置、单次连续跑 100 题（每题新 session、per-case scope），替换 `eval100_scope_fixed_packet.json` 的组装口径；报告 provenance 写入 packet。
- **通用性**：组装集是评测方法问题；单次运行是任何 RAG 评测的基本要求。
- **预期**：消除 P01/P02 的口径不一致；质量闸读数变为"单次可复现"。
- **验证**：与组装集同题逐题配对（记录差异来源：模型随机性 vs 范围）；预算 ~100 题 × ~8 调用 ≈ 800 次，按 `judges/rag.py --ask` 预算闸执行，先预注册。
- **默认**：评测侧；不进产品。

- **实测结果（2026-10-22，§43/§43b）**：100/100 抓取成功、0 空答案；四指标 pooled = precision 71.43%、recall 89.22%、faithfulness **85.02%**、relevancy 99.00%（CP CI 见 LEDGER §43b）。对照组装集：−0.40 / −1.80 / **−4.19** / +2.00pp；四项均 ≥ FLOORS，但 **faithfulness 越过 −2pp 非劣线 → 单次判定 FAIL**。

- **重复运行（2026-10-23，§46/§46b）**：同配置再跑 run2/run3（各 100/100、0 事故）。三次均值：precision **71.83%**、recall **90.02%**、faithfulness **88.34%**、relevancy **99.00%**；faithfulness 极差 **5.000085pp**，按预注册 ≤5pp 严格口径 **FAIL（超 0.000085pp）→ 不切换、保留组装集**。结论：**单次 −4.19pp 主要是运行级波动**（run1 为整次级低异常，符号检验 p≈4.9e-5；均值仅 −0.87pp），**单次读数波动约 5pp 量级**——任何 <2pp 的移动在单次运行里不可分辨。若要换主口径，需重新预注册 N=5 次并以均值/中位数判定（不能把 5.00pp 显示值当 5pp 放行）。
#### P0-3 证据通道补全（产品侧，零模型调用）——**本轮已落地（第一批）**

- **机制**：
  1. `citations.py` 引用快照补全工具已返回但被丢弃的字段——**已修录音 `duration_minutes`**；继续补：`query_meeting_state` 结果级 `notice`（按需进入引用卡片/判定上下文）、`get_minutes` 条目的全部槽位与证据（已有 `_item_text`，核对是否遗漏）、`search_knowledge` 切片的 `source_text`（当前只用 quote）。
  2. `rag_quality` 归因升级——**已修**：区分 `*_attribution_mismatch`（证据在别的 ref 里，可修引用）与 `*_not_in_cited`（哪里都没有，疑似编造）。
- **通用性**：RAG 系统的引用卡片就是"证据快照"；快照丢字段 = 用户与判定者都看不到支撑，属于通用工程缺陷。
- **预期**：直接降低"假 unsupported"（m015 类时长断言、state notice 类）；用户点回体验一致；不改生成、不改检索分母。
- **验证**：单测（已加）；对 cross30 低 faithful 题做离线反事实重判（把工具已返回字段补进 contexts，重判 1–2 题）；真实链路抽样 10 题。
- **默认**：默认开（只是让快照等于工具返回；不改变答案文本）。

#### P0-4 裁判锚点与双族校准（评测侧，人工 + 判定预算）

- **机制**：100 条 claim 级 + 20–40 条答案级人工签名盲评（2 名标注者，报 Cohen's κ）；deepseek 主判 + qwen 跨族复判；`JUDGE_CARD.md` 落盘模型/版本/提示词/校准数字；跨族一致率 <阈值时结论降级。
- **通用性**：LLM judge 的系统偏差是通用问题（位置/长度/自我偏好）；人工锚是唯一校准手段。
- **预期**：把"89% faithfulness"从方向信号升级为可决策；识别 judge 漏判（m030/m032/m060/m001 类）。
- **验证**：κ ≥0.6 才允许进入决策；双族一致率入报告；不达标只报"检不出"。
- **默认**：评测侧；不进产品。

#### P0-5 质量闸/报告口径统一（评测侧，零调用）——**本轮已落地**

- **机制**：`quality_gate.py` 的 `FLOORS` 与报告阈值同步（代码为准）；冻结基线必须**早于**当前改动（当前 frozen=当前，PASS 无信息量）；CI/Clopper-Pearson 区间入报告；`pass^k` 修好（同一配置 3 trial）或如实标"不可评"；`mixed100` 换单次运行后重设基线。
- **通用性**：门禁的统计学意义是通用工程要求。
- **预期**：PASS/FAIL 重新变得有信息量；防止 2pp 噪声被当退化/提升。
- **验证**：`python evaluation/quality_gate.py` + 单测；旧基线保留并标"历史"。
- **默认**：直接落地。

### P1（2–6 周，机制型；每次一个 + 独立 holdout + 配对 + 护栏）

#### P1-1 Claim→span 引用校验与重归属（product-ready 需"最终稿替换"UX）

- **机制**（调研 P0-1 / 本项目实验的升级版）：生成后拆 claim → 规则处理数字/日期/引语（高精度）→ 仅对不确定 claim 调一次小模型 → 动作限定 `rebind / hedge / drop`，**不改事实、不动上下文分母**；修复后守卫（删除比例/压缩比例/引用清空）回退原答案。
- **为什么通用**：ALCE/AttributionBench/CiteFix 均证明引用归属是跨模型、跨数据集的未解问题；后处理是生产 RAG 的通用做法。
- **平衡性**：只改答案层，`context_precision/recall` 不动；风险是过度删除伤内容/relevancy → 用内容覆盖与 relevancy 做护栏。
- **本项目的实测**：已有实验 +0.5/+1.7pp（安全但 <+5pp），且低分题被上游卡住 → **优先级下调为 P1**：先做 P1-4 上游（series 覆盖）与 P0-3 证据通道，再回来做产品化（需要"最终稿替换/纠正事件"的 UX 设计，否则直播流式场景无法隐藏草稿）。
- **门禁**：cross30 faith_content ≥+3pp、precision 不降 >1pp、内容覆盖降 ≤2pp、单题删除 >30% 的 case ≤3；不达标登记"不产品化"。

#### P1-2 工具"证据回执"契约 + 基于状态的停止/补查（调研 P0-2）

- **机制**：每个工具结果统一返回 `coverage/slot_status/provenance/empty_reason/next_actions`；确定性规则判断"是否已足够"；只抑制**同参重复且零新增证据**的调用（以及 `query_meeting_state` 已覆盖时的重复调用）。
- **为什么通用**：τ-bench/Sufficient Context/ToolBeHonest 均指向"状态与充分性"是可验证对象；按贡献抑制是通用 agent 工程。
- **平衡性**：已试的按意图/数量压制全部伤 faithfulness；按贡献压制理论上不伤（有贡献的 extra call 保留）。
- **验证**：fresh trajectory 27 题（tool F1、strict、无贡献 over-call、token）+ cross30 答案质量（faith 非劣 ≤2pp）；同配置配对。
- **门禁**：tool F1 ≥+0.04、无贡献 over-call ≤3、cross30 faith ≥−1pp。
- **默认**：实验开关，过门禁再开。

#### P1-3 结构化查询分解（仅多问句/多来源题；工具参数化，非全局 prompt）

- **机制**：把"拆子问题"作为检索工具显式参数 `subqueries[]`，每个子查询返回命中/覆盖回执；只在检测到多问句/来源缺口时触发（不做全局注入）。
- **为什么通用**：IRCoT/Least-to-Most/Self-Ask 是多跳/多问句的通用前置；检索侧证据强于"全局改写"。
- **平衡性**：召回↑、可能 precision −0~2（多检索多上下文）；用"来源覆盖回执 + 只对缺口补检索"控制分母。
- **验证**：cross30（含 cs/cm/ct 分层）配对：recall、precision、faith、token；先预注册。
- **门禁**：recall ≥+3pp 且 precision 降 ≤2pp 且 faith 不降。

#### P1-4 系列/跨来源覆盖与作用域（cross30 cs* 42% recall 的直接修法）

- **机制**：系列范围（series_id）与会议范围在检索工具里成为显式参数；系列题返回"系列状态快照"（最新会议、已确认/草稿、待办、被替代关系）作为结构化事实，而不是靠模型在转写里猜；"缺失来源/槽位"才补检索（现有 coverage 节点的升级版）。
- **为什么通用**：跨来源覆盖是 agentic RAG 的通用问题（IRCoT 的"下一步检索取决于已获得什么"）；"状态快照 + 结构化事实"与 GraphRAG 的局部做法同源但不建图。
- **平衡性**：召回↑；上下文变多可能压 precision → 快照用结构化字段+引用，不塞整段转写。
- **验证**：cross30 cs/cm/ct 分层 + new_meeting；人工盲评 10 条；配对。
- **门禁**：cs recall ≥+10pp、整体 precision 不降 >2pp、faith 不降。

#### P1-5 检索 precision：句级裁剪（保留 span）+ 融合校准（二选一先做）

- **机制**：对 top-k 上下文做句级裁剪，删"问题无关句"但保留引用 span 身份；或把等权 RRF 换成可用 dev 集校准的加权融合（1 个参数，冻结 holdout 验证）。
- **为什么通用**：Lost in the Middle/Provence/LLMLingua 支持裁剪；Bruch 2023 支持融合校准。
- **平衡性**：precision↑、recall 可能 −≤1pp、faith 不降；裁剪误删是主要风险，用"引用可定位率 100% 保持"做护栏。
- **验证**：cross30 + extended68 配对；检索侧指标 + 四指标；不加候选深度（已证 k=40 只 +0.5pp 但延迟/成本 +36%/+66%）。
- **门禁**：precision ≥+2pp、recall 降 ≤1pp、faith 不降。

#### P1-6 纪要：抽取步 keypoint checklist + 证据契约；轴4 确定性校验

- **机制**：
  - 轴3：分段抽取步输出"原子要点 + 证据 span"（清单式，非自由摘要）；合并步做去重+no-drop；只对弱场/低抽取密度触发 gap-fill（plan+gap-fill 作用在已接近无损的合并步，所以 +1.92pp 不够）。
  - 轴4：`MISSING_DEADLINE` 改为条件规则（证据窗含时间才报）；deadline 必须 timex/`declared_unknown`（field_misuse 自动识别）；owner 必须来自参会人/证据引文（fabricated 检测）；speaker-attributed owner 证据链（谁承诺=谁说话）。
  - 轴2：审查 issue 强制 quote/source_span 证据门控（已部分实现，补齐可定位性）。
- **为什么通用**：FineSurE/QMSum 的清单/抽取范式；timex 归一与字段校验是信息抽取通用做法；证据门控是 RAG 引用通用要求。
- **平衡性**：完整性↑、审查 precision↑；风险是清单噪声（R4 曾出现强场回退）→ 条件触发 + 保默认护栏。
- **验证**：26 场 VCSum 配对（旧基板先做机制验证，换 ASR 后重基线）；轴4 规则零调用离线复算 + 人工抽检。
- **门禁**：core 覆盖 ≥+3pp（预注册阈值）或无显著退化；owner fabricated ≤2%；MISSING_DEADLINE 误报 ≤20%。

### P2（条件触发/长期）

#### P2-1 ASR 引擎切换（MOSS SA-ASR）

- **机制**：`TRANSCRIPTION_ENGINE=http` + 本地 MOSS 侧车（Apache-2.0）；先修复历史失败模式（hub 错误、默认 max_new_tokens 5120 截断、OOM/超时），跑满 8 场，按预注册判定（cpCER ≥5pp 改善且无静默截断/覆盖率守卫通过 → 采纳；否则保持云端）。
- **为什么通用**：SA-ASR 是会议转写主流方向；模型卡 AliMeeting cpCER 22.17 vs 本项目 30.09。
- **平衡性**：cpCER/CER 同时改善；代价是 1 卡 GPU、延迟（RTF≈0.25–0.5，8 场约 40–60min 推理）、运维；必须加**覆盖率/截断守卫**（历史上有过静默截断）。
- **验证**：8 场逐场配对 cpCER/CER/Δcp；覆盖率守卫；产品真实链路 1–2 场复核；预注册（见调研文档 §4.3）。
- **默认**：侧车可选；验证通过后是否默认需单独决策（资源/成本）。

#### P2-2 人工金标与 holdout 换血（评测长期）

- 3–5 场真实会议 + 人工签名金标；holdout 消费 5–10 次换血；报告模板强制 smoke/realistic/hard/real+human 四层。

#### P2-3 条件触发项（现在不做）

- GraphRAG（系列题规模 <50 且无关系型缺口证据）；late chunking/contextual embeddings（已试未过主指标）；本地 claim/citation 小模型（先积累 2–3k 标注）；ColBERT/multi-vector（recall <85% 且人工判语义不足时才考虑）；Semantic chunking（成本未证明值得）。

## 5. 平衡性分析：为什么这些机制不是"换指标"

| 机制 | 升 | 可能降 | 平衡手段 | 判定 |
|---|---|---|---|---|
| 生成后 claim 校验/重归属 | faithfulness、citation attribution | 内容覆盖、relevancy（过度删除） | 动作限 rebind/hedge/drop + 守卫回退 + 内容覆盖护栏 | 已实测：+0.5/+1.7pp、0 变差、覆盖 ±0（安全但不足） |
| 工具证据回执/按贡献抑制 | tool F1、token、无贡献 over-call | faithfulness（若误压有贡献调用） | 只压"同参重复且零新增证据"；有 citation 贡献的保留 | 待验证（预注册） |
| 结构化查询分解 | 跨来源/多问句 recall | context_precision（多上下文） | 只对缺口触发、子查询回执、保留引用身份 | 待验证 |
| 系列覆盖/状态快照 | cs* recall、faith | precision（快照过长） | 结构化字段 + 引用，不塞整段转写 | 待验证 |
| 句级裁剪/融合校准 | context_precision | recall、引用可定位 | 保留 span 身份；引用可定位率 100% 护栏 | 待验证 |
| 纪要抽取步 checklist | 完整性 core | 强场覆盖（清单噪声） | 条件触发 + 保默认护栏（−2pp 预注册） | 待验证（旧基板先做） |
| ASR 换 MOSS | cpCER/CER/Δcp | 可靠性（截断/OOM）、成本/延迟 | 覆盖率守卫 + 逐场配对 + 回滚开关 | 本轮复测中 |
| 全局证据 prompt（已否证） | faithfulness +6.2pp | precision −8.2pp | —— | **默认关，不再走这条路** |
| 意图路由/强制首工具（已否证） | tool F1 | faithfulness −5.6~−15pp | —— | **默认关** |

**结论**：只有"不动检索分母、或只修数据/契约"的机制具备"双赢"潜力；凡是改变"喂给模型的上下文集合/工具策略"的机制，都必须用配对+护栏证明不是拿 precision/faith 换 F1。

- 部署：`compose.yaml` 新增 `asr-sidecar`（profile: moss；可移植 Dockerfile 构建）；
  本机因镜像构建网络慢，用 `scripts/moss_sidecar_container.sh`（compose 网络内、挂载 WSL venv 与
  `C:/moss-model`，`--restart unless-stopped`）。启用手册/回滚：`docs/MOSS-ASR启用.md`。
- **产品链路全量验证（2026-10-23，§47/§47b）**：R8007_M8011（31min）走产品 `/transcription` →
  `SUCCEEDED`、`model_name=moss-transcribe-diarize-0.9b(local)`、墙钟 844s、覆盖率 99.85%、
  **产品 cpCER 13.99% vs 直连 12.35%（+1.64pp ≤2pp 预注册线）**；DB `ai_call_log` 记
  `usage.engine=local-http`（run_a 云端为 50766ms/qwen，可区分）。
- **长场容量（2026-10-23，§48/§48b）**：62.87min 合成材料直连单次跑完（覆盖率 99.92%、无 OOM、
  墙钟 2753.6s/RTF 0.730、峰值显存 98%）；产品 `reject_overlong_audio` 对 >60min 返回 HTTP 400。
  结论：**无放宽余量，守卫取 45min/2700s，超时 2400s**；45–60min 会议需拆段。
- **过程中修复的三个真实缺陷**：①真正执行转写的是 temporal-worker，其 env 陈旧导致
  10-22 的 60s 冒烟实际走云端而详情误显示 local（已 force-recreate worker；展示层改为优先读
  `ai_call_log.model_name` 实际执行值）；②产品链路不传 `max_new_tokens`，侧车默认 5120 在 5.7min
  处静默截断（首轮真实验证覆盖率 27.72%）——侧车 v3 自动按音频时长计算，产品也改为显式传
  `16 tok/s+6144`，并**拒绝 truncated/覆盖率<99% 的输出**（失败而非 SUCCEEDED）；③`task.model_name`
  字段不再作为引擎证据，引擎判定以 `ai_call_log.model_name`/`usage.engine` 为准。
- 回滚：`TRANSCRIPTION_ENGINE=dashscope` + 重建/重启 backend 与 temporal-worker（执行侧是 worker）+ 停侧车。

#### 6.3.3 限制与后续

- **不得**把 MOSS 读数与旧云端基板数字相减：轴 2–4（纪要/行动项/RAG）需按 MOSS 基板重基线。
- **16GB 卡容量实测（§48）**：30.9min 密集场峰值 12.67GB；62.87min 合成场峰值 **15,976/16,303 MiB
  （98%，仅 327MiB 余量）**、RTF 0.730、墙钟 2753.6s（无 OOM，但无放宽余量）→ **90min 不可取、
  60min 也无安全余量**。产品守卫已收窄为 **2700s（45min）**、`ASR_TIMEOUT_SECONDS=2400`；
  >45min 会议拆段；若要单次 60min，需超时 ≥3000s 并在目标机验证 55–60min 显存余量。
- 单路串行 RTF 0.32–0.73（30min 会议 10–19min、45min 最长约 33min），并发转写会排队；
  `ASR_TIMEOUT_SECONDS=2400` 覆盖单任务，多 worker 排队需再放大或串行提交。
- `speaker_label` 为 `S01` 形态，启用后需抽查下游展示/说话人映射。
- 侧车常驻依赖 WSL 存活（休眠/关闭会掉线）；生产建议 compose `asr-sidecar` + 开机自启。
- 产品侧新增守卫（2026-10-23）：显式生成预算 + 覆盖率/截断拒绝（缺口 >2s 或 >1%）+ 展示实际执行
  模型名（单测 645/645）；**执行侧是 temporal-worker，代码变更必须同时重建 backend 与 worker 两个镜像**，
  且 worker 与 backend 的 env 必须同时生效（只重建 backend 会让 worker 继续走旧代码/旧引擎）。

## 8. 诚实边界（不能说的话）

1. **不能说"当前质量达标"**：quality gate PASS 是冻结基线相对回归；cross30 recall 被 gold 污染；单裁判、无人工金标。
2. **不能说"修复了 faithfulness"**：本轮实验只 +0.5/+1.7pp，未过 +5pp；低分题的上游问题（作用域/证据选择/证据通道）未解。
3. **不能说"跨录音检索差"**：cm 跨录音 recall 94.74%；缺口在 cs 系列题（42.11%），且其中 11 条是 gold 元数据事实。
4. **不能说"工具选不对"**：0 题只漏调；主因是 over-call 混合（7/18 无贡献），且按数量硬压会伤 faithfulness。
5. **不能说"MOSS 22.17 可达"**：公开值用官方切分/推理栈；本项目输入是 8 通道平均下混单声道；公开值只作方向锚，实测以 8 场自身指标（宏平均 cpCER 13.47%）为准。
6. **不能把轴 1–4 的旧基板数字与轴 5 当前链路拼成"系统总分"**：评测宪法第 6 条禁止加权总分。
7. **不能说 pass^k 已有结论**：27 题集 `evaluated_cases=0`（只传了 1 份 trial）。
8. **预注册时序不可独立证明**：§40（预注册）与 §40b（结果）在同一未提交工作树里，LEDGER 的 mtime 晚于结果 JSON；内容顺序正确，但"先于调用写死"这件事没有独立 commit 可证。**后续实验规则：预注册单独 commit（或在跑之前打 tag）再执行。**
10. **recall-v2 的类别清单不是双人金标**：`fact_classes.json` 的类别来自 metric-auditor 单次逐条归因（human_checked=false），只标注了缺失事实；`judge_uncertain` 仍计入分母（保守）。round2 独立验证已发现并更正 4 条误分类（cs06×3、n01），提升为最终金标前仍需按 `gold/ANNOTATION_GUIDE.md` 双人复核。
11. **质量闸的 CI 只描述抽样不确定性，不做显著性检验**；n=6/15/30 的区间很宽，PASS 不等于“质量达标”，只表示“未跌破下限/冻结基线”。
9. **MOSS 的 8 场自身指标（cpCER 13.47%）已落盘，但它仍是单基板、单数据集（AliMeeting Eval 远场下混）读数**；不等于真实会议分布，也不与旧云端基板数字相减。产品链路已做 **1 场全量复核**（R8007_M8011：cpCER 13.99% vs 直连 12.35%，+1.64pp）＋ 62.87min 合成容量测试（无 OOM 但显存 98%），但**未做 8 场产品链路 cpCER**，真实会议分布与 >45min 场景仍未验证。
8. **不能把 judge 的 89% 当答案正确率**：已知 4 类漏判（矛盾/归属/过度推断/时间歧义）。
