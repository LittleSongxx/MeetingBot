## 1. 定位重估：为什么换路线

### 1.1 项目本质

它不是"SA-ASR 平台"，而是 **会议智能 Agent**：

```
音频/录音
  └─(MOSS 本地 SA-ASR，已采用)─→ 转写
       └─(LangGraph agent_graph：review→refine→finalize)─→ 纪要（契约 v2）
            ├─→ 用户确认 → KB outbox → pgvector/BM25 索引
            ├─(确认后)─→ action_item / 记忆候选
            └─→ 问答（LangGraph chat_graph：agent→tools→coverage→…）→ 引用
                  └─→ 评测（5 轴/质量闸/预注册）→ 机制改进
```

### 1.2 已完成、可以讲的资产（不要再重复建设）

| 类别 | 资产 | 作品集价值 |
|---|---|---|
| Agent 编排 | 两张 LangGraph 图：`agent_graph`（纪要 review/refine/finalize + 契约/证据门控/支持复核）、`chat_graph`（工具循环 + 三道硬闸 + coverage/nudge/finalize） | **高**：能讲"为什么单 Agent""终止条件为什么必须在代码里" |
| 工具/证据 | 5 个结构化工具、citation registry、coverage plan（来源/槽位）、evidence 状态 | 高：工具契约、证据链 |
| 质量系统 | 5 轴指标、recall-v2、质量闸（CI、sha 冻结、双口径）、预注册/holdout 纪律 | **很高**：评测工程能力稀缺 |
| 数据/实验 | 100 题 fresh、3 次重复（单次波动≈5pp）、claim α 校准、holdout、MOSS 8 场 | 高：会做实验、知道噪声 |
| 引擎 | MOSS 直连 + 产品链路（cpCER 13.47% / 13.99%，+1.64pp） | 中：工程落地能力，但非 Agent 核心 |

### 1.3 已经"过度投入"的部分（后面不再做）

- MOSS 部署运维：worker 镜像/env、超时 2400s、45min 守卫、配额、Docker↔WSL 网络；
- 真人 100 claim 双标（α 已证明 claim 裁判不可靠，再标也主要服务论文级结论）；

  重基线不可测，只做链路完整性验证即可）。

## 2. 当前架构与指标盘点

### 2.1 两条 Agent 主流程

**A. 纪要自检/修订图**（`services/agent_graph.py`）

| 节点/边 | 行为 | 机制亮点 |
|---|---|---|
| `review` | 模型审查纪要 → issues（带 source_span/target_text） | 证据门控 + 契约前提校验（MISSING_DEADLINE 必须有时间语义） |
| 条件边 | issues 非空 → refine；空 → finalize | 轮数由代码兜底（max_rounds） |
| `refine` | 按 issues 有界重写 | 只改 issues 指向的字段；契约 v2 类型化 |
| `finalize` | 落最终稿 + 停止原因 | 支持复核（AGENT_JUDGE）在 refine 前 |

**B. 知识问答图**（`services/chat_graph.py`）

| 节点/边 | 行为 | 机制亮点 |
|---|---|---|
| `agent` | 模型调用（带工具） | 预算累计（token/成本/工具次数）、停滞检测 |
| `tools` | 执行 5 工具 | 结果结构化 + 引用登记 |
| `coverage` | 确定性检查来源/槽位缺口 → 注入一次定向提示 | **不预检索、不替他答**，只让模型自己补 |
| `nudge` | 首轮没调工具 → 结构性提醒一次 | 防"记忆编造"（实测 4 连问 2 次编造后改的） |
| `stop`/`finalize` | 硬闸停止、停止原因/可读说明 | 轮数/token/成本/工具上限/停滞 |

**尚未进入图的能力**（都是候选机制）：查询规划（默认关，证据不足）、意图路由（默认关，
伤 faithfulness）、生成后证据绑定/校验（无）、系列覆盖（coverage 只看单轮来源，不看系列）、
行动项抽取（无独立步）、pass^k（不可评）。

## 3. 缺口诊断：Agent 质量还能从哪里来（按数据）

### 3.1 生成后证据绑定（attribution）— **首选**

- 数据：fresh cross30 数字 **cited-gap 18.31%（39/213）**、any-gap 9.39%（20/213）；
  引语 any-gap 18.31%（13/71）；m030（相反）、m032（归属冲突）、m060（合并推断）是 judge 漏判的
  典型——说明"生成时靠提示词自觉引用"不可靠。
- 机制：`finalize` 前加一个**确定性证据绑定节点**（零模型调用）：
  1) 从答案抽断言（数字/日期/人名/引语/结论句）；
  2) 在**本轮全部检索上下文**里定位证据：命中 → 重绑到正确 `[n]`；命中多个 → 选最相关；
  3) 哪里都没有 → 不删信息，改为**降级表述**（"资料未明确"）并标注 `unbound`；
  4) 记录 `claim→evidence` 映射，供评测/审计。
- **上界已可先算（来自 `quality_gap_report.json#citation_attribution`）**：
  cross30 fresh 数字 cited-gap 39 条，其中 **19 条在"其它检索上下文"里出现**（39−20=19）
  → 纯重绑可消除 19/213=**8.92pp**，cited-gap 上界 **18.31%→9.39%**（恰好等于 any-gap）；
  mixed100 为 74−52=**22 条可重绑**（5.8pp）；extended68 为 46−31=**15 条**（8.0pp）。
  引语则 13 条都不在任何上下文（不可重绑）→ 引语需单独策略（删引号/改转述/标注"未核实"）。
  这条上界**零调用可复算**，是决定是否产品化的第一道闸。
- 预期：数字 cited-gap 18.31%→≤9.4%（上界）；faithfulness 非劣、relevancy 非劣；
  与已有 `rag_quality` 标注、`claim_repair` 实验（+0.5/+1.7pp 未过 +5pp 线）不同——
  这次改**产品运行时**，且主指标是 cited-gap（规则可测、零调用可回放）。
- 验证：**先离线回放**（现有 packet 的 answers+contexts 应用 binder，重算 attribution，0 调用）；
  若回放达不到"消除 ≥15/39 条"，先改进定位规则再产品化；通过后 30 题 fresh off/on A/B
  （~250 CHAT + 60 judge）；不达标默认关。
- 风险：流式输出需要在 `done` 前改写最终答案（前端在 done 时用最终文本刷新即可）；
  过度降级会掉信息量 → 用"降级不删除"。

### 3.2 系列/跨录音覆盖 — **第二优先**

- 数据：cross30 recall-v2 **88.0%（44/50）**，缺口集中在 **cs 系列题 8/19=42.1%**；
  coverage 节点只检查"来源是否覆盖/槽位是否缺失"，不检查**系列内会议是否都被检索**。
- 机制：`CoveragePlan` 增加 series-aware 字段：系列题 → 列出系列全部会议 → 
  `required_sources=系列会议`；状态类槽位（owner/deadline/status/supersedes）跨会议合并校验；
  仍只注入**一条定向提示**，不预检索、不替模型答。
- 预期：cross30 recall 88→93+，precision 非劣；tool F1 可能下降（多调有贡献）→
  用 `tool_utility`/faith 报告，不用 F1 单指标。
- 验证：cross30 30 题 fresh（~300 calls）+ 27 轨迹（~80 calls）；零调用先审计覆盖率。
- 信号：跨会议推理 + "状态一致性"是 Agent 记忆/多源推理的好故事。

### 3.3 行动项抽取 + 规则校验 + 闭环 — **第三优先**

- 数据：owner fabricated **6.3%（9/143）**、deadline field_misuse 14；产品侧 **AMC-AID 无读数**；
  现有 `services/action_item.py` 只有人工/确认后同步，没有"抽取步"。
- 机制：纪要确认前加独立 `extract_action_items`（LLM，1 次/场）：输出结构化
  item（content/owner/deadline/evidence_span/confidence）；**规则校验器**：span 必须可定位、
  owner 必须能在转写里找到、deadline 必须有 timex，否则降级为 open item；与 decisions/pending
  去重；确认后写 `action_item`/待办候选。
- 指标：建 10 场 action-item 金标（AI 起草 + 人工抽检 30 条，`human_checked=false` 明示）：
  item precision/recall/F1、owner fabricated、deadline misuse；目标 F1 ≥0.70、owner ≤2%。
- 验证：10 场生成（~10 calls）+ 判定（~60 calls）；零调用规则检查。
- 信号：结构化抽取 + 可验证性 + 闭环（确认→行动项→问答状态查询）。

### 3.4 完整性抽取步 — **第四优先（时间够再做）**

- 数据：core 覆盖 0.781；损失在**抽取步 0.242**，合并步 ≈0；plan+gap-fill +1.92pp <3pp（已关）。
- 机制：先"抽取原子要点清单"（LLM 1 次/场）→ 生成后对照清单自检 → **只补缺失**（不重写全文）；
  或者把"一步生成"拆成"分段抽取→合并"两步，针对抽取步损失。
- 预期：core 0.781→0.82（+3–4pp），faithfulness 非劣；若达不到就登记负结果（也是好故事）。
- 验证：26 场 VCSum（判定 ~200 calls，双族）；成本较高，放最后。

### 3.5 轨迹/pass^k — **低成本顺手做**

- 数据：tool F1 0.7309；router 提升 F1 但伤 faith（88.63→83.06）；pass^k 不可评。
- 决策：**不压 over-call**（已验证会伤答案），改做两件事：
  1) `tool_utility` 作为产品埋点（每次 extra call 是否贡献引用）——评测叙事用；
  2) **27 题 ×3 trials**（~240 calls）跑 pass^3，把"不可评"变可报。
- 信号：知道"F1 不是唯一目标"是成熟度表现；pass^k 是可靠性故事。
