# 容量模型与压测

这份文档回答两个问题：**现在能扛多少**、**要扩该扩哪里**。数字都是"怎么算出来的"
而不是拍出来的——按下面的模型自己代一遍，比记住结论有用。

## 一、先分清四类负载

| 负载 | 谁在做 | 瓶颈通常在哪 | 典型耗时量级 |
|---|---|---|---|
| 读接口（列表/详情/观测） | backend | MySQL 连接池、接口内串行查询条数 | 10–100 ms |
| 问答（SSE） | backend | **模型供应商的速率与并发**、单轮 3–6 次模型调用 | 5–60 s |
| 转写（长任务） | temporal-worker | ASR 接口配额 + 音频时长（≈0.1× 音频时长） | 分钟级 |
| 纪要/自检/索引（长任务） | temporal-worker | 模型供应商速率上限 | 10 s–数分钟 |

四类负载的扩容动作完全不同：读接口加副本即可（限流计数已在 Redis，见
`common/ratelimit.py`）；长任务受"按类型并发上限"控制（`TEMPORAL_MAX_CONCURRENCY_<类型>`，
每类任务一个队列，一类打满不影响另一类）；问答既受限流（`CHAT_ASK_LIMIT_PER_USER/IP`、
`CHAT_DAILY_TOKEN_BUDGET`）也受供应商配额约束。

## 二、并发上限怎么算（Little 定律）

对任何"请求进、响应出"的系统：

```
同时在线请求数 ≈ 到达率（次/秒） × 平均耗时（秒）
```

**反过来说**：给定并发上限 `C` 与平均耗时 `T`，可持续的吞吐是 `C / T`。

举例（问答）：单轮问答平均耗时 20 s（含 2 次检索 + 3 次生成），希望 5 个用户
同时问不排队，则 backend 侧至少要有 **5 个并发处理中的请求**——FastAPI 是异步的，
这点并发不需要 5 个进程；真正卡住的是**模型供应商的并发配额**与
`CHAT_ASK_LIMIT_PER_USER=30/分钟` 这类限流阈值。也就是说：**问答的容量瓶颈在
配额，不在 CPU**，扩容 backend 副本对问答吞吐几乎没有帮助。

举例（读接口）：平均 60 ms、单副本（uvicorn 2 worker）能跑到 p95 800 ms 的
并发大约是 `C/T` = 几十到上百 QPS 量级；要更高的吞吐先看 MySQL：连接池
`maxsize=10`（`settings.py`），一个副本 10 条连接，N 个副本就是 `10N`，
**先确认 MySQL 的 `max_connections` 跟得上**再谈加副本。

## 三、长任务的容量

每类任务一个 Temporal 队列，并发上限独立可配：

| 环境变量 | 含义 | 默认 |
|---|---|---|
| `TEMPORAL_MAX_CONCURRENCY` | 所有类型的兜底上限 | 2 |
| `TEMPORAL_MAX_CONCURRENCY_TRANSCRIPTION` | 转写并发 | 继承兜底值 |
| `TEMPORAL_MAX_CONCURRENCY_MINUTES` | 纪要生成并发 | 继承兜底值 |
| `TEMPORAL_MAX_CONCURRENCY_AGENT_RUN` | 自检并发 | 继承兜底值 |
| `TEMPORAL_MAX_CONCURRENCY_KB_INDEX` | 知识库索引并发 | 继承兜底值 |

队列名是 `{TEMPORAL_TASK_QUEUE}-{类型}`。升级时会多起一个"兼容 worker"消费旧队列
（升级前入队的任务留在那里），新任务一律进分类型队列。

**排队时间估算**：任务数 `N`、并发 `C`、单任务耗时 `T`，第 `N` 个任务约等
`(N/C)×T`。例如 20 场 1 小时的会议同时入队，转写并发 2、单场约 6 分钟：
最后一场大约 1 小时后开始。**这是设计内的排队，不是故障**——别用"加大并发"解决，
先确认供应商配额与机器负载是否允许。

## 四、实测数据（2026-10-16，本机单副本）

压测脚本在真环境跑过一轮（`grafana/k6:0.54.0` 容器，`--network host` 打本机后端）：

| 场景 | 配置 | 结果 |
|---|---|---|
| 读路径（会议/纪要/转写列表 + 观测页） | 20 VU × 30s，THINK_TIME 0.2s | **6,928 请求 / 0 失败**，p95 **81ms**（阈值 800ms），约 **222 请求/秒** |
| 问答（SSE，走真实模型） | 2 VU × 30s，THINK_TIME 3s | 4 轮完成 / 0 失败，**单轮 p95 17.1s**（avg 15.0s，min 12.1s） |

读路径的余量很大（阈值 800ms，实测 p95 81ms）；问答的耗时几乎全在模型侧。
账本里逐轮核对（`ai_call_log` 按 biz_id 聚合）：**跑 2 轮的轮次模型侧合计 4.6–8.9 秒，
跑 5–6 轮的 14.8–16.7 秒**；k6 观察到的端到端 12.1–17.3 秒正落在多轮那一档——
差额来自检索嵌入与串行开销。**2 并发下没有退化**（min 与 max 的差距来自模型侧抖动，
不是排队）。再往上加并发要先看供应商的并发配额，不是先加 backend 副本。

## 五、怎么跑压测

前置：`./scripts/compose.sh up`（或 `docker compose up -d`），一个可登录账号的 JWT，
以及问答压测需要的会话 id（先在页面上新建一次对话，或调 `POST /chat/session`）。

```bash
# 读路径：20 并发浏览，看 p95 与错误率
k6 run -e BASE_URL=http://127.0.0.1:19091 -e TOKEN=$TOKEN -e VUS=20 -e DURATION=60s \
       scripts/loadtest/read.js

# 问答：5 并发同时提问（会真实产生模型调用与费用，先用最小 VUS 试）
k6 run -e BASE_URL=http://127.0.0.1:19091 -e TOKEN=$TOKEN -e SESSION_ID=1 \
       -e VUS=5 -e DURATION=60s scripts/loadtest/chat.js
```

阈值写在脚本里（首字 p95 < 5s、失败率 < 1%），不达标时 k6 退出码非 0。

**问答压测会花钱**：每次请求都会真实触发模型调用。先用 `VUS=1` 跑 10 秒确认链路，
再逐步加。开跑前把 `CHAT_ASK_LIMIT_PER_USER/CHAT_ASK_LIMIT_PER_IP` 调到不会挡住
计划并发（否则测到的是限流器，不是容量）。

## 六、观测什么

压测期间同时看三处（都在 `/metrics` 与运行观测页）：

| 指标 | 说明 |
|---|---|
| `gen_ai_client_operation_duration_seconds` | 模型调用耗时分布（按模型/调用类型/成功失败） |
| `gen_ai_client_token_usage_total` | token 用量（按输入/输出） |
| `meetingbot_ai_call_cost_micro_total` | 已定价调用的成本合计 |
| `meetingbot_ai_call_unpriced_total` | 未定价调用次数（**它不为 0 时上面那行的成本是不完整的**） |

`/metrics` 默认只在本机端口上可达（compose 把后端端口绑在 127.0.0.1）；
放到别的机器抓取时设 `METRICS_TOKEN` 并要求采集器带 `x-metrics-token` 头。

## 七、这套模型没覆盖的

- **尾延迟**：均值算不出 p99。上线前至少跑一次 30 分钟的稳态压测，看 p95/p99 的分叉。
- **供应商侧的限流**：本项目的限流只约束"自己发出去多少"，供应商仍有自己的 RPM/TPM
  上限，撞上时表现为 `ai_call_log` 里成片的 429（观测页失败原因里能看到）。
- **磁盘**：`storage/` 里是上传的音视频与转写产物，容量按"每人每月录音时长 × 码率"估，
  不在本文档的并发模型里。
