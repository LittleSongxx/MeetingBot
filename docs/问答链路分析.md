# 问答链路分析：四指标首测的 bad case 逐环节诊断

日期：2026-10-16。数据来源：种子会议（两段录音 / 128 转写片段 / 61 检索切片）、
27 组人工标注问答、两个族的判定（`results/rag_packet.json`）、以及 `ai_call_log` 的真实用量。

这份文档回答一个问题：**85.3% / 91.9% / 83.6% / 92.6% 这四个数，坏在哪里、该先修什么。**
结论按"证据 → 根因 → 修法 → 怎么验证"写，不按模块罗列。

---

## 零、结论先行

校准完尺子之后（见第一节），回答质量其实不是主要短板；**真正的短板是四处工程性的**：

| 优先级 | 问题 | 证据 | 修法 | 预期收益 |
|---|---|---|---|---|
| **P0-1** | 工具参数**没有强转**：模型把数组写成字符串 `"[2]"`，langchain 校验直接拒，错误文本还不是 JSON，模型原样重试 3 次 → **停滞闸掐断 → 空答案** | q26/q27 两轮（27 轮里的 2 轮）`stop_reason=stalled`、答案长度 0；手工复现确认 | 参数模型加 `mode="before"` 校验器：字符串先 `json.loads` | 消掉 100% 的轮级失败（2/27 → 0），召回缺口 5/5 全部消失 |
| **P0-2** | 首轮靠"提醒"补救检索：**24/27 轮**完全不检索就直接答，被提醒后重跑 | 每轮模型调用数 − 工具轮数 = 1 的轮次占 89% | 首轮 `tool_choice="required"`（两家供应商已实测支持） | 省 **约 26% token**（≈102k/390k）与一次往返延迟；消除"没检索"分支 |
| **P0-3** | faithfulness 的**口径把出处说明算成不支撑**：83.6% 里 83% 是"以上信息来自…""该会议 meeting_id=2"这类元陈述 | 81 条不支撑里 67 条命中元信息模式 | 判定提示词加一句"跳过关于出处的元陈述"；报告里分列"内容级/全部"两个口径 | 数字从 83.6% → **97.6%**（跨族 98.6%），且不再误导排查方向 |
| **P0-4** | 停滞闸的终止行为**不可读**：掐断后没有答案、用户只看到一句提示 | 同上两轮，`content` 为空 | 停滞/失败时把"最后一次工具错误"作为可读结局返回 | 失败从"什么都没给"变成"告诉用户卡在哪" |

`context precision` 85% 的 15% 噪声是**相关但答不了问题**的片段（同会议、同关键词、
不同问题），不是错会议——这条属于 P1（rerank / 改写 / 过滤），见 2.3。

## 一、先把尺子校准：跨族复判与口径偏差

### 1.1 两个族的对照（同一批 27 轮产物）

| 指标 | A：qwen3.8-max（同族） | B：deepseek-flash（跨族） |
|---|---|---|
| context precision | 85.3%（93/109） | 85.0%（91/107） |
| context recall | 91.9%（57/62） | 91.9%（57/62） |
| faithfulness | 83.6%（414/495） | 88.0%（213/242） |
| answer relevancy | 92.6%（25/27） | 92.6%（25/27） |

**逐条一致率**（同一批上下文与金标事实，可比）：

- 上下文"有没有用"的判定一致率 **98.1%**（105/107）
- 金标事实"找没找到"的判定一致率 **100.0%**（62/62）
- "是否正面回答"的轮级判定一致率 **100%**（27/27，零翻转）

**读法**：`context precision / recall / answer relevancy` 对裁判族稳健（差距 ≤0.3pp，
一致率 ≥98%），可以放心引用；**`faithfulness` 不能直接比**——两个族把答案切成不同粒度
的断言（495 条 vs 242 条），分母差一倍，比率自然不同。这与仓库既有的"换裁判 = 换仪器"
是同一条限制，写在这里以免有人把 83.6% 与 88.0% 当成"测量误差"。

### 1.2 faithsfulness 的口径偏差（这条比跨族差异重要）

把 81 条（A）不支撑断言按内容分类：

| 类别 | 条数 | 占比 | 例子 |
|---|---:|---:|---|
| 元信息 / 出处说明 | 67 | 83% | "以上信息均来自产品发布评审会议。"、"该会议的 meeting_id=2。"、"回答引用了来源 [7] 作为观点条目依据。" |
| 数字或日期 | 9 | 11% | 其中 8 条其实是引用编号（元信息的变体，如"该863秒转写对应上下文编号[1]"） |
| 推断 / 规范化表述 | 2 | 2% | "不允许在构建过程中穿插增量更新"（原文是"建议资料整理完成后再发起构建"）、"会议决策将报表导出异步化改造推迟处理"（原文是条件句） |
| 其它 | 3 | 4% | 同上元的变体 |

**剔除元陈述后的内容级支撑率**：

| 族 | 原口径 | 内容级 |
|---|---|---|
| qwen3.8-max | 83.6%（414/495） | **97.6%（414/424）** |
| deepseek-flash | 88.0%（213/242） | **98.6%（213/216）** |

也就是说：**答案对会议事实的支撑率约 98%**；83.6% 这个数有八成在惩罚"答案自己标注了出处"
这件正确的事。判定提示词要修（P0-3），报告的默认口径也要改成内容级、并保留原口径备查。

### 1.3 真实的内容级编造仍在，但很少

27 轮里找到 1 例明确的实体编造（q14）：

> "此前对话摘要中提到**李婷**、8月31日17:00、产品内弹窗/官网公告/邮件通知等信息。"

核对：`李婷` 在种子数据里**零出现**（`grep` 全表为 0），`弹窗/邮件通知` 也不存在；
而"8月31日17:00"是真实事实（张晨与王工专项评审）。模型把真事实与**编造的人名和
通知渠道**混在一句里，还错标成"来自对话摘要"（摘要里没有这句）。

发生率：内容级断言 495 条里 1–2 条（≈0.3%）。**频率低但性质严重**（编造人名），
属于"判定逮到了、产品没有拦截"的那一类——见 2.5 的修法。

## 二、逐环节诊断

### 2.1 入口层：query 几乎没有处理（当前为空）

**现状**：用户问题原文进检索，无改写、无分解、无意图识别、无路由。
`question_message()` 只做一件事：把模板里的附加要求缀在问题后面。

**证据**：

- **多问句按一次检索处理**：q15「正式发布的时间是什么？**前提条件是什么？**」、
  q24「灰度分几步走？**回滚能力如何？**」都是一次检索回答两问。q24 的
  `context precision` 0.75（4 条里 1 条被判无用）。
- **相对时间不做归一**：q06「最近七天…」——知识库里没有任何"最近七天"的绝对日期，
  模型只能猜。检索到的 3 条被判无用（"只提到需要查看失败率，没有给出具体数值"）。
- **指代无法消解**：q26「**下午这场会**定了哪些行动项」——产品里两段录音挂在同一场会议
  （meeting 2）下，没有"哪段录音"这个维度可查，见 2.2 的第二个现象。

**业界做法**（对齐项）：self-query / metadata filter（把"下午那场"变成过滤条件）、
query rewriting（消解指代与相对时间）、decomposition（多问句拆子查询）、
intent routing（枚举类走结构化查询、单点事实走检索、寒暄直接答）。

**修法**（P1）：见第四节 5–6 条。**先加过滤能力再谈改写**——没有过滤维度时，
改写出来的条件也无处可用。

### 2.2 工具层：参数不健壮 + 选择策略 + 错误不可见

#### 现象一：字符串化参数直接打死一轮（P0-1，最严重）

完整链路（手工复现确认）：

```
模型发出  list_facts(kind="pending_item", meeting_ids="[2]")   ← 数组被写成字符串
   ↓
langchain StructuredTool 用 args_schema 校验 → ValidationError（不是我的校验器拦的）
   ↓
回给模型的 tool 结果**不是 JSON**，而是一段 pydantic 报错文本
   ↓
模型的 SSE 摘要显示"结果无法解析"（我的 summarize_tool_result 解析不了）
   ↓
模型不懂，用**同样的参数**再试一次（第二、三次）
   ↓
停滞闸按"同签名连续 3 次"判停滞 → 掐断 → stop_reason=stalled、答案为空
```

q26/q27 两轮都是这条链路，各 3 次工具调用、0 条引用、0 字答案。
**context recall 缺失的 5 条金标事实全部来自这两轮**——也就是说 91.9% 这个数里，
81% 的缺口是一个参数强转问题造成的。

**根因**：LLM 把数组/对象参数写成 JSON 字符串是**已知高频行为**（`"[2]"`、`"{\"a\":1}"`），
生产级工具层都做宽松解析；我这里没有。

**修法**：参数模型加 `mode="before"` 校验器——字符串先尝试 `json.loads`，成功且类型对得上
就采用；这条修在 `kb_tools` 的参数模型上，聊天与 MCP 两条传输同时受益（一处定义）。

#### 现象二：工具选择本身是合理的，但被"权威级"卡住

工具选择分布：首轮 `search_knowledge` 23/27、`list_facts` 4/27；全部调用 search 31 次、
list_facts 10 次；7 轮调了 3 次工具（多轮）。

q26/q27 问行动项，模型选 `list_facts(kind="pending_item")` ——**这个选择是对的**。
问题在于：两段录音的纪要有两份，**下午那份是 DRAFT**，而 `list_facts` 只读 `CONFIRMED`
（这是"人拍板才算数"的正确实现）。于是模型在这里查不到下午的待办，
**又不知道要回退到转写检索**（search 明明能命中）。

**修法**：工具结果里**显式说明"为什么没有"**——例如 list_facts 返回
`{"facts": [], "notice": "该会议范围内没有已确认的纪要；草稿纪要不算事实，可改用 search_knowledge 检索转写原话"}`。
让"空结果的原因"成为模型可行动的信息，而不是让它自己猜。

#### 现象三：工具错误对用户不可见

工具失败时模型会看到 `{"ok": false, "error": ...}`（这是对的），但**用户看不到**：
页面上只有最终答案，失败被模型消化成"资料不足"。q26/q27 就是这种形态——
用户看到"没有"，看不到"工具卡在参数上"。

**修法**（P0-4）：把最后一轮工具错误作为**结局**的一部分呈现（`stop_reason` 对应的提示里带上原因）。

### 2.3 检索层：召回够用，精确率是主要缺口

**现状**：混合检索（dense + sparse，服务端 RRF）→ `limit=8`（模型自选，实测 2–9 条）。

**证据（噪声的构成）**：被判无用的 16 条上下文，全部是**同一场会、关键词相近、
但回答不了该问题**的窗口：

| 问题 | 无用上下文 | 判定理由（判定模型原话） |
|---|---|---|
| q06 最近七天成功率 | `[risks] 模型服务延迟波动…` | "只提到需要查看失败率，没有给出问题所需的具体数值" |
| q09 转写与纪要流程 | `[261s] 请测试负责人陈琳介绍质量验证情况…` | "只涉及质量验证和边界场景，未说明转写与纪要生成流程" |
| q21 需求验收情况 | `[233s] 论我复述一遍，第一，V2.0按期发布…` | "只涉及发布安排和行动项，未提供验收情况本身" |
| q22 压测暴露的问题 | `[58s] 有两个方案，一是加缓存…` | "只讨论解决方案和工期，未说明压测暴露的具体问题" |

**三条结构性缺口**：

1. **没有元数据过滤维度**：`search_knowledge` 只有 `query/limit/authority` 三个参数，
   **没有会议、时间、语句类型过滤**。所以"下午这场会"、"最近七天"、"关于灰度的决策"
   这类限定只能靠语义相似度碰运气。
2. **没有 rerank**：RRF 融合后的 top-8 直接进上下文；同会议同主题的窗口彼此很"像"，
   排名难以区分"提到了"与"回答了"。
3. **跨轮重复命中**：33 个切片被不同轮次重复检索到 1–4 次（同一场会反复问），
   没有缓存或去重。轮内没有重复（0/27）——说明切块与去重是干净的。

**召回侧**：除失败的两轮外，其余 25 轮的金标事实**全部被检索到**（57/57），
说明混合检索+切块对本语料是够用的。

### 2.4 上下文工程：成本随会话线性增长，没有压缩

**实测**（27 轮共 390k token、92 次调用）：

| 观察 | 数值 |
|---|---|
| 单轮 token | 平均 14.4k，最低 5.7k（第 1 轮），最高 26.5k（第 23 轮） |
| 每轮模型调用 | 2–5 次（含提醒轮与多轮工具） |
| 增长来源 | 滑窗里的 10 条历史消息（其中助手答案平均 461 字、20–30 条断言），加摘要 |
| 浪费 | 提醒机制多跑 24 次调用 ≈ **102k token（26%）** |

**三条缺口**：

1. **历史里的助手消息是全文**：上一轮 20–30 条断言的完整答案进下一轮输入。
   业界做法是"保留结论与引用、压缩过程"（或用摘要代替）。
2. **首轮那份被丢弃的答案仍占上下文**：`stream_answer` 把首轮正文挡在用户之外，
   但它已经进了图的消息状态，后续调用仍要付它的 token。改 `tool_choice="required"` 后
   这一项自然消失。
3. **工具结果不做预算控制**：8 条切片 × 每条最多几百字，问题不大；但没有"按问题裁剪"的机制，
   上下文预算是隐式的。

### 2.5 生成层：答案形态本身在给度量添噪声

**现状**：答案平均 461 字、20–30 条断言，且大量断言是**出处说明**（"以上信息均来自…"、
"该条目为人工确认条目"）。这是提示词要求"给依据"的副作用：模型把"依据"写成了散文式署名。

**两个后果**：

- **度量**：67/81 条"不支撑"来自这些元陈述（第一节 1.2）。
- **成本**：每轮多出 200–300 字，乘以 10 条历史窗口，就是上下文里可观的一块。

**修法**：提示词把"给依据"改成**结构化的一行**（结论 + `[n]` 引用），不要散文式署名；
并把 q14 那类实体编造做成**可检测的护栏**（见 4.11 的实体核查）。

### 2.6 记忆层：能用，但会把错误固化

**现状**：滑窗（10 条）+ 滚动摘要（水位线），实测 8 次摘要调用、摘要长度 3k–7k 字。

**证据（一次真实的污染）**：会话 1 的摘要里留着**修复前的编造内容**：

> "用户反馈最集中的两个问题是**新版搜索响应慢（尤其商品列表页）和优惠券叠加规则提示不清晰**…"

这两件事在会议里**根本不存在**（它们是修复前那次"不检索直接答"的产物）。它们被摘要
压缩后，就成了后续轮次的"事实"。这就是"记忆层放大第一次错误"的完整形态：
**编造 → 答案 → 摘要 → 后续回答的依据**。

**修法**（P1/P2）：

1. 摘要提示词加一句"**摘要不是事实来源**，不得引入原文没有的人名、数字与渠道"；
2. 摘要只压缩**已被引用过的结论**（带 `[n]` 的句子），不压缩自由叙述；
3. 更长远的：答案侧做实体核查（引用里出现的人名/数字必须能在检索结果里找到）。

### 2.7 护栏层：三道闸有效，但"停下来"的体验不可读

- **轮数闸**：未触发（最大 5 轮，上限 6）。
- **停滞闸**：**触发 2 次**（q26/q27），确实拦住了无限重试——但代价是"用户什么都没得到"。
- **token/成本闸**：未触发（单轮最高 26.5k，日预算 500k）。

**结论**：闸门本身是必要的（没有它，那两轮会一直重试到轮数上限，花更多钱、给同样的空答案），
**要修的是终止时的输出**，不是闸门本身。

## 三、与业界对齐评估

| 能力 | 业界主流 | 本项目现状 | 判定 |
|---|---|---|---|
| 检索 | 混合检索 **+ rerank + 元数据过滤** | 混合检索 ✓、RRF ✓、**rerank ✗、过滤 ✗** | **缺两项**（最大差距） |
| query 理解 | 改写 / 分解 / 意图路由 / 相对时间归一 | 无 | **缺** |
| 工具层 | 3–5 工具 + **参数宽松解析** + 错误可自纠 | 4 工具 ✓、参数校验严 ✗、错误可读 ✓ | 部分 |
| Agent 控制 | 单 Agent + 硬闸 + **首轮强制检索** | 单 Agent ✓、三道闸 ✓、强制检索（提醒式）△ | 部分 |
| 上下文工程 | 压缩 / 裁剪 / 显式预算 | 滑窗 ✓、摘要 ✓、**无压缩** | 缺 |
| 记忆 | 工作记忆 + 摘要（+ 长期记忆按需） | 两层 ✓，未做长期 | **达标**（垂类不需要长期记忆） |
| 引用可核验 | 句级/切片级引用 + 可点回 | 编号 + 卡片 + 两条零调用不变量 | **领先** |
| 评测 | RAGAS 四指标 + 检索侧指标（recall@k / MRR） | 四指标 ✓（已跨族复判）、检索侧指标 ✗、意图 F1 ✗ | 部分 |
| 可观测 | token / 成本 / 延迟 / 失败分类 / 成本趋势 | ✓（本轮补齐，含单价与成本） | 达标 |
| 内容护栏 | 输入/输出审核 + 引用核查 | 三层审核 ✓、实体核查 ✗ | 部分 |

**一句话**：这套系统的**"证据链"部分（引用、契约、零调用不变量、跨族判定）明显强于业界通用水平**；
**"检索与查询理解"部分落后于 2026 年的主流**（缺 rerank 与元数据过滤是硬差距）；
**"上下文/记忆工程"做了必需的两层，但缺压缩这一层**。

## 四、优化清单（按 ROI，含验证方式）

### P0（改一处、当天可验）

1. **工具参数宽松解析**（`services/kb_tools.py`）：给 `list_facts.meeting_ids`、

## 六、这次分析自身的方法与限制

- **方法**：四指标 + 跨族复判 + 逐条分类（元信息/数字/实体/推断）+ 链路级复现
  （参数强转那条是手工重放出来的，不是推测）。
- **限制**：
  1. **单会议、27 轮**：所有比例都是方向信号；`context recall 91.9% → ~100%` 这类
     预期是从"缺口全在两轮"推出来的，重跑验证才算数。
  2. **判定仍是模型**（两个族不一致处已标出），不是人类金标。
  3. **成本数字含"提醒"这次无谓调用的输出**：它的输入本就包含在下一轮里，
     26% 是按调用均摊估算的**量级**，不是精确账。
  4. 噪声（无用上下文）只有 16 条，**分类结论的样本非常小**——"噪声都是同会议同主题"
     这个结论来自逐条人工阅读，不是统计。

### 两条只有真跑才会知道的结论

1. **判定仪器本身会移动读数**：同一批输入、同一提示词，`context_precision` 在
   开思考 85.7% / 关思考 60.0% 之间摆动（≈26pp），模型串 alias 与快照只值 2pp。
   首测的 A/B 读数与后来的复判**不是同一把尺子**——引用数字时必须连判定配置一起报。
2. **新能力会被误用**：加了 `date_from/date_to` 之后，模型自己**猜**会议日期
   （猜成 2024 年），过滤器把正确内容全挡在外面，那一轮 3 条金标事实一条没检索到。
   修法是"把猜错的代价封顶"（空结果自动去掉时间限定重试一次），而不是把能力收回。
3. **"这次是不是值得多花一次调用"要按用途分开判**：查询规划最初把"问题里有没有相对时间/
   指代"当成"整轮要不要规划"的开关，结果 100 题只有 12 题拿到意图决策——而枚举类问题
   往往一个时间词都没有，却正是最需要提示的那一类。现在门只管**改写**那一句。
