## 一、元数据过滤与 payload 索引

**行业做法**（Qdrant 官方文档，已核对原文）：

| 做法 | 原文要点 |
|---|---|
| 给**每一个会被过滤的字段**建 payload 索引 | 没有索引时规划器只能读 payload 逐条比对，"会不必要地消耗集群资源"，拖慢其他查询 |
| 索引类型要与取值匹配 | keyword 精确匹配 / integer 范围 / datetime 范围 / bool；`match.any` 比多个 `should` 更快，值多时尤其明显 |
| **建索引要在写入之前** | 过滤感知的 HNSW 边只在建索引之后生成；后补索引要重建 HNSW 才能拿到那部分结构 |
| 硬条件进过滤、**偏好进打分** | "把一切都当硬过滤"是常见错误——一半的"过滤"其实是"偏好"（例如"优先最近"） |
| 权限一律硬过滤 | 返回一条用户看不到的文档是安全事件 |

出处：<https://qdrant.tech/documentation/concepts/indexing/>、<https://qdrant.tech/documentation/concepts/filtering/>

**我们落到哪**：

- `common/qdrant.INDEXED_FIELDS` 声明 5 个过滤字段（`meeting_id` / `authority` /
  `chunk_type` / `meeting_start_epoch` / `source_id`），建库时创建；
  `ensure_collection` 对**已存在的库**也补齐索引。
- `match.any` 用于大列表（会议集合、来源集合）——过滤器统一在 `must` 上（硬条件）。
- 只有**权限**与**显式元数据限定**进过滤；没有把"优先最近的"这类偏好塞进过滤
  （我们的排序仍由 RRF 决定；改排序是 rerank 的事，不是过滤的事）。

**一次真实事故（本轮修掉）**：索引创建原先只发生在"要重嵌"那条路径里
（`_embed_and_store`），而**内容未变化的库会在它之前就返回**——于是最常见的情形
（内容没变）永远建不出索引，过滤一直是慢查询且**不报错**。修法：把"索引就绪"
上移到 `execute_kb_index` 的入口（每条索引路径都过），并在容器内实查
`payload_schema` 五个字段齐备。这类"漏建不报错"的漂移与官方文档点名的
"unindexed filtering 只是慢"完全一致。

**我们没跟着做的**：`is_tenant` 标记、payload 索引的内存档位、稀疏专用字段的
`enable_hnsw: false`（我们规模小，收益不抵复杂度）；"建索引用严格模式拒绝未索引字段"
（需要先在部署上全量建索引，属于运维策略）。

## 二、查询理解：分解、改写与排序

**行业做法**（Azure 架构中心的 RAG 检索阶段指南，已核对原文）：

- **先判简单还是复杂，再决定检索几次**：简单事实问题一次检索；复杂/多部分是
  "多个子问题合起来"，**要分别检索再合并**（"determine whether the query requires
  multiple searches *before* you run any searches"）。
- **子问题必须自包含**：替换代词（it/this/那场）为完整实体、补足限定；
  同一问题里既有依赖型（interdependent）也有并列型（multiple independent）。
- **合并→重排→截断**：多路检索的结果先用 RRF 合并，再过 reranker，最后只把 top-N
  交给生成模型；候选集大小建议 20–50。
- **评测口径**：precision@k / recall@k / MRR；**并明确提醒"离线 MRR 好看不等于线上答案好"**，
  要看 nDCG@K、faithfulness 与"第一名是错文档"的比例。

出处：<https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-information-retrieval>

**路由的行业做法**（Anthropic《Building Effective Agents》，已核对原文）：

- 路由 = "分类输入 → 交给专门的处理"；**只在类别确有不同处理方式时才值得拆**；
  分类必须可靠，否则错误会被放大（"classification is accurate via an LLM or traditional
  model/algorithm"）。
- 总原则：**从最简方案开始**，需要时才加复杂度；工作流给确定性、Agent 给灵活性。

出处：<https://www.anthropic.com/engineering/building-effective-agents>

**检索得到的二手归纳**（搜索无链接，仅作方向参考）：

- 生产级路由普遍是**分层**的：便宜的规则先过，LLM 只处理模糊的那些；带**置信度**、
  **弃权/UNK 通道**与**回退**（"宁可多检索，也不要漏"）；
  路由元数据随响应一起返回，便于观测。
- 多部分问题的分解是"即插即用"的增强（有报告称 MRR@10 +36.7%），代价是多几次 LLM 调用；
  评测要看"分片覆盖"与"答案完整性"两个维度。

**我们落到哪**：

- 查询规划一次调用同时产出：意图、**置信度**、改写、**子问题**、建议工具；
  **提示式注入**（不改工具集、不强制 `tool_choice`）——因为分类还不够可靠，
  强制路由会把误判放大（这正是 Anthropic 那句"分类必须可靠"的推论）。
- **弃权与回退**：置信度 < 0.6 时丢掉工具建议、强制 `needs_retrieval=true`，
  提示里明说"按检索处理"（对齐"宁可多检索"）。
- **分解**：并列多问句拆成自包含子问题，逐条列进提示并要求**分别检索**再合并
  （我们不用固定流水线预取，因为本体是 agentic 的：让 Agent 执行，
  这符合 Azure 指南里"agentic RAG 适用于运行时自适应"的分工）。
- **分类法按"动作"定义**：`procedure`（流程解释）与 `single_fact` 的路由动作完全相同
  （都走检索），而两版提示词下它的 F1 从 53% 摆到 12%——**这条边界不可稳定测量**，
  本轮合并成四类（每类对应一个不同动作）。

**我们没跟着做的**：HyDE、多查询扩展（multi-query）、step-back ——它们都要额外调用，
而我们的检索侧指标（recall@k/MRR/nDCG）**实测 88.9%/0.640/0.682**，先把已有的
分解与过滤量准再说；跨编码器类专用 reranker 没有 GPU、且要引入新服务。

## 三、rerank 的定位（决定"默认关"这个选择是否合理）

**行业共识（二手归纳，搜索无链接，需核对）**：

- **专用 cross-encoder 优于 LLM reranker**：有基准报告显示专用 reranker 的 NDCG@10
  比强 LLM 高 12–15pp，而**点式 LLM 重排甚至会拖垮一阶段召回**；延迟与成本也差 10–30 倍。
- LLM 重排的可用形态是 **listwise 且只在小候选集（约 top 5–10）**；
  点式打分"未校准且慢"。
- rerank **只修排序、不修召回**；上线前要量 nDCG@K 与延迟，不能只看 MRR。

**我们落到哪**：`KB_RERANK_ENABLED` 默认关，且**先量再开**——量它的尺子是零调用的
recall@k/MRR/nDCG（不随判定模型漂移），并同时记延迟（`ai_call_log.elapsed_ms`）。
我们实现的是 listwise 单次调用（候选 24 条），按上面的口径**仍在"待验证"档**：
要么量出收益，要么改成更小的候选集再量，要么引入专用 reranker（有 GPU 时）。

## 四、量到的结果（2026-10-17 两臂真跑）

同一份代码、同一批索引、100 题，只差 `KB_QUERY_PLAN_ENABLED`（零调用尺子，未花判定调用）：

| 端点 | 规划关 | 规划开 |
|---|---:|---:|
| 多检索轮次（分解与改写确实在被用） | 8/100 | **22/100** |
| recall@k | 0.846 | **0.897** |
| MRR | 0.627 | **0.673** |
| nDCG@k | 0.668 | **0.709** |
| 每轮 token / 答案均长 | — / 376 字 | — / 352 字 |

**能说的**：开着不比关着差，且检索覆盖更高、三个指标同向——与 Azure 那条
"分解能提高覆盖"的方向一致。**不能说的**：n=100 下 5pp 未过功效分析，
"规划有效"不是这批数据能支持的结论；rerank **没有量**（行业基准说 LLM 重排在候选一多时
可能拖垮一阶段召回，我们按同一份基准把它的形态收成"listwise 前 10 条 + 并列保持原序"，
**默认仍关**）。

**两处与行业做法的偏离（有意为之）**：
- 官方指南建议固定流水线（先分解、再逐子问题检索、再合并）；我们是 **agentic** 的
  ——分解结果作为提示交给 Agent 自己执行，因为我们没有固定任务集合，
  且 Agent 能按中途结果调整（Azure 指南也把这类归给 agentic RAG）。
- 官方建议候选集 20–50 交给 reranker；我们给 LLM 的窗口**更小（10）**，
  因为后面接的是 LLM 而不是 cross-encoder（后者才适合几十条）。
