# Agent 能力落地方向调研（2026-10-30）

> 目标：回到本项目（AI 会议纪要助手）的具体业务场景，回答「哪些 AI Agent 能力是自然长出来的、值得做；哪些是看起来热闹但不该硬塞的」。
> 方法：外部产品/论文/官方文档调研 → 提炼会议场景共性 → 回到本项目现有工作流、数据、单进程/MySQL 约束逐项判断。
> 说明：**不把旧 MeetingBot 分支当权威参考**；旧分支只作为业界对照的旁证。结论以本文调研与项目约束为准。

## 一、外部调研：会议场景的 AI 能力，行业真正在做什么

### 1.1 产品侧：价值在「会前-会中-会后闭环」，不在「聊天机器人」

| 产品 | 已验证的能力（摘要） |
|---|---|
| **Otter.ai** | 从"记录"扩展到"会前准备、会中提示、会后跟进"：会前基于历史会话/待办/文件生成 pre-meeting brief；会后把对话变成可交付物（跟进邮件、提案、CRM 更新），并明确"ready to review and send"——由人确认后发送。另有跨所有会议提问的 AI Chat。见 [Otter Work Mode/Live Assist](https://otter.ai/blog/otter-rethinks-the-meeting-new-ai-preps-you-coaches-you-and-follows-through)、[Otter AI Chat across meetings](https://otter.ai/blog/otter-ai-chat-unlocking-hidden-gems-across-all-your-meetings) |
| **飞书智能会议纪要** | 会中实时总结；会后"会议纪要千会千面"、**精准提取待办 + 责任人 + 原文溯源**、章节纪要可点击跳转、待办可创建为飞书任务、纪要多人协作、会议速递周报、会议质检。见 [飞书智能会议纪要](https://www.feishu.cn/content/article/7577317993749269689) |
| **腾讯会议 AI 小助手/元宝纪要** | 实时总结要点、会后纪要"真人感"还原（官方新闻页）。见 [腾讯会议新闻](https://meeting.tencent.com/news/aijy20250820.html) |
| **通义听悟** | 章节速览（分割/标题/摘要）、全文摘要/发言总结/问答回顾/思维导图、要点提炼（关键词/待办/重点内容）、口语书面化、说话人分离、词级时间戳。见 [阿里云通义听悟能力](https://help.aliyun.com/zh/tingwu/benefits.md) |
| **Fireflies.ai** | 单场会议 AskFred（问答、总结、行动项、跟进邮件、AI Skills）、**全部历史会议 Global AskFred**、答案 👍/👎 反馈、AI Skills 自动化。见 [AskFred 单场](https://guide.fireflies.ai/articles/6556345325)、[Global AskFred](https://guide.fireflies.ai/articles/1512776728-learn-about-global-askfred) |

**结论 1（产品共性）**：会议 AI 最刚性的价值不是"能聊天"，而是**把会议变成可核对、可执行、可复用的产物**：要点/章节 → 决策与行动项（含负责人/截止）→ 原文溯源 → 跟进/导出/协作。聊天（单场/跨场）是第二层入口，不是第一层。

### 1.2 研究侧：长会议摘要的可靠性与用户真实需求

- **CHI/CSCW 的 LLM meeting recap 研究**（[arXiv:2307.15793](https://arxiv.org/abs/2307.15793)）做了两个设计：**Highlights**（关键要点/行动项，快速总览）与 **Hierarchical**（按章节的纪要，理解讨论脉络）。用户评价：两者互补；行动项需要**可编辑的 assignee/date**，且要能"show context"（展开该条目前后 3 句转写）。用户会通过 add/edit/delete 去调整 AI 纪要——这些编辑本身就是改进模型的信号。
- **长对话直接一把摘要容易产生幻觉**：该研究明确指出，即使先进 LLM，直接处理大段对话也可能幻觉；把转写**按主题分段再摘要**可以降低幻觉、改善主题连贯性。
- **QMSum**（[arXiv:2104.01081](https://arxiv.org/abs/2104.01081)）把"查询驱动的会议摘要"形式化；**MeetingBank**（[ACL 2023](https://virtual2023.aclweb.org/paper_P3774.html)）提供真实会议摘要基准；**ELITR-Bench**（[arXiv:2403.20262](https://arxiv.org/abs/2403.20262)）专门评测"会议助手"长上下文问答，且发现不同模型对 ASR 噪声鲁棒性差异明显。→ 说明**转写噪声、长上下文、问题定位**是会议 AI 的固有问题，需要工程化兜底。
- **Meetalk**（[ACL 2025](https://aclanthology.org/2025.knowllm-1.9/)）用检索增强 + 从**用户编辑反馈**学习个性化结构/风格，并引入"幻觉不确定标记"提示用户复核。→ 说明**把人工确认/修改转成数据**是可行且有效的。

### 1.3 Agent 工程侧：先 workflow，别为了"Agent"而自治

- Anthropic 的 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) 明确区分 **workflow（预定义代码路径）** 与 **agent（LLM 自主决定流程与工具）**：任务定义清晰时优先 workflow；只在开放式问题、无法预知步骤时才用自治 agent。并指出常见增强组件是**检索、工具、记忆**，但"先从最简单的方案开始，只有简单方案不够时才加复杂度"。
- **LLM 自我纠错在无外部反馈时并不可靠**：Huang et al. 的 ICLR 2024 论文 [Large Language Models Cannot Self-Correct Reasoning Yet](https://arxiv.org/abs/2310.01798) 发现"仅凭模型自身"的 self-correction 常常无法改进、甚至变差。→ 对本项目最直接的启示：**现有"审查→重写→收尾"反思环，继续加轮数收益有限；应把"外部证据（转写原文/时间戳）"引入审查**，让 review 变成"对照证据核对"而不是"再问一遍模型"。
- **评估是能力的一部分**：RAGAS（[arXiv:2309.15217](https://arxiv.org/abs/2309.15217)）给出无参考答案的 RAG 评估维度（上下文相关性、faithfulness 等）；LLM-as-a-judge（MT-Bench，[arXiv:2306.05685](https://arxiv.org/abs/2306.05685)）可做规模化近似人工评估。→ 个人项目完全可以用"10~20 场 golden set + LLM judge + 人工抽检"建立质量闸。
- **安全**：转写文本是**不可信数据**，存在间接 Prompt Injection 风险（Greshake et al., [arXiv:2302.12173](https://arxiv.org/abs/2302.12173)）。→ 如果做"会议问答/工具调用"，必须坚持**只读工具 + 权限校验 + 不自动执行外部动作 + 答案带引用**。

**结论 2（Agent 化方式）**：本项目应走"**workflow + 少量受控工具 + 人工确认**"的 agentic system，而不是自治多 Agent。对外可以叫 Agent 能力，但架构上不要为了标签加复杂度。

## 二、回到本项目：现状与"自然延伸点"

当前工作流（fact）：上传资料 → ASR 转写（含说话人/时间戳）→ 六字段结构化纪要（summary/topics/viewpoints/decisions/pending_items/risks）→ 反思环自检 → 人工确认/导出（docx/pdf）。已有资产：

- `TranscriptSegment` 有 `start_ms/end_ms/speaker_label/speaker_user_id/content`（`models.py`），**天生具备"引用到句"的数据基础**；
- 六字段里 `decisions/pending_items` 已经要求模型给出 `owner_suggestion/deadline_suggestion`，**天生就是行动项的原材料**；
- 已有"人工确认"闸门与 AgentStep 时间线，**天生适合 HITL（human-in-the-loop）**；
- 已有 AI 调用日志、Prompt 模板、观测页，**可做评测与成本口径**；
- 约束：MySQL、单进程后端、无向量库/队列，个人项目不能为"概念"引入重基础设施。

判断标准（三个问题，缺一不做）：

1. 它是否直接解决用户**在现有工作流里的下一步真实动作**（核对、分派、追问、回顾、汇报）？
2. 现有数据/流程/权限能否复用，而不需要新增一套基础设施或改变产品定位？
3. 做完能不能用一个具体指标验证"真的有用"，而不是只多了一个页面？

## 三、推荐能力清单（按"自然程度 × 价值 ÷ 成本"排序）

### 能力 1：可核对的纪要（Grounded Minutes / 原文溯源）——最自然，优先级最高

**用户故事**：我看 AI 生成的"决策/待办"时，想知道"它凭什么这么说"；点一下就能看到对应转写片段、谁在什么时间说的；改的时候心里有底。

**为什么本项目最自然**：
- 现有六字段纪要的最大信任瓶颈是"对不对、有没有编"；转写片段已有时间戳与说话人，**不需要新数据源**；
- 行业产品把"原文溯源"当基础能力（飞书待办原文溯源、CHI 研究的 show context）；
- 研究指出长对话摘要会幻觉，**证据绑定 + 人工核对**是比"再加两轮反思"更直接的解法；
- 现有 Agent 反思环可顺势升级为"evidence-grounded review"，不必新建 Agent 框架。

**最小实现（不引入新基础设施）**：
1. 六字段的条目结构增加可选 `evidence: [{segment_no, start_ms, end_ms, quote}]`（JSON 内嵌，兼容旧数据；Prompt/Schema 同步）。
2. 生成后做**确定性绑定**：对模型给出的 quote 在 `transcript_segment` 里做归一化匹配（去标点/空白 + 子串/相似度），绑定失败则标记"未定位"，不静默丢弃；也可让模型输出 segment_no，但以代码回填为准。
3. `agent review` 的输入从"整段截断转写"改为"带证据的条目 + 对应片段"，审查目标改为"证据是否支持该结论 / 是否漏掉反例"（这正好规避当前 20k 字符截断的问题）。
4. 前端纪要详情：每条右侧"原文"按钮 → 弹层显示前后各 1~2 句 + 时间戳 + 说话人；后续可跳转转写详情定位。
5. 导出时可选"带来源"版本（Word 里加脚注/括号时间戳）。

**验证指标**：证据覆盖率（有条目有引用的占比）、引用支持率（人工抽检 30 条，引用是否真的支持结论）、人工修改率下降。

**不做**：不引入向量库；不要求 100% 定位（允许"未定位"并提示）；不做自动改写原纪要。

### 能力 2：质量评测与反馈闭环（Eval + Feedback）——工程上最该先补

**用户故事**（开发者视角）：我改了 Prompt/模型/流程后，怎么知道纪要变好了而不是只是"看起来更顺"？哪些条目用户总在改？

**为什么本项目最自然**：
- 已经有人工确认/编辑动作，**每次确认天然产生"AI 草稿 vs 人工终稿"的监督信号**（Meetalk 的研究正是用用户修正做个性化）；
- 现有 Agent 反思环没有外部质量基准，研究又表明"纯自纠"不可靠（[2310.01798](https://arxiv.org/abs/2310.01798)）——评测就是外部反馈；
- 个人项目不需要大动干戈：`evaluation/` 目录 + 10~20 场 golden set + 脚本即可。

**最小实现**：
1. 生成时保留一份 `ai_draft_json`（六字段原样），人工确认时保存终稿；对比差异得到"修改/删除/新增"统计（不一定要新表，可先放 JSON 字段或轻量 revision 表）。
2. 指标 v0（无参考答案可用 LLM judge，有标注用人工）：
   - **字段覆盖率**：六字段非空比例；
   - **决策/行动项召回**：对照人工标注（10~20 场，每场 3~10 条）；
   - **引用支持率**（配合能力 1）；
   - **人工修改率**：每条目被改的比例；
   - **幻觉抽检**：随机 20 条，人工判定是否可由原文支持。
3. 用 RAGAS/LLM-judge 做规模化近似（[RAGAS](https://arxiv.org/abs/2309.15217)、[MT-Bench](https://arxiv.org/abs/2306.05685)），人工只抽检。
4. 把"Prompt 改动前后跑同一套指标"做成脚本，进 CI 或至少发版前跑一次。

**验证指标**：同一套 golden set 上指标不退化；Prompt 改动可解释。

### 能力 3：行动项闭环（Action Items）——最自然的下游"可执行产物"

**用户故事**：会议确认完，待办不是躺在纪要 JSON 里，而是能勾选、能看负责人/截止、能跟踪状态、能导出给项目协作工具。

**为什么本项目最自然**：
- 六字段里 `pending_items`/`decisions` 已含 owner/deadline 建议，**只差"从建议变成对象"**；
- 行业产品全部把"待办提炼 + 责任人 + 跟进"作为核心（飞书待办转任务、Otter follow-through、AWS 会议摘要+action item 教程）；
- CHI 研究显示用户会直接编辑行动项的 assignee/date——说明这必须是**可编辑的一等对象**，而不是只读文本；
- 它是本项目第一个"**受控写工具**"的自然落点（`create_action_item` / `update_action_item`），为后续对话式 Agent 做工具层铺垫，但**不需要自治**。

**最小实现**：
1. 新表 `action_item(id, meeting_id, minutes_id, content, owner_user_id nullable, owner_text, due_date, status[OPEN/DONE/CANCELLED], source[AI/MANUAL], confirmed_by, create_time, update_time)`；零外键沿用现有约定。
2. 在纪要**确认时**（或确认后手动触发）把 `pending_items` 转成草稿行动项：AI 提取 + 人去重/编辑/确认；未确认不落"有效待办"。
3. 新页面"行动项"：按状态/负责人/会议筛选，支持勾选完成、改负责人/截止日；导出 CSV/ICS（轻量，不接外部系统）。
4. 接口层权限沿用现有模型：管理员看全部、员工看与自己相关的会议/行动项。
5. 可选：下一场同系列会议生成纪要时，把"上次未完成行动项"作为提示注入（轻记忆，见能力 5）。

**验证指标**：行动项提取准确率/召回（人工标注 20 场）、确认率、完成率、从会议到行动的时延。

**不做**：不自动写入飞书/钉钉/Jira/日历；不做"AI 自动分派"；外部同步等有真实需求再做。

### 能力 4：单场会议问答（Ask this meeting）——第二层入口，不急

**用户故事**：这份纪要太长/我关心的点没写在摘要里，我想直接问"张涛负责什么？""预算为什么被砍？"答案要能点回原文。

**为什么本项目适合但排在后面**：
- 行业有需求（Fireflies 单场 AskFred、Otter 会议内 chat），本质是"对单场转写做检索问答"，不需要跨会议基础设施；
- 本项目单场转写规模有限（通常几十分钟），先用关键词/时间/说话人过滤 + 取上下文即可，**不需要向量库**；
- 但它不是"第一层刚需"：用户更常见的是看纪要+待办；聊天是补充入口，且引入会话表/前端面板/成本控制，收益需要能力 1/2 先打底。

**最小实现（如果做）**：
1. 只读工具层：`search_transcript(meeting_id, query, speaker?, time_range?)` → 返回 top-k 片段（含 segment_no/start_ms/speaker/quote）；`get_minutes_fields(meeting_id)`。
2. 单 Agent 循环（最多 2 次工具调用）或直接检索 + 一次生成；答案必须带 `citations`；检索不到就回答"纪要中没有提到"，**不允许编造**。
3. 无会话持久化（前端只保留当前对话），或最简 `chat_message` 表；只读，不写业务数据。
4. 安全：把转写当不可信数据，拒绝"忽略以上指令"类注入；答案不经外部工具执行。

**验证指标**：答案可支持率、引用准确率、"不知道"的精确率（不该答时能否拒答）。

---

### 能力 5（可选）：轻记忆/会议系列——有周期会议再做

**用户故事**：周会/项目例会，上次的待办跟进情况、悬而未决的问题，能否在本次纪要/会前自动带出来？

**为什么排序最后**：行业有 pre-meeting brief/会议速递（Otter Work Mode、飞书会议速递），但完整"记忆"是重设计。本项目可以只做**最轻版本**：
- 按标题/参会人/时间规律识别"同系列会议"（或人工标记）；
- 生成新纪要时，把上一场**未完成行动项 + 未决议题**作为上下文（而不是建长期记忆库）；
- 不做跨会议事实抽取、不做向量记忆、不做自动更新。

**验证指标**：上一场待办带出率、用户是否在确认时保留。

---

### 能力 6（可选）：跟进材料生成（follow-up email / 周报）——低成本增值

- 基于**已确认**的纪要与行动项生成"跟进邮件/周报"草稿（Otter/Fireflies 的同类能力），前端复制/导出，**不自动发送**；
- 属于输出层小功能，不引入基础设施；建议放在能力 1/3 之后顺手做。

## 四、明确不推荐（避免过度设计/硬塞）

| 方向 | 不做的理由 |
|---|---|
| 实时会议机器人入会（Zoom/Teams 自动加入、实时字幕/提示） | 需要平台授权/机器人基础设施/合规评估，与当前"上传后处理"定位不符；个人项目投入产出比最低 |
| 自治多 Agent / orchestrator-workers / 复杂 Agent 编排 | 会议纪要任务路径明确，Anthropic 也建议"任务清晰用 workflow"；多 Agent 只会增加延迟、成本与不可解释性 |
| 全量跨会议对话（Global chat） | Otter/Fireflies 有，但依赖大量历史会议与检索基础设施；本项目会议量小，先做单场问答/待办+导出更自然 |
| 向量数据库 / PostgreSQL / Redis / Temporal / MCP server | 个人项目当前 MySQL + 单进程足够；为这些引入运维复杂度，违背"不过度设计" |
| 自动发邮件 / 自动写日历 / 自动改 CRM / 自动改纪要 | 无明确需求，且违反本项目核心安全设计（AI 只建议、人工确认才写回）；如需外部同步，先做导出/人工触发 |
| 继续给反思环加轮数 | 研究显示无外部反馈的自纠收益有限；应改为"引用证据约束 + 评测"，而不是更长的自问自答 |
| 实时录音/声纹/多模态 PPT 对齐 | 现有 ASR 上传链路已满足本地使用；实时能力属于产品形态变化，不是 Agent 能力补齐 |

## 五、建议落地路线（自然增量，不做大重构）

### Iteration 1（1~3 天）：让纪要"可核对"
- 六字段 schema 增加 `evidence`；生成后确定性绑定到 `transcript_segment`；
- 纪要详情"查看原文"弹层（时间戳+说话人+前后文）；
- Agent review 改为"对照证据审查"，不再扩大截断转写；
- 指标：证据覆盖率、引用支持率（人工抽检）。

### Iteration 2（3~5 天）：让纪要"可执行"
- `action_item` 表 + 确认时生成草稿 + 行动项页面（状态/负责人/截止）+ CSV/ICS 导出；
- 接口权限沿用会议可见/创建人模型；
- 指标：行动项召回/准确、确认率、完成率。

### Iteration 3（约 1 周）：让质量"可证明"
- golden set（10~20 场）+ `evaluation/` 脚本（字段覆盖/决策召回/引用支持/人工修改率）+ LLM-judge 抽检；
- 记录"AI 草稿 ↔ 人工终稿"差异作为反馈数据；
- 指标：改 Prompt/模型前后不退化；可输出一页评测报告。

### Iteration 4（按需）：单场问答 / 系列轻记忆 / 跟进材料
- 先做单场问答（只读工具+引用+拒答），验证真实使用频率后再决定是否跨会议；
- 周会场景再补"上次待办带出"；跟进邮件作为导出层小功能。

## 六、与现有"Agent 自检"的关系（一个关键判断）

现状：`review → refine → finalize` 反思环 + 人工确认。**不建议继续强化"模型自审"**，理由：

1. 研究结论：无外部反馈的 intrinsic self-correction 不可靠（[2310.01798](https://arxiv.org/abs/2310.01798)）；
2. 本项目已有"外部反馈"资源：**转写原文+时间戳、人工确认/编辑**；把它们接进 review/eval，比让模型"再想一遍"更有效；
3. 因此演进方向是：**evidence-grounded review（能力 1）+ feedback-driven eval（能力 2）**，反思环保留为可解释的 workflow（审查→重写→人工确认），而不是升级为自治 Agent。
