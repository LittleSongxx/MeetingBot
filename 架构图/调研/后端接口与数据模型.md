# AIMeeting 后端接口层与数据模型调研（task-1）

> 调研对象：`ai_meeting/fastapi-app`（FastAPI + Tortoise ORM + MySQL + LangChain/LangGraph）与 `ai_meeting.sql`（Navicat dump）。
> 方法：只读静态阅读（read/grep/glob），未启动服务、未连接数据库、未执行任何会读写数据库的脚本；个别结论依赖框架运行时语义，标注为"推断"并说明依据。
> 证据等级：**直接** = 代码/DDL 字面可证；**支持性** = 多处代码或配置联合可证；**推断** = 依据框架/运行时语义推理，未实际运行验证；**未知** = 仓库内没有足够证据。
> 采集时间：2026-10-29。行号以当前文件为准。

## 0. 关键发现（先看这里）

| # | 结论 | 严重度 | 证据等级 |
|---|------|--------|----------|
| 1 | 认证只有"JWT 门票 + 每请求 DB 复核"，没有权限框架、角色表或资源级 ACL；密码明文比较/存储、JWT 密钥硬编码、模型 API Key 明文入库，`ai_meeting.sql` 里还带着真实形态的 `sk-...` 种子数据 | 高 | 直接 |
| 2 | "会议访问权"是唯一数据边界。进入同一会议后，参会人对会议下多数资源（纪要、资料、转写片段）拥有同等写权限；各接口的 owner 校验口径互相不一致（资料删除不校验上传人、转写重试不校验发起人、纪要编辑/确认任何参会人可做、`/agent/selectByMinutes` 可读他人运行） | 中 | 直接/支持性 |
| 3 | 3 个 `/deleteBatch` 把 `ids` 声明为 `List[int]`（FastAPI 视为 query 多值），前端却用 JSON body 发送（`request.delete(url, {data: ids})`），按框架绑定规则会 422，再被统一包装成 `code=500 请求参数错误`。批删大概率不可用 | 中 | 推断（未运行验证） |
| 4 | 13 张表、**零外键**、ORM 侧全是 `IntField` 没有任何关系字段，级联/引用完整性完全手写；存在孤儿记录路径：删纪要或删转写不清理 `agent_run`/`ai_call_log`，删模型配置不检查 `ai_call_log` | 中 | 直接/推断 |
| 5 | 会议状态机实现严格且与注释一致：`SCHEDULED→IN_PROGRESS→FINISHED`、`SCHEDULED→CANCELLED`，仅 ADMIN/创建人/主持人可改，开始时间有 [计划开始-10min, 计划结束] 窗口校验；无自动流转、终态不可回退 | — | 直接 |
| 6 | 没有 StaticFiles/nginx：文件一律走 `FileResponse`；头像下载完全公开；头像 URL 硬编码 `http://127.0.0.1:9090`，Vue 生产环境变量 `VITE_BASE_URL='http://:9090'` 缺主机名 | 中 | 直接 |
| 7 | 注释密度极高、绝大多数与代码一致；少数地方措辞夸大实现（retry 的"条件更新防并发"未校验影响行数、启动恢复只是重新入队、东八区落库依赖部署机时区）。整体可视为"高质量但有个别过度承诺" | 低 | 支持性/推断 |

## 1. 应用装配与路由注册

### 1.1 `main.py`（60 行）装配顺序

1. `lifespan`：启动时依次 `await recover_transcription_tasks()`、`recover_minutes_tasks()`、`recover_agent_runs()`，全部返回后才 `yield` 开始接请求；关闭阶段无动作（`ai_meeting/fastapi-app/main.py:16-28`）。
2. `FastAPI(lifespan=lifespan)`（`main.py:32`）。
3. CORS：`allow_origins=["*"]`、`allow_methods=["*"]`、`allow_headers=["*"]`，未开 `allow_credentials`（`main.py:35-43`）。
4. `app.include_router(api_router)`（`main.py:47`）→ `register_tortoise(..., add_exception_handlers=True)`（`main.py:49`）→ `setup_exceptions(app)`（`main.py:51`）。
5. 根路由 `GET /` 返回 `Result.success()`（`main.py:54-56`）。
6. `uvicorn.run("main:app", host="localhost", reload=True, port=9090)`，仅在 `python main.py` 直跑时生效（`main.py:59-60`）。
7. 未设置 `docs_url/openapi_url` → `/docs`、`/redoc`、`/openapi.json` 默认开启且无需认证（**直接**：全仓库 grep 无覆盖，`main.py` 全文未出现）。

### 1.2 路由自动发现

`api/__init__.py` 先注册 4 个账号级路由（`/login`、`/register`、`/updatePassword`、`/currentUser`，`api/__init__.py:57-117`），再用 `pkgutil.iter_modules` 导入 `api` 包下所有模块，凡有 `router` 属性就 `include_router`（`api/__init__.py:120-123`）。
效果：**新增模块只要定义 `router` 就自动挂载**，没有 `api/v1` 之类版本前缀，也没有集中式路由清单；11 个子 router 的前缀见 `api/*.py` 各自的 `APIRouter(prefix=...)`。

### 1.3 端点规模

- 全部端点 **69 个**（grep `@router.`/`@api_router.` 计数）。
- 鉴权分布：`require_admin` **17 个**、仅 `get_current_user` **49 个**、无鉴权 **3 个**（`/login`、`/register`、`/files/download/{filename}`），另有根路由 `/` 与 `/docs` 系列。
- 响应形态：业务接口统一返回 `Result`（HTTP 恒 200，见 §4）；文件下载/导出用 `FileResponse` 或 `StreamingResponse`；Agent 事件流用 SSE（`text/event-stream`）。

## 3. ② 权限模型实际怎么做

### 3.1 认证机制（不是 OAuth2、不是 Bearer）

- 前端每次请求把 token 放进**自定义请求头 `token`**（`request.js:23-24`）；后端 `get_current_user(token: str | None = Header(default=None))` 从同名头取值（`common/auth.py:21`）。
- token = PyJWT HS256，payload 只有 `sub`(用户ID 字符串)、`role`、`exp`；有效期 `JWT_EXPIRE_HOURS=24`；密钥、算法硬编码在 `settings.py:32-34`，签发在 `common/auth.py:11-18`。
- 每次请求都 `jwt.decode`（校验签名 + exp）后**回查数据库**，用户不存在或 `status != NORMAL` 时抛 `CustomException(..., "401")`（`common/auth.py:26-39`）。
- token 里的 `role` 在授权时**不被信任**：`require_admin` 以数据库记录的 `role` 为准（`common/auth.py:42-48`，注释也明确写了这一点）。
- 密码：登录/注册/改密全部**明文直接比对/写入**（`api/__init__.py:62`、`:83-94`、`:99-112`；`models.py:29-30`；SQL 列注释"登录密码" `ai_meeting.sql:513`；dump 种子 `admin/admin`、`123456` `ai_meeting.sql:534-536`）。无哈希、无加盐、无失败次数限制。
- 退出登录没有服务端接口（无 token 黑名单）；管理员把账号改成 `DISABLED` 后，下一次请求即被 `get_current_user` 拒绝（`common/auth.py:36-38`）。
- 所有鉴权失败都返回 **HTTP 200 + `code:"401"/"403"`**（`common/exception_handler.py:17-24`），前端拦截器按 `code` 跳登录（`request.js:42-45`）。

### 3.2 角色模型

- 只有两种角色：`ADMIN`、`EMPLOYEE`（`models.py:36`；`ai_meeting.sql:516` 注释）。没有角色表、权限表、菜单表。
- `require_admin` 只用于"管理面"17 个端点：部门全部、用户增删/列表、会议删除/删除预览、AI 模型全部、Prompt 模板全部（grep `Depends(require_admin)` 17 处，见 §2 各表）。
- 其余接口用**函数内手写判断** `current_user.role == "ADMIN"` 决定数据范围或放行（如 `meeting.py:95`、`:259`、`:292`；`user.py:176`、`:185`、`:225`、`:236`；`transcription.py:280`、`:318`；`meeting_minutes.py:136`、`:176`、`:237`；`agent.py:48`、`:180`、`:218`；`observability_service.py:93`、`:101`）。
- 注册接口固定 `EMPLOYEE`（`api/__init__.py:90-91`）；管理员只能由已有管理员通过 `/user/add`（`user.py:140-143`）或 `/user/update`（管理员分支不 pop role，`user.py:184-192`）设置。

### 3.3 数据归属：唯一的边界是"会议访问权"

`has_meeting_access`（`api/meeting.py:93-101`）：ADMIN 全通过；创建人或主持人通过；否则查 `meeting_participant` 是否有记录。`get_accessible_meeting` 把"会议不存在"和"无权限"分成 500/403 两种业务码（`meeting.py:104-112`）。
该函数被**级联复用**为几乎所有业务资源的权限入口：

| 资源 | 权限入口链 | 证据 |
|------|------------|------|
| 会议 | `get_accessible_meeting` 直接 | `meeting.py:104-112` |
| 会议资料 | 资料 → 所属会议 | `meeting_material.py:80-86` |
| 转写任务 | 任务 → 所属会议 | `transcription.py:60-66` |
| 转写片段 | 片段 → 任务 → 会议 | `transcription.py:385-394` |
| 会议纪要 | 纪要 → 所属会议 | `meeting_minutes.py:47-53` |
| Agent 运行 | 纪要 → 会议（`/agent/start`、`/agent/selectByMinutes`）；运行归属（其余接口） | `agent.py:42-50`、`:134`、`:198-203` |
| 观测 | 按业务 ID 反查归属，员工只看自己的任务/纪要/运行产生的日志 | `observability_service.py:56-77` |

结论：**"是不是这场会议的参与者"是绝大多数写操作的门槛；再往细的所有权校验只覆盖少数接口**（见 3.4）。

### 3.5 授权缺口与不一致（按严重度）

1. **（高）密码与密钥体系不安全**：明文密码（见 3.1）；JWT 密钥硬编码 `ai-meeting-jwt-secret`（`settings.py:32`）；AI 模型 `api_key` 明文入库（`models.py:151-152`、`ai_meeting.sql:126`、dump 里是 `sk-15ec...` 形态真实 Key `ai_meeting.sql:139-142`）。列表接口只回掩码（`ai_model.py:36-44`、`:59-60`），但数据库/导出文件全暴露。
2. **（中）同会议内写权限过宽**：资料删除（`meeting_material.py:318-323`）、转写重试（`transcription.py:239-248`）、纪要编辑与确认（`meeting_minutes.py:201-226`）都只要求"会议访问权"。一个被拉进会议的普通参会人可以删掉别人上传的资料、重跑别人的转写、改并确认别人的纪要草稿。
3. **（中）跨用户读取运行的旁路**：`/agent/selectByMinutes` 只校验纪要访问权（`agent.py:198-203`），而 `/agent/selectById`、`/events` 校验运行归属（`agent.py:42-50`）——同一份纪要的参会人可以通过前者看到别人运行的完整步骤与修订稿。
4. **（中）纪要归属可被改写**：重新生成纪要时 `created_by=current_user.id` 被覆盖（`meeting_minutes.py:119-126`），于是"谁能删/取消确认"随最后一次生成者变化。
5. **（中）管理员自我保护缺失**：可以把自己 `role` 改成 `EMPLOYEE` 或 `status=DISABLED`（`user.py:167-200` 只保护 delete 场景 `:205-207`、`:216-217`），改完立即失去管理入口。
6. **（低）越权信息面**：任何员工可调用 `/user/selectMeetingCandidates` 获取全公司正常账号的姓名/部门/职位（`user.py:258-276`）；`/user/selectAll` 还会带 phone/email（`user.py:55-81`、`:233-241`）。这是"企业通讯录"性质，但注释未说明其敏感性。
7. **（低）观测口径**：员工看不到自己触发的 `SPEAKER_MATCH` 调用日志（`observability_service.py:68-77`），页面 slogan 却是"个人AI与Agent观测"（`:220`）——属于设计取舍，但与命名有张力。
8. **（低）无审计/无限流/无 CSRF 防重放**：除 `ai_call_log` 外没有操作审计；`/login`、`/register` 无频率限制；token 24h 有效且无吊销列表。

## 4. ③ Result / CustomException / 异常处理器 / 分页约定

### 4.1 Result

`common/result.py:7-25`：

```python
class Result(BaseModel):
    code: str   # '200' 成功、'500' 业务失败、'401' 登录失效、'403' 无权限
    msg: str
    data: Any = None
```

- 成功统一 `Result.success(data)`：用 `jsonable_encoder` 把 ORM/datetime 转可序列化结构（`result.py:15-21`）。
- 失败统一 `Result.error(msg)` → `code="500"`，但**全仓库无调用点**，是死代码（grep `Result.error` 只命中定义 `result.py:24-25`）。
- 业务失败实际全部走 `CustomException`（HTTP 200 + `{code,msg}`，**无 `data` 键**）；前端拦截器用 `typeof res === 'string'` 兼容字符串响应（`request.js:46-49`），说明历史上可能存在返回裸字符串的接口。
- 资源不存在（会议/用户/纪要/任务等）一律用 `CustomException("xxx不存在")`，`code=500`，没有 404 语义（`meeting.py:108`、`user.py:174`、`transcription.py:63` 等）。

### 4.2 CustomException 与 3 个异常处理器（`common/exception_handler.py`）

| 处理器 | 触发 | 返回 | 证据 |
|--------|------|------|------|
| `CustomException(message, code="500")` | 业务主动抛出 | HTTP **200** + `{"code": exc.code, "msg": exc.message}` | `exception_handler.py:8-13`、`:17-24` |
| `RequestValidationError` | 请求体/查询参数类型不合法（422） | HTTP **200** + `{"code":"500","msg":"请求参数错误"}`；`print` 明细到控制台 | `exception_handler.py:26-37` |
| `Exception` | 未捕获异常 | HTTP **200** + `{"code":"500","msg":"系统错误"}`；`print(repr(exc))`；手补 3 个 CORS 响应头 | `exception_handler.py:39-55` |

关键点：
- **"HTTP 永远是 200"是显式设计**（代码注释反复写"http总是返回200"），前端也按 code 分支（`request.js:32-52`）。
- 全项目没有任何 `logging`，只有两处 `print`（grep `logging`/`print(` 仅命中 `exception_handler.py:29`、`:42`）；异常不带请求上下文、不带 traceback，排障只能看控制台。
- 全局异常处理器手工补 `Access-Control-Allow-*`（`exception_handler.py:50-54`），注释说明是"兜底处理器不经过 CORS 中间件"。**推断**：这依赖 Starlette 内部行为，若后续调整中间件顺序可能失效。
- `main.py:49` 的 `register_tortoise(..., add_exception_handlers=True)` 按 Tortoise 惯例还会注册 `DoesNotExist`/`IntegrityError` 处理器（返回非 200、`{"detail": ...}` 形状）。若这些异常逃出业务代码，会**绕过 Result 包装**，前端拿到 `undefined` 的 code。**推断/未知**：未能安装依赖核对 tortoise-orm 1.1.8 的具体注册行为；本次未运行验证。

### 4.3 分页约定

- 统一响应结构：`Result.success(PageInfo(total=..., list=[...]))`，`PageInfo` 两个字段 `total:int`、`list:List[Any]`（`common/result.py:28-32`）；所有 `selectPage` 都遵守（11 处，见 §2）。
- 请求参数两套命名（见 §2.13 第 2 条）：`page_num/page_size` 与 `pageNum/pageSize`。
- `total` 在分页查询之后用**同一个未切片的 QuerySet** 求 count（如 `meeting.py:465-468`、`user.py:301-302`、`department.py:152-154`）。依据 Tortoise QuerySet 的克隆语义，`order_by/offset/limit` 不改变原对象，count 不受分页影响（**支持性**，未运行验证）。
- **无任何边界校验**：`page_num: int = 1`、`page_size: int = 10` 没有 `ge=1`、没有上限（如 `meeting.py:436-437`、`user.py:287-288`）。`page_num=0` 会产生负 offset，`page_size=100000` 会直接压库（**直接**：参数声明处无 Field 约束）。

### 4.4 其它约定细节

- 列表接口普遍是 **N+1 查询**：`meeting_dict` 每条会议再查创建人/主持人/全部参会人/参会人用户/部门（`meeting.py:176-222`），`task_dict` 每任务查 4 张表 + count（`transcription.py:69-118`），`run_dict` 每次查用户/会议/模型/素材（`agent.py:76-128`）。没有 `select_related/prefetch_related`（grep 0 命中），ORM 也没有关系字段可 join。
- 时间统一由 `common/times.py` 输出：`now()` 返回 **+08:00 aware**，`format_datetime` 输出 `YYYY-MM-DD HH:MM:SS` 字符串（`times.py:3-15`）。接口返回的时间一律是预处理过的字符串，而不是 datetime。
- 文件/导出响应不是 Result：`FileResponse`（下载）与 `StreamingResponse`（docx/pdf 导出、SSE 事件流），前端用 `responseType: 'blob'` 分支处理（`request.js:36-39`、`meeting_minutes.py:343`、`agent.py:314-319`）。

### 5.4 ORM 与 SQL 的差异（迁移来源不一致的风险）

- ORM 只声明了唯一性（`unique=True` / `Meta.unique_together`，如 `models.py:107`、`:137`、`:243`、`:339`、`:421`），**没有声明 Dump 里大量普通索引**。因此 `Tortoise.generate_schemas()` 生成的库与 `ai_meeting.sql` 不同；测试正是用 `sqlite://:memory:` + `generate_schemas()`（`tests/test_meeting_material.py:14-22`、`tests/test_timezone.py:15-21`），**测试通过不代表生产 schema 正确**（**支持性**）。
- 列类型是 ORM 粗粒度映射（`TextField` ↔ `text/longtext`、`BigInt` ↔ `bigint`、`JSONField` ↔ `json`），逐列核对未见缺列，但索引/字符集/`COLLATE` 只在 SQL 里（**直接**）。
- `settings.py:28` `use_tz=False` 与 dump 里的 `datetime`（无时区）一致；时间语义见 §8 第 2 条。

### 5.5 参照完整性的手工实现与缺口

已实现的保护（都是应用层手写）：
- 删会议：顺序删 `agent_step → agent_run → meeting_minutes → transcript_segment → transcription_task → meeting_material(+磁盘) → meeting_participant → meeting`（`meeting.py:353-383`）。
- 删转写任务：先删关联纪要（受纪要权限约束）与片段，再删任务（`transcription.py:274-301`）。
- 删 Agent 运行：先删步骤再删运行（`agent.py:280-289`）。
- 删资料：有转写任务引用则拒绝；先删磁盘文件再删记录（`meeting_material.py:307-315`）。
- 删用户：11 项业务引用任一命中即拒绝（`user.py:90-129`）。
- 删部门：有员工即拒绝（`department.py:99-102`）。
- 删模型配置：被转写/纪要/自检引用即拒绝（`ai_model.py:160-176`）。

缺口（无外键的直接后果，**推断**）：
1. 直接删除纪要（`meeting_minutes.py:142-150`）不会检查/清理 `agent_run.minutes_id`，也不会删 `agent_step`（步骤需经 run 级联），留下孤儿运行；`material_name_of_minutes` 对悬空 `minutes_id` 返回 `None`（`minutes_service.py:203-218`）。
2. 删除转写任务/会议时不会清理 `ai_call_log.biz_id` 指向它们的日志；员工观测靠 `biz_id ∈ 自己的业务 ID 集合` 反查（`observability_service.py:56-77`），业务记录删除后这些日志对员工"隐身"，对管理员仍可见。
3. 删除模型配置不检查 `ai_call_log`，日志里的 `model_config_id` 会悬空；观测页按已删除 ID 过滤会被 `CustomException("筛选模型配置不存在")` 拒绝（`observability_service.py:83-85`）。
4. 删除会议不清理 `files/` 下用户头像（头像不属于会议，非缺陷）；也不清理 `ai_call_log`（同 2）。
5. 创建/更新会议时参会人重建是"先全删再插入"（`meeting.py:122-150`），非事务：中途失败会短暂丢名单（**推断**，Tortoise 未显式 `in_transaction`，grep 无 `atomic`/`in_transaction`）。

## 6. ⑤ 文件上传校验与静态文件服务

### 6.1 两个上传入口的校验对比

| 维度 | 头像 `POST /files/upload` | 会议资料 `POST /meetingMaterial/upload/{meeting_id}` |
|------|---------------------------|------------------------------------------------------|
| 鉴权 | 登录即可 | 登录 + 会议访问权 |
| 大小限制 | 5MB，流式边写边计数，超限中断并删残文件（`files.py:14`、`:43-48`） | 500MB，同样流式计数（`meeting_material.py:22`、`:114-122`） |
| 类型校验 | 扩展名白名单 jpg/jpeg/png/gif/webp（`files.py:13`、`:31-33`） | 扩展名分 AUDIO/VIDEO/ATTACHMENT 三类白名单（`meeting_material.py:23-42`） |
| 文件名处理 | `replace("\\","/").split("/")[-1]` 去路径（`files.py:26`） | 同样处理（`meeting_material.py:100`） |
| 存储名 | `uuid4().hex + 原扩展名`（`files.py:37`） | 同（`meeting_material.py:107`） |
| 内容哈希 | **无** | 流式 `hashlib.sha256`，`(meeting_id, file_hash)` 唯一；先查重、再靠 `IntegrityError` 兜底并发（`meeting_material.py:111-161`；DB 唯一键 `ai_meeting.sql:214`；ORM `models.py:137`） |
| MIME | 不使用 | 存浏览器上报的 `file.content_type`，下载时原样作 `media_type`（`meeting_material.py:145`、`:303`）；**未做嗅探/交叉校验** |
| 空文件 | 拒绝（`files.py:49-50`） | 拒绝（`meeting_material.py:123-124`） |
| 失败清理 | `except` 里 unlink 残文件（`files.py:51-54`） | `except` 里 unlink（`meeting_material.py:166-169`）；并发重复时也删副本（`:130`、`:158`） |
| 路径穿越 | 下载侧 `Path(filename).name != filename` 拒绝（`files.py:64-66`） | 下载只接受资料 ID，不拼用户输入路径（`meeting_material.py:290-304`） |

**结论**：会议资料的上传实现是本项目里少数"工程性较强"的部分（流式、限流大小、SHA-256 去重、唯一索引兜底、失败清理齐全）；头像上传相对简单且没有任何去重/MIME 校验。

### 6.2 静态文件服务方式

- **没有 `StaticFiles`、没有 `app.mount`、没有 nginx 配置**（grep `StaticFiles|app.mount` 仅 `main.py:47` 的 `include_router`；仓库也无部署脚本/Dockerfile）。
- 文件落盘位置由 `Path(__file__).resolve().parent.parent / "files"` 推导（`files.py:12`；资料再下一层 `files/meeting_material` `meeting_material.py:21`），不是配置项。当前磁盘上已有 6 个头像文件和 6 个资料文件（目录实测）。
- 对外服务全部走 Python 路由：
  - 头像：`GET /files/download/{filename}`，**无鉴权**，`FileResponse(media_type='application/octet-stream')`（`files.py:62-74`）。
  - 资料：`GET /meetingMaterial/download/{material_id}`，鉴权后 `FileResponse(filename=原始文件名, media_type=入库 MIME)`（`meeting_material.py:290-304`）。
  - ZIP 预览：读中央目录最多 500 条，不做解压（`meeting_material.py:203-242`）；DOCX 预览：python-docx 读取段落+表格，最多 500 块（`:245-287`）。
- 删除联动：删会议时遍历资料删磁盘文件（`meeting.py:361-365`）；删单条资料时同样 unlink（`meeting_material.py:311-313`）。头像文件在用户删除/换头像时**不会被清理**（无对应代码）。

### 6.3 文件相关风险

| 风险 | 说明 | 严重度 | 证据等级 |
|------|------|--------|----------|
| MIME 伪造 | `content_type` 来自客户端，落库并在下载时作为响应 `media_type`；扩展名白名单只能防"存成 .png 的可执行脚本"，防不了伪造 MIME 的 HTML/SVG 内容 | 中 | 支持性（`meeting_material.py:145`、`:303`） |
| 恶意文档解析 | `docxPreview` 直接 python-docx 打开用户上传的 docx，恶意/畸形文件可造成 CPU/内存消耗 | 中 | 推断（`meeting_material.py:259-263`） |
| 磁盘/配额 | 单文件 500MB，但无总量/人均配额、无上传并发限制；500MB 边界只在应用层，没有反代 body limit 配置 | 中 | 推断 |
| 孤儿文件 | 进程被 kill 时 `except` 不执行，可能留下无 DB 记录的残文件；头像不清理 | 低 | 推断 |
| 公开头像 | `/files/download` 无鉴权 + URL 硬编码 | 低 | 直接 |
| 部署地址写死 | `files.py:58` 返回 `http://127.0.0.1:9090/...`；`ai_meeting/vue/.env.development` 是 `http://localhost:9090`，`.env.production` 是 `http://:9090`（缺主机名，生产构建不可用） | 中 | 直接 |

## 7. ⑥ 状态机与"谁能在什么条件下改状态"

### 7.1 会议（`meeting` 表，唯一由 API 直接改的业务状态）

默认 `SCHEDULED`（`models.py:77`；`meeting.py:243`）。合法流转只有 4 条，写在 `change_status` 内的一张字典里（`meeting.py:296-302`）：

| 当前状态 | 允许目标 | 附加条件 | 谁能操作 | 证据 |
|----------|----------|----------|----------|------|
| `SCHEDULED` | `IN_PROGRESS` | 当前时间 ≥ 计划开始-10min 且 ≤ 计划结束 | ADMIN / 创建人 / 主持人 | `meeting.py:292-311` |
| `SCHEDULED` | `CANCELLED` | 必须带 `cancel_reason` | ADMIN / 创建人 / 主持人 | `meeting.py:292`、`:313-314` |
| `IN_PROGRESS` | `FINISHED` | 无时间校验 | ADMIN / 创建人 / 主持人 | `meeting.py:298`、`:315-319` |
| `FINISHED` / `CANCELLED` | 无出边 | 任何操作都拒绝（`transitions.get` 取到空集合） | — | `meeting.py:296-302` |

补充约束：
- 前置条件：调用者必须先有**会议访问权**（`get_accessible_meeting`，`meeting.py:290`），无权限 403；有访问权但不是 ADMIN/创建人/主持人 → 403（`:292-293`）。
- 编辑会议也只允许 `SCHEDULED`（`meeting.py:262-263`），且只有 ADMIN/创建人（不含主持人，`:259-260`）；删除只有 ADMIN（`:323-324`、`:353-354`）。
- **没有自动流转**：没有任何定时任务/钩子按 `start_time/end_time` 自动把会议改成进行中/已结束（全仓库无调度器，grep 无 APScheduler/crontab；`main.py` lifespan 只做恢复）。会议过期不结束会一直停在原状态（**直接**）。
- `CANCELLED/FINISHED` 后没有取消/重开/重新排期接口（`update` 也要求 SCHEDULED），只能删了重建（**直接**）。
- 前端按钮条件与后端同口径（`Meeting.vue:219-221`、`:50-54`），没有"前端能点但后端拒绝"的常见错位（**直接**）。

### 7.3 并发控制手法（本项目实际用了哪几种）

1. **进程内 `asyncio.create_task` + 模块级字典去重**：`schedule_transcription/schedule_minutes/schedule_agent_run` 发现同 ID 协程还在跑就跳过（`transcription_service.py:505-514`、`minutes_service.py:184-193`、`agent_service.py:436-444`）。
2. **信号量限流**：转写与纪要各 `asyncio.Semaphore(2)`（`transcription_service.py:26-30`、`minutes_service.py:78-83`），Agent 无信号量。
3. **条件 UPDATE 抢占**：
   - 转写执行 `filter(id=..., status="PENDING").update(...)`，返回 0 就退出（`transcription_service.py:404-416`）；
   - 转写重试 `filter(id=..., status="FAILED").update(...)`（`transcription.py:255-269`，但**未检查返回值**）；
   - Agent 中断/应用修订 `filter(id=..., status=...).update(...)` 并检查结果（`agent.py:222-230`、`:238-242`）；
   - 会议状态变更是"读后写"，未做条件更新（`meeting.py:290-319`），两个并发请求可能都通过状态机检查后先后写入（**推断**，低风险）。
4. **启动恢复**：`main.py:24-26` 依次重排三类遗留任务；转写把残留 `PROCESSING` 退回 `PENDING`（`transcription_service.py:517-527`），Agent 把残留 `RUNNING` 步骤标记失败后续跑（`agent_service.py:455-460` 与 `:366-368`）。
5. **唯一索引兜底**：转写任务按 `material_id` 唯一、纪要按 `source_task_id` 唯一、资料按 `(meeting_id,file_hash)` 唯一，捕获 `IntegrityError` 后回读（`transcription.py:231-233`、`meeting_minutes.py` 靠先查、`meeting_material.py:152-161`）。

**风险（推断）**：以上 1/2/4 全部是进程内状态，前提是**单进程**。`main.py:59-60` 直跑是单进程 + `reload=True`；若用 `uvicorn --workers N` 或多副本部署，同一 `RUNNING` 的 Agent 运行可能被两个进程同时续跑（`execute_agent_run` 读后判 `status != RUNNING` 即退出，但没有原子抢占，`agent_service.py:361-364`）；纪要的 `execute_minutes` 同样是"读 GENERATING 再跑"无抢占（`minutes_service.py:130-134`）。转写因为有条件 UPDATE 抢占相对安全（`transcription_service.py:404-416`）。仓库没有部署配置/README 说明必须单 worker（无 README/部署脚本）。
