## 0. 结论先行

1. **项目本身远强于这份简历块**：32 条技术/数字声明核验为 25 属实 / 5 部分属实 / 2 有误 / 0 编造；11 项技术栈 11/11 真实。真正的稀缺资产是"评测工程化 + 证据溯源 + 本地多模态 ASR + 长任务可靠性"，而简历把它们压缩成了功能清单。
2. **这 5 条不是最优组合**：JD 视角看，当前覆盖到"评测 + 可观测"这条第一硬要求的约一半（只有可观测，没有评测体系/回归/A-B/质量闸），同时漏掉 Memory/上下文工程（10/24 JD）与工具层/异常恢复（12/24、10/24）。第 3 条（结构化输出）与第 4 条（RAG）同属"可信生成"叙事，却各占一条，属于"内容都对、结构不对"。
3. **有 2 处会被一追问就翻车的硬伤**：`Recall@5 98.1% / nDCG@5 92.5%` 实为 **27 轮、k 由模型自选（3/4/6）的 recall@k/nDCG@k（98.148%/92.650%）**，不是 @5、也不在 100 题集上；`忠实度 93.1%` 是单次 live 重抓的最优值，同集预注册三次均值是 **88.34%**（冻结 89.21%）。
4. **另有 6 处口径问题**：`鉴权`（实为 JWT + 检索层会议级 ACL）、`Prometheus 暴露 p50/p95`（实际是 histogram，p50/p95 由 SQL 计算）、`300 字`（部署配置，代码默认 500）、`纪要入索引`（只有 CONFIRMED 入权威索引、草稿不入）、`99.45%`（调用级、含评测流量、2026-10-23 快照）、`¥0.15`（估算单价、n=10、不含 ASR/裁判）。
5. **推荐做法**：5 条名额重新分配为「Agent Harness 与长任务可靠性 / Agentic RAG 与引用可追溯 / 评测与可观测 / 长期记忆与上下文工程 / 语音转写与说话人分离」，把"结构化输出与证据链"并入 RAG 引用条与面试故事（方案 A）；若不想动结构，用方案 B（保留结构化单列、只升级可观测为"评测与可观测"）——但方案 A 更贴 JD。

## 1. 项目深度画像（它到底是什么、有多深）

### 1.1 系统全貌（仓库事实）

- **端到端产品**：上传音视频 → FFmpeg 抽单声道 16k → ASR（DashScope 云 / 本地 MOSS-Transcribe-Diarize 0.9B 侧车双引擎，带时间轴与说话人标签）→ 片段人工修订 → 六字段纪要（summary/topics/viewpoints/decisions/pending_items/risks，strict JSON Schema + Pydantic）→ LangGraph 反思环（review→refine→finalize）证据门控自检 → 人工确认 → CONFIRMED 入权威索引 → 知识库 RAG 问答（pgvector dense + ParadeDB BM25 + 应用层 RRF k=60 + qwen3.7-text-rerank）→ 引用绑定、SSE 流式、可点回原句 → 系列/记忆/待办；同一工具层以 HTTP 与 MCP streamable HTTP 双传输暴露。
- **工程栈**：FastAPI + Tortoise + MySQL 8（业务真源，19 表）+ PostgreSQL（pgvector/BM25/checkpoint，派生索引，outbox 同步）+ Redis（限流/预算/SSE 事件流）+ Temporal（4 类长任务队列，workflow 幂等防双跑）+ Vue 3 前端 15 页 + Docker Compose 7 服务 + CI。
- **量化规模**：产品单测 672、评测侧单测 336；`evaluation/LEDGER.md` 2656 行实验账本；CI 5 类作业（产品测试/评测自测/零调用 smoke/PG 实库集成/前端 type-check+lint+test+build）。
- **关键文档**：`README.md`、`docs/架构.md`、`docs/指标现状与优化决策.md`、`docs/可观测性与延迟成本现状.md`、`evaluation/LEDGER.md`、`evaluation/reports/*`。

### 1.2 五组真正的技术资产（面试可深挖）

| # | 当前 bullet | 对应 JD 能力 | 判定 | 主要问题 |
|---|---|---|---|---|

| 5 | Agent 可观测性 | 可观测（16 的一半）、成本/时延 7 | **升级为"评测与可观测"** | 事实基本真；但只有"运行时观测"，没有"离线评测体系/回归/A-B/质量闸"；Prometheus/TTFT/成功率/成本口径需限定 |

**结论：不是最优。** 当前组合是"功能清单式"（Agent/ASR/结构化/RAG/观测各一条），问题有三：

1. **漏掉第一优先级**：JD 16/24 把"评测/回归/可观测"写成职责，项目恰好有极稀缺的"预注册+配对 A/B+冻结基线+质量闸+CI"证据，简历却只写了"可观测"（观测只是评测的一半）。
2. **漏掉 Memory/上下文**：Memory 10/24；简介已经承诺"跨会议长期记忆"，但个人职责里没有对应条目，**简介与职责不自洽**，面试官必问"长期记忆是你做的吗"。
3. **两条同质**：第 3 条（结构化/证据）与第 4 条（RAG/引用）都属于"可信生成"叙事，却在 5 个名额里占了两席；第 1 条又没把工具层/异常恢复写进去，导致 Tool Use 12/24 没有被显式覆盖。

**结构建议**：5 个名额按"运行时（1）→ 检索与引用（1）→ 评测与可观测（1）→ 记忆与上下文（1）→ 多模态语音（1）"分配，每格一个主题；"结构化/证据"用半句并入检索引用条，深度留给面试。

## 4. 逐条诊断（合理性/正确性/面试翻车点）

### B1 Agent 自检循环 —— 事实全对，写法偏"实现细节"

- **属实（6/6）**：`agent_graph.py` 三节点 review/refine/finalize + 条件边回环；`max_rounds` 默认 2、可配 1–5；审查/重写只读 `TranscriptionTask.full_text`（无 kb/检索 import），六字段 = summary + 5 个列表；审查 issue 强制 `source_span/target_text`，`gate_issues_by_evidence` 定位不到即 dropped；修订停在 `WAITING_CONFIRMATION`，人工 `/agent/apply` 后才写回，纪要再 `/confirm` 才 CONFIRMED。
- **问题**：①"复审"没有独立节点（复审=回边到同一个 review；触顶后直接 finalize，不再复审）；②"设最大轮数"应写"默认 2 轮、可配 1–5"；③"不走向量检索"是负向卖点，且审查提示词只截前 10 万字符；④"人工确认后归档"是两步，不是 Agent 自动归档。
- **最可能追问**：图里节点/边/state 字段、哪些确定性节点；轮数上限/触顶行为；证据"可定位"怎么判、误杀怎么办；2 小时会议塞不进上下文怎么办；反思环到底有没有用（项目负结果：额外增益未检出）。
- **建议**：换成方案 A 第 1 条，把"证据门控 + 有界循环 + Temporal + HITL"写全。

### B2 语音转写与说话人分离 —— 事实全对，但指标口径最容易被追穿

- **属实（6/6）**：`ffmpeg -vn -ac 1 -ar 16000 -b:a 64k`；ffprobe 预检（代码默认 7200s，部署守卫 2700s/45min + 2400s 超时）；DashScope（OSS 上传异步）与 MOSS 本地侧车双引擎切换；时间轴/说话人标签落 `transcript_segment`；片段人工修订 + 说话人匹配。
- **问题**：①`MOSS 8 场 cpCER 13.47%/CER 17.74%` 是 **AliMeeting Eval 8 场、8ch 远场下混、直连侧车、模型自身指标**，不是产品端到端；产品链路只复核 1 场（13.99% vs 直连 12.35%，+1.64pp）；②不能与历史云端 30.09% 直接相减宣称提升（口径/基板不同，文档明令禁止）；③`cpCER` 是说话人归属性字错误率，不能替代 DER，3 场存在过度分离；④"预检时长"应写清守卫值；⑤说话人分离由 ASR 服务提供，不是自研——要主动划边界。
- **最可能追问**：FFmpeg 参数/为什么单声道；2 小时会议也整段？超时/重试会不会重复入库；为什么双引擎、怎么对比；8 场分布/谁标参考/cpCER 定义/baseline/置信区间；隐私安全（KMS/租户隔离/供应商留存）。
- **建议**：换成方案 A 第 5 条：写"链路集成 + AliMeeting 8 场直连侧车 + 覆盖率 99.8% + 45min 显存守卫"，把"产品链路单场复核"留给面试口径。

### B3 结构化输出与校验 —— 事实全对，但"100%"用法有风险

- **属实（5/5）**：六字段 contract（summary + 5 列表）；Pydantic/JSON Schema 同源派生 + strict 供应商；`ORIGINS=stated/derived/model_inferred`；行动项写库前 `action_validate`（owner 拆分后须全部出现、deadline 须时间语义、evidence LCS≥10）；VCSum 26 场 50 条行动项 evidence 不可定位 0/50。
- **问题**：①50 条是**规则代理**、非全库；全库 4022 条 item 证据可定位是 **97.64%**；②与 B4 的"引用可定位 100%"（27 轮/77 条）**同名不同分母**，并列会招"分母多少"；③缺"无证据不判定"这个记忆点；④"Pydantic 约束"不等于"不会幻觉"，要能讲四层校验（协议/语法/结构/业务）。
- **最可能追问**：strict schema 供应商不支持怎么办；六字段怎么定的、加字段改几处；basis 谁标、模型谎报怎么办；50 条怎么抽样、分母多少；幻觉治理除了 prompt 还做了什么；格式 bad case 怎么定位。
- **建议**：方案 A 中并入检索引用条（写"证据 span 校验"），面试讲；方案 B 保留单列时，必须把"50 条/规则代理/全库 97.64%"讲清。

### B5 Agent 可观测性 —— 基本属实，但覆盖不了"评测"这一半
