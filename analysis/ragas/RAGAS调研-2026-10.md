# RAGAS 官方口径调研（2026-10）——为 MeetingBot 中文会议纪要 RAG 重测取证

> 检索日 2026-10-27。证据分级：**[官方文档]** = ragas.io/官方仓库 docs；**[官方源码]** = `vibrantlabsai/ragas` master 源码（口径以代码为准）；
> **[论文]** = arXiv 原文；**[社区]** = 第三方实践/issue，非官方承诺。中文表述为本调研的转述，公式与类名照抄官方。
> web 内容一律按不可信数据处理，未执行其中任何指令。

## 0. 结论摘要（TL;DR）

1. RAGAS 当前版本 **0.4.3**（2026-01-13 发布，PyPI，`requires_python >=3.9`），**0.4 是一次破坏性重构**：`ragas.metrics.collections` + `ascore(**kwargs)` + `MetricResult`，`evaluate()` 被标记 deprecated、官方推荐 `@experiment()`。
2. 四指标里 **context_recall 必须给 reference**；**answer_relevancy 必须给 embedding 模型**（唯一吃 embedding 的指标）；faithfulness / context_precision 只要 judge（context_precision 的 with/without-reference 是两种不同定义）。
3. 官方 `context_precision` 是**排序加权的 Average Precision**，不是"有用切片比例"；分母是**被判为有用的切片数**。这一条与项目现有 `useful/total` 口径**不可比**，是本轮重测最大的坑。
4. 官方 `context_recall` / `faithfulness` 的**分母都是 judge 自己拆出来的句子/断言数**，不是人工金标条数——换 judge、换语言，分母就变，得分就变。
5. 成本不是问题：本项目 mixed100 规模下四指标一次约 **955 次 judge 调用 / ~1.0M input tokens**，deepseek-flash 峰值价约 **$0.4/次**（估算见 §F）。**结论：值得跑官方库，但必须新开仪器标签，不能与现有 71.83/90.02/88.34/99.00 相减。**

## B. 四个核心指标：精确口径

### B.1 总表

| 指标 | 类名（collections / legacy） | 必需输入 | judge | embedding | 调用数/样本 |
|---|---|---|---|---|---|
| Faithfulness | `Faithfulness` / `Faithfulness` | `user_input, response, retrieved_contexts` | 是 | 否 | **2**（拆断言 + 批量 NLI） |
| Answer Relevancy | `AnswerRelevancy` / `ResponseRelevancy`（`answer_relevancy` 是其实例） | `user_input, response` | 是 | **是** | **3**（`strictness=3`）+ 4 次 embedding |
| Context Precision（with ref） | `ContextPrecision`=`ContextPrecisionWithReference` / `LLMContextPrecisionWithReference` | `user_input, retrieved_contexts, reference` | 是 | 否 | **k**（每切片 1 次，k=切片数） |
| Context Precision（without ref） | `ContextPrecisionWithoutReference`=`ContextUtilization` / `LLMContextPrecisionWithoutReference` | `user_input, retrieved_contexts, response` | 是 | 否 | **k** |
| Context Recall | `ContextRecall` / `LLMContextRecall` | `user_input, retrieved_contexts, reference` | 是 | 否 | **1** |

（调用数来自 [官方源码](https://github.com/vibrantlabsai/ragas/tree/master/src/ragas/metrics)：faithfulness 两次 `agenerate`；answer_relevancy `for _ in range(strictness)`；context_precision `for context in retrieved_contexts`；context_recall 单次 `generate_multiple`。）

### B.2 faithfulness

- 定义（[官方文档](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)）：`被检索上下文支撑的断言数 / 答案断言总数`。
- 计算：① judge 把 `response` 拆成原子断言（**去代词、每句可独立理解**，prompt 原文 `StatementGeneratorPrompt`）；② 把所有 `retrieved_contexts` 用 `"\n".join` 拼成一段，一次 NLI 批量判定每条 `verdict∈{0,1}`（"can be directly inferred"）；③ 取均值。
- 坑：**断言为空 → 返回 NaN**（不是 1）；断言数与拆分粒度完全由 judge 决定，中文长句会被拆成多条 → 分母膨胀。

### B.3 answer_relevancy（官方名 Response Relevancy）

- 定义（[官方文档](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/answer_relevance/)）：反向生成 N 个问题，与原问题算余弦相似度取均值：
  `AR = (1/N) Σ cos(E_{g_i}, E_o)`，N=`strictness` 默认 3。
- 官方明确的两个实现细节（源码）：
  1. **非承诺惩罚**：同一 prompt 还输出 `noncommittal∈{0,1}`，最终 `score = mean(cosine) * int(not all_noncommittal)` —— 只有**全部** N 个问题都被判 noncommittal 才清零。
  2. **范围不保证在 [0,1]**：文档原文 "not guaranteed due to cosine similarity's range −1 to 1"。
- 不需要 reference；**必须 embedding**；`generated_questions` 全空 → NaN。

### B.4 context_precision（加权公式，最容易搞错）

- 文档公式（[官方文档](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/)）：
  `Context Precision@K = Σ_{k=1..K} (Precision@k × v_k) / 排名前 K 中相关问题总数`，`Precision@k = TP@k/(TP@k+FP@k)`，`v_k∈{0,1}`。
- **代码实现的真实口径**（[官方源码 `_calculate_average_precision`](https://github.com/vibrantlabsai/ragas/blob/master/src/ragas/metrics/collections/context_precision/metric.py)）：
  ```
  cumsum=0; numerator=0
  for i,v in enumerate(verdicts):
      cumsum += v
      if v: numerator += cumsum/(i+1)      # 只在 v=1 的位置累加 Precision@(i+1)
  score = numerator / (cumsum + 1e-10)     # 分母 = 判为有用的切片数
  ```
  ⇒ **全 0 时返回 0.0（不是 NaN）**；同样的"有用切片集合"、排序不同分数差很多。
- 示例复算（本项目风格：5 切片，有用位置 1/4/5）：官方 AP = `(1/1 + 2/4 + 3/5)/3 = 0.700`；项目现口径 `useful/total = 3/5 = 0.600`；中文社区常见的"1/k 权重和 ÷ 相关数"≈0.48（[社区文章](https://rawqing.github.io/2026/07/15/ragas-hands-on.html)）——**三种算法三个数**。
- 变体：`ContextPrecisionWithoutReference`（对 `response` 判有用，别名 `ContextUtilization`）、`NonLLMContextPrecisionWithReference`（需 `reference_contexts` + rapidfuzz）、`IDBasedContextPrecision`。

### B.5 context_recall

- 定义（[官方文档](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/)）：`reference 中被检索上下文支撑的断言数 / reference 断言总数`。**必须有 reference**。
- 实现（源码）：prompt 原文是 "analyze **each sentence** in the answer and classify if the sentence can be attributed to the given context"——**实际按句子拆，不是严格的 claim**；`retrieved_contexts` 同样 `"\n".join`。
- 注意：文档把它描述成 claims，代码是 sentences → **中文长句/分号句的分母行为与英文不同**，这是跨语言不可比的直接原因之一。

## C. 评判模型（judge）

- **接法**（[官方文档 customize_models](https://docs.ragas.io/en/stable/howtos/customizations/customize_models/)）：`llm_factory(model, client=AsyncOpenAI(...))`，走 **Instructor 做结构化输出**；非 OpenAI 原生 provider 走 **LiteLLM**（`provider="litellm"`，覆盖 Azure/Bedrock/Vertex/100+）。因此**任何 OpenAI 兼容端点都能接**。
- **DeepSeek 可接**（两条独立路径）：① `AsyncOpenAI(base_url="https://api.deepseek.com")` + `llm_factory("deepseek-chat", client=...)`（社区已验证此写法，[社区文章](https://rawqing.github.io/2026/07/15/ragas-hands-on.html)）；② LiteLLM 原生支持 `deepseek/deepseek-chat`（[LiteLLM 文档](https://docs.litellm.ai/docs/providers/deepseek)）。
- **temperature/JSON**：0.4 由 `llm_factory` 统一强制结构化输出（`instructor`），GPT-5/o 系列还会自动处理 temperature/top_p 约束；裁判侧仍建议显式 `temperature=0`（项目既有做法），并关闭 thinking（`deepseek-reasoner` 的 reasoning 会显著抬高延迟）。
- **校准（必做）**：项目已有预注册口径——`KAPPA_THRESHOLD = 0.70`，同时报 **Cohen κ 与 Krippendorff α（nominal，2 标注者）**，见 [claim_anchor_score.py](evaluation/gold/claim_anchor_score.py)（LEDGER §44）。建议把 RAGAS judge 的逐条 verdict 当作"标注者 B"，与人工 A 算 α；α<0.70 只作方向信号，不进结论。外部实践同向：多人标注才需要一致性指标，首选"单一领域专家 + 分歧裁决"（[Hamel FAQ：几个人标注](https://hamel.dev/blog/posts/evals-faq/how-many-people-should-annotate-my-llm-outputs.html)）。
- **单裁判 vs 双裁判**：RAGAS 本身不提供"多裁判投票"（旧的 `ensembler.from_discrete` 是对**同一裁判多次采样**投票，不是跨模型）。工程建议：**主裁判 1 个（deepseek，与生成同族需披露）+ 交叉裁判 1 个（qwen）只跑 20–30 条 spot-check 算 α**，不做全量双裁判（成本翻倍、收益递减）。
- **同族自评风险**：官方默认 gpt-4o-mini 裁判；若生成模型也是同一家族，分数系统性偏高（[社区文章 §4.1](https://rawqing.github.io/2026/07/15/ragas-hands-on.html)）。本项目生成与裁判都是 deepseek → **必须在报告里披露，并至少有 qwen 交叉证据**。

## D. embedding 与 reference

- **answer_relevancy 是唯一吃 embedding 的指标**，且它比的是"原问题 vs 反推问题"两个**短中文问句**的余弦相似度 → 对 embedding 的中文语义分辨力极敏感。
- 已知偏差：官方仓库有 issue **#1829 "Answer relevancy metric is worse in languages other than English"**（[issue 链接](https://github.com/explodinggradients/ragas/issues/1829)，本次仅取到标题，正文抓取失败）→ 非英语场景 answer_relevancy **不可直接与英文基准比**。
- 选型：`text-embedding-3-small` 是官方示例默认，**中文不建议直接沿用**；中文/多语首选 **BGE-M3**（`BAAI/bge-m3`，100+ 工作语言、支持 8192 token、dense+sparse+multi-vector，[论文 arXiv:2402.03216](https://arxiv.org/abs/2402.03216)），或阿里云 `text-embedding-v4`（[文档入口](https://www.alibabacloud.com/help/zh/model-studio/text-embedding-v4)，本次未取正文，仅列为备选）。本地 bge 可通过 `HuggingFaceEmbeddings(model=..., device="cuda")` 接（[迁移文档](https://docs.ragas.io/en/stable/howtos/migrations/migrate_from_v03_to_v04/)）。
- **换 embedding = 换仪器**：answer_relevancy 的绝对值随 embedding 变，报告必须写死模型名+维度。
- **reference 从哪来**（context_recall / context_precision-with-ref 的唯一硬需求）：
  1. **首选：项目金标 `expected_facts` 拼成一段陈述句 reference**（可追溯到 fact 编号，审稿可核）。注意 reference 的**句子数就是 recall 的分母** → 拼接时控制句式，别把 5 条事实写成 3 句或 8 句。
  2. **没有人工 reference 时**：用 `ContextPrecisionWithoutReference`（对 `response` 判有用）+ 放弃 context_recall（或改 `NonLLMContextRecall` 用 `reference_contexts`）。**不要**用 answer 当 reference 再算 recall——那是自证循环。
  3. **官方造数据路线**：`ragas.testset` 从知识图谱合成 (question, reference)（[官方文档 testset generation](https://docs.ragas.io/en/stable/concepts/test_data_generation/rag/)），但它生成的是**合成问题/reference**，与项目现有 100 题金标不是同一批样本，只能做补充不能替代。

## E. 样本量与统计

- **100 题是否够**：够做"系统级方向判断"，不够做"小数点后两位的比较"。分母视角更关键——本项目 mixed100 现有分母差异极大：`context_precision` 355 切片、`context_recall` 167 事实、`faithfulness` 593 断言、`answer_relevancy` 100 case（见 [packet summary](evaluation/results/eval100_scope_fixed_packet.json)）。同名"100 题"其实是四个不同精度的估计。
- **二项 95% CI 半宽**（p(1−p)/n 近似，本调研自算）：n=100,p=.97 → ±3.3pp；n=167,p=.91 → ±4.3pp；n=355,p=.72 → ±4.7pp；n=593,p=.89 → ±2.5pp。
- **但切片/断言嵌套在 case 内，不独立** → 上述区间偏乐观（有效 n < 名义 n）。**应报 case 级 cluster bootstrap**（项目已有 [paired_bootstrap.py](evaluation/analysis/paired_bootstrap.py) 可复用）；官方 packet 里已同时给 Wilson 与 Clopper-Pearson，属同一思路。
- **N=3 与方差**：项目已有实测——"同配置两次运行 faithfulness 极差可达 5pp"（[evidence_bind_paired.py](evaluation/analysis/evidence_bind_paired.py) 文档）。5pp 已超过多数实验臂的效应量 → **单次跑不能判优劣**；N=3 取均值 + 报极差是合理下限，且**同一裁判同一天跑完**（跨天 drift 会混入方差）。
- **分层抽样**：沿用现有 p0/cross30/new_meeting/mixed100 分层报，不合并成一个总分（与项目"逐指标报、不报加权总分"一致）。
- **表述边界**：RAGAS 分是"裁判+提示词+embedding+样本"四元组的函数，只能做**同仪器前后对比**，不能跨数据集/跨论文比较（同向证据：[Hamel FAQ 通用指标](https://hamel.dev/blog/posts/evals-faq/should-i-use-ready-to-use-evaluation-metrics.html)：通用指标会给"虚假的信心"）。

## F. 成本与延迟（本项目实测规模推算）

**调用数**（按 mixed100：100 case、355 切片、strictness=3）：`355 (precision) + 200 (faithfulness 2×100) + 100 (recall) + 300 (relevancy 3×100) = 955` 次 judge 调用；embedding `100 原问题 + 300 反推问题 = 400` 条文本。

**token 估算**（按会议纪要答案 500 字、切片 400 字、reference 200 字，中文≈1 token/字）：

| 项 | input | output |
|---|---|---|
| context_precision 355×(问题30+切片400+ref200+prompt400≈1.0k) | 355k | 21k |
| faithfulness 100×(800+2200) | 300k | 60k |
| context_recall 100×(2100) | 210k | 30k |
| answer_relevancy 300×(500) | 150k | 24k |
| **合计** | **≈1.02M** | **≈0.135M** |

**单价**（[LiteLLM DeepSeek 定价](https://docs.litellm.ai/docs/providers/deepseek)，USD/1M tokens，deepseek-flash）：峰值 $0.30 入 / $1.20 出，**低谷半价** $0.15/$0.60。
⇒ 峰值 ≈ `1.02×0.30 + 0.135×1.20 = $0.47`；低谷 ≈ $0.23。**N=3 全量 ≈ $0.7–1.4**。结论：**成本不是决策变量，限流和工程才是。**

**延迟/限流**：v2 指标内部是**串行 await**（[源码](https://github.com/vibrantlabsai/ragas/blob/master/src/ragas/metrics/collections/context_precision/metric.py)），必须自己在样本外层 `asyncio.gather` + `Semaphore`；建议并发 8–16（`max_workers=16` 是官方旧默认），配 `AsyncOpenAI(timeout=60, max_retries=5)`（[run_config 文档](https://docs.ragas.io/en/stable/howtos/customizations/run_config/)）；context_precision 的 355 次调用是尾部瓶颈。粗估 955 次 × 3s ÷ 12 并发 ≈ **4–5 分钟/次**。

## G. 中文场景的坑（逐条给处置）

1. **claim/句子拆分**：拆分由 judge 完成，prompt 是英文指令 + 英文 few-shot（`StatementGeneratorPrompt`、`ContextRecallClassificationPrompt`）。中文长句易被切成多条或漏切 → **分母不稳**。处置：跑前用 10 条样本对同一答案做 3 次拆分，看条数波动（>±30% 则改用固定中文拆句后自定义 prompt）。
2. **提示词语言**：官方提供 `metric.prompt.adapt(target_language="chinese", llm=...)`（0.4 新 API，[迁移文档](https://docs.ragas.io/en/stable/howtos/migrations/migrate_from_v03_to_v04/)）把 instruction+examples 译成中文；但**一旦 adapt 就是换仪器**，必须新开 label，且 adapt 后要重算 α。
3. **数字/日期归一**：NLI 判据是 "can be directly inferred"，`1月15日` vs `2024-01-15` vs `二〇二四年一月十五日`、`216万` vs `2,160,000` 都可能被判不支持。处置：在送 judge 前对**上下文与答案同时**做数字/日期归一化（同一函数处理两侧，避免制造差异），并在报告里披露。
4. **繁体/全角标点**：`（）`、`，`、`。` 与半角混排不影响语义、对 embedding 影响小，主要影响**人工核对**与**字符串类指标**（`NonLLM*` 需先归一）。
5. **embedding 中文效果**：见 §D，answer_relevancy 在中文上系统性偏低/噪声大（issue #1829）。
6. **judge 语言偏好**：中文提问 + 英文 prompt 时，judge 可能对"中文里夹英文术语"更严格；**同一次重测里 judge prompt 语言必须唯一**，不能一半中文一半英文。
7. **会议纪要特有问题**：答案里大量"以上信息来自…""该会议 meeting_id=2"这类**元陈述**，RAGAS 的 statement generator 会照样拆成断言并判不支持 → faithfulness 被系统性拉低。项目已有 `faithfulness_content`（剔元陈述）口径是对的方向；**RAGAS 官方口径下没有这个开关**，只能靠自定义 prompt（同样算换仪器）。

## H. 社区批评与 2026 年的替代/补充

- **通用指标批评（最有力的一条）**：现成指标（含 RAGAS 四件套）当"质量度量"用会制造**虚假信心**，更适合当"找 trace 的探索信号"；应先用 error analysis 定义二元失败模式，再做**自定义 evaluator 并用人工标签验证**（[Hamel FAQ](https://hamel.dev/blog/posts/evals-faq/should-i-use-ready-to-use-evaluation-metrics.html)，2025-07 发布 / 2026-09 修订）。
- **answer_relevancy 的 embedding 偏差**：非英语更差（[issue #1829](https://github.com/explodinggradients/ragas/issues/1829)）；且分数可能越界（官方文档自认）。
- **faithfulness 依赖 judge 拆分**：断言数是分母，judge 换版本/换语言即变；社区实测"同配置两次运行差 5pp"（项目内证据）与"RAGAS 与人工相关性约 0.55"的说法并存（[中文实践](https://rawqing.github.io/2026/07/15/ragas-hands-on.html)，**该数字为社区转述，未见原始出处，不可引用为结论**）。
- **context_recall 必须有 reference**：无金标即不可算（官方文档明确），这是"reference-free 框架"名不副实之处——原论文定位是 reference-free（[arXiv:2309.15217](https://arxiv.org/abs/2309.15217)），但 context_recall 一路都需要参考。
- **不可跨数据集比较**：分母定义随数据变（切片数/事实数/断言数），绝对值无外部含义。
- **替代/补充框架（简表）**：

| 框架 | 定位 | 与 RAGAS 的差异 | 来源 |
|---|---|---|---|
| **RAGChecker**（Amazon） | 细粒度诊断，拆 retrieval/generation 两组指标 | 论文称 meta-eval 与人工判断相关性**显著更好**；需要 reference，指标更多更细 | [arXiv:2408.08067](https://arxiv.org/abs/2408.08067) |
| **TruLens** | RAG Triad：Context Relevance / Groundedness / Answer Relevance | 三支柱、无需 reference，偏"可观测+反馈函数"而非固定分数 | [TruLens RAG Triad](https://www.trulens.org/getting_started/core_concepts/rag_triad/) |
| **DeepEval / Arize Phoenix** | pytest 风格单测 / trace 级可观测 | 偏 CI 门禁与线上监控；指标可自定义 | 本次未逐页核对，仅列为候选 |
| **人工 + 自定义 judge** | error analysis → 二元失败模式 → 校准 | 与 Hamel/项目宪法同向，成本最高但最可信 | [Hamel FAQ](https://hamel.dev/blog/posts/evals-faq/) |

> 判断：2026 年没有出现"取代 RAGAS"的统一标准；趋势是**从"四个通用分"转向"领域自定义 evaluator + 人工校准 + trace 级诊断"**。RAGAS 的价值主要在**有一套可复现的默认口径**，而不是"分数权威"。

## 对本项目的直接建议

1. **跑官方库，但只作为"第二台仪器"，并行报、不相减。** 新开仪器标签（如 `r1`），与 `a/b/c/d/e/g` 并列；任何数字必须带标签。理由：三处硬口径（AP 排序权重、分母=有用切片数、断言由 judge 重拆）无法用自研对齐，硬对齐等于自欺。
2. **先把现有 packet 转成官方输入，再决定要不要重跑 RAG。** 现有 [eval100_scope_fixed_packet.json](evaluation/results/eval100_scope_fixed_packet.json) 已含 `user_input/response/retrieved_contexts/expected_facts`，可**离线复算**（不重新检索、不重新生成）；这样"换口径"与"换系统"两个变量才不混淆。
3. **reference 用 `expected_facts` 拼陈述句，别用 answer。** 控制句子数（分母）；无金标/负样 case 报 `null` 不进分母——沿用项目"判不了不计为通过"的宪法第 3 条。
4. **judge：deepseek-chat 主判（temp=0，`llm_factory` + AsyncOpenAI base_url）+ qwen 交叉 20–30 条算 α。** 生成与裁判同族必须披露；α<0.70 时 RAGAS 分数只作方向信号。
5. **answer_relevancy 单独标注"中文 embedding 版"**：用 bge-m3 或 text-embedding-v4，写死模型名；它与现有"是否正面回答"的 99.00 完全不是一回事，**预期会明显下降**，这是口径差异不是系统退步。
6. **是否值得全量重跑：值得，但只跑 2 次（N=2 估方差），不要 3 次。** 单次 <$0.5、<5 分钟；先用 20 case 打通管线并核对 NaN/0.0 边界（全判 0 的 case 官方给 0.0，不是 NaN），再全量。
7. **报告口径**：四指标各自分母写清（chunk/fact/claim/case），CI 用 case 级 cluster bootstrap；**禁止**把四个数加权成总分，**禁止**与旧口号"71.83/90.02/88.34/99.00"直接比大小。

**最大坑（一句话）**：官方 `context_precision` 是**排序加权 AP 且分母是"被判有用的切片数"**，不是"有用切片/切片总数"——项目现有 71.83 与官方值即使同一批判定也**必然不同**，且"有用切片排在后面"会被额外惩罚；把它当"新版同一个指标"写进对比表，就是拿两台仪器相减。
