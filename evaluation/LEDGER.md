# 评测账本（LEDGER）

两个职能：**存活结论登记**（哪些数字可引用、口径与证据在哪）与**运行账本**
（每次真实运行登记一行）。旧账本（RUN_INDEX 十七节，含全部撤回记录）在
git 历史（重构前最后一个提交）中，本文只保留**仍存活**的结论与撤回摘要。

引用规则：任何数字必须连同其口径列一起引用；单裁判读数必须带「方向信号」
限定；会议级绝对数必须连配置（thinking=OFF）一起报。

### 轴5 口径修正的仪器复核（label c，2026-10-16）

**目的**：口径修正是**改仪器**（判定提示词要求把出处说明标成 `meta`），必须用新标签
在**同一批首测答案**上重判，才能把"仪器变化"与"产品变化"分开。判定族 qwen、
`--thinking off`（与 label b 的形态一致），56 次调用（27 个 case × 2 半 + 1 次重试）。

| 指标 | 值 | 与首测的关系 |
|---|---|---|
| context precision | 71.3%（77/108） | **不可与首测 85.3% 相减**（首测走供应商默认思考，本行关思考——见首测一节末尾的仪器复核） |
| context recall | **91.9%（57/62）** | 与 A/B 逐条一致：三个标签都是 57/62，同一批 5 条事实没找到 |
| faithfulness（全部断言口径） | 86.0%（166/193） | 与 A 83.6% / B 88.0% 同量级（断言切分粒度不同，不逐条比） |
| **faithfulness_content（内容级，可引用口径）** | **98.75%（158/160）** | 与首测手工分类的 97.6%（A）/98.6%（B）**吻合**——这是本行要验证的事 |
| answer relevancy | 92.3%（24/26） | 与 A/B 的 25/27 一致；2 个 case 的答案半判定被形状校验拦下（见下） |
| 被判为出处的元陈述 | 33 条 | 全是"以上信息均来自…（meeting_id=2）"这类**纯出处句** |
| 内容级里的不支撑断言 | **2 条** | q10（含归属的复述句）、q20（"不允许在构建过程中穿插增量更新"，首测人工分类里就有它） |

**读法**：修复前"81 条不支撑里 67 条是出处说明"这个诊断被新仪器证实——现在不支撑的
只剩下真实的内容级问题。**这条复核把 P0-3 从"提示词改了一句"变成"仪器换过之后数字站得住"**。

**两次仪器自身缺陷（都在首轮 label c 暴露并已修，首轮判定已作废清除）**：

1. **提示词里的引号把模型带进 JSON 陷阱**：首版例子用 ASCII 引号包整句，模型照抄这个
   风格，遇到答案里本来就带引号的句子就**停住并补闭合括号**——返回的 JSON 可解析但内容
   从那里截断（27 个 case 里 21 个如此，断言数 495 → 125）。修法：例子改成不带引号的
   条目式列举。这条值得记住：**给判定者的例子会连同"排版习惯"一起被模仿**。
2. **"合法的 JSON"被当成"完整的判定"**：截断响应里最后一条断言没有 `supported`、
   `answered` 整字段消失，而汇总只是跳过没标记的条目——**分母静默变小**，报告上看不出
   异常。修法：形状校验（不合格记 `*_error`、不进分母、下次运行补判）+ 失败的那一半
   重试一次并附 re-ask 说明（instructor 式）+ **重试同样走过硬预算闸**。

- **口径不适用 36 条**：纪要条目是人确认过的结构化摘要，不是逐字引用，

- 判不了的引用（缺对照物/空引文）：0 条（单独计数，不算通过）
- 答案引用检索未返回过的编号（编编号）：0 条

**对照物是转写表的原始片段**（`/transcription/selectById`），不是检索结果本身——
引文本来就是从检索结果拷的，用它自查等于自己跟自己比。判据是产品契约层的
`evidence_locatable`（与纪要证据同一份定义）。这批数据覆盖了
切块 → 入库 → 检索 → 登记 → 答案这条完整链路，**但 n=27 轮、单一会议，
"100%" 只说明这条链路上没有系统性断裂，不能外推成"引用永远正确"**。

### 本轮真实运行暴露的产品缺陷（2026-10-16）

### 预注册：问答引用的两条零调用不变量（2026-10-16，先于任何抓取写死）

**假设**：产品落库的问答记录里，(a) 答案引用到的每一条引文都能在**它指向的内容**里
逐字定位；(b) 引用所属会议都在提问者当时的可见范围内（管理员不设限）。

**唯一主指标**：两条各自的比例（locatable / authorized），**不合成总分**。

**判定阈值**：两条都必须为 **100%**。(a) 是结构性不变量：引用是宿主按检索结果分配的
编号、引文取自该条内容本身，出现不可定位说明落库或渲染环节改动了引文；
(b) 是权限不变量：任何一条越权引用都是缺陷，没有"可接受的越权率"。

**样本量与功效**：样本 = 一次授权抓取的全部问答轮次（`judges/rag.py --ask`）。
功效说明：阈值是 100%，因此任何样本量下"发现一条违约"即可判定失败；
反过来，小样本通过**不能**证明不存在越权（只能说明这次没抓到）——这一限制如实写在
产出里（`chat_checks.summarize` 的 reading 与本节）。

**何为失败**：(a) 出现任一条不可定位引用；(b) 出现任一条越权引用；(c) 出现
`unknown_refs` 非零（答案引用了检索从未返回过的编号，说明模型在编编号）。
"判不了"（引用没带 source_text）不计为通过，单独计数。

**结果**：**已执行**（2026-10-16）。27 轮问答、107 条被引引用：两条不变量都是
**100%**（可定位 71/71，CI 94.9–100%；未越权 107/107，CI 96.6–100%），
编编号 0 条。36 条纪要条目引用判为"口径不适用"（不是逐字引用），
**这 36 条当前没有覆盖**——是缺口而不是通过。
**判定失败的路径没有出现**：样本量（27 轮、单一会议）不足以证明不存在越权或不可定位，
只能说这条链路上没有系统性断裂——这一限制写在 §一 轴5 的读数旁边。

### 行业对齐改造：检索基础、路由与查询分解（2026-10-17）

依据逐条列在 `docs/检索与路由：行业对齐.md`（Qdrant 索引/过滤、Azure RAG 检索阶段、
Anthropic 路由模式三份**已核对原文**；rerank 基准那几条是检索得到的二手归纳，标注了
"需核对"）。这一节只登记**改了什么、量到什么、以及这些读数不能被读成什么**。

**四处改动**：

1. **payload 索引**（5 个过滤字段）+ 把"索引就绪"上移到每条索引路径都过。
   真跑验证：容器内 `payload_schema` 五字段齐备；`source_ids` 过滤实跑
   （全部→来源 {6,7}；只 6→{6}；只 7→{7}）。**顺带修掉一个真缺陷**：
   索引原先只在"要重嵌"的路径上建，而内容未变化的库会在它之前返回——
   最常见的部署形态**永远建不出索引，且不报错**（与官方文档点名的
   "unindexed filtering 只是慢"同形）。
2. **来源身份**：`source_id` 进检索结果 / 引用快照 / 工具参数（`source_ids` 过滤），
   跨录音问题（`also_in`）的检索指标从"判不了"变成可评。
3. **路由鲁棒性**：判定流程（有序）取代平铺定义；`confidence` 与 `sub_questions`
   写进 schema 的 `required`（不写进 required，模型就真的不给——实测 100 题里
   confidence 一条都没有）；**弃权**：置信度 < 0.6 时丢掉工具建议、强制检索。
4. **分类法合并**（这是本节的争议点，理由写死在这里）：删掉 `procedure`。
   它与 `single_fact` 的**路由动作完全相同**（都走检索），而两版提示词下它的 F1 从
   53% 摆到 12%——**这条边界不可稳定测量，只产出标签噪声**。迁移是机械规则
   （问题里出现「哪些/哪几项/哪几类/分别/几个」→ aggregation，其余 → single_fact，
   13 + 2 条逐条标了 `intent_revision`），四类各自对应一个不同动作：
   smalltalk→不检索；cross_meeting→必须分别检索多来源；aggregation→先列清单再检索；
   single_fact→检索。

**意图 F1（同一批 100 题、同一套**四类**金标；v1–v3 的模型输出按新金标重算）**：

子问题自包含。

**四条限制（防止把上表读成"提示词 A/B 的因果结论"）**：

1. **这是开发读数**：我一边看中间读数一边改提示词与分类法，没有预注册、没有冻结中间版本
