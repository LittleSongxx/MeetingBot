# 评测账本（LEDGER）

两个职能：**存活结论登记**（哪些数字可引用、口径与证据在哪）与**运行账本**
（每次真实运行登记一行）。旧账本（RUN_INDEX 十七节，含全部撤回记录）在
git 历史（重构前最后一个提交）中，本文只保留**仍存活**的结论与撤回摘要。

引用规则：任何数字必须连同其口径列一起引用；单裁判读数必须带「方向信号」
限定；会议级绝对数必须连配置（thinking=OFF）一起报。

### 轴5 口径修正的仪器复核（label c，2026-10-16）

**目的**：口径修正是**改仪器**（判定提示词要求把出处说明标成 `meta`），必须用新标签
在**同一批首测答案**上重判，才能把"仪器变化"与"产品变化"分开。判定族 qwen、
`--thinking off`（与 label b 的形态一致），56 次调用（27 个 case × 2 半 + 1 次重试）。

| 指标 | 值 | 与首测的关系 |
|---|---|---|
| context precision | 71.3%（77/108） | **不可与首测 85.3% 相减**（首测走供应商默认思考，本行关思考——见首测一节末尾的仪器复核） |
| context recall | **91.9%（57/62）** | 与 A/B 逐条一致：三个标签都是 57/62，同一批 5 条事实没找到 |
| faithfulness（全部断言口径） | 86.0%（166/193） | 与 A 83.6% / B 88.0% 同量级（断言切分粒度不同，不逐条比） |
| **faithfulness_content（内容级，可引用口径）** | **98.75%（158/160）** | 与首测手工分类的 97.6%（A）/98.6%（B）**吻合**——这是本行要验证的事 |
| answer relevancy | 92.3%（24/26） | 与 A/B 的 25/27 一致；2 个 case 的答案半判定被形状校验拦下（见下） |
| 被判为出处的元陈述 | 33 条 | 全是"以上信息均来自…（meeting_id=2）"这类**纯出处句** |
| 内容级里的不支撑断言 | **2 条** | q10（含归属的复述句）、q20（"不允许在构建过程中穿插增量更新"，首测人工分类里就有它） |

**读法**：修复前"81 条不支撑里 67 条是出处说明"这个诊断被新仪器证实——现在不支撑的
只剩下真实的内容级问题。**这条复核把 P0-3 从"提示词改了一句"变成"仪器换过之后数字站得住"**。

**两次仪器自身缺陷（都在首轮 label c 暴露并已修，首轮判定已作废清除）**：

1. **提示词里的引号把模型带进 JSON 陷阱**：首版例子用 ASCII 引号包整句，模型照抄这个
   风格，遇到答案里本来就带引号的句子就**停住并补闭合括号**——返回的 JSON 可解析但内容
   从那里截断（27 个 case 里 21 个如此，断言数 495 → 125）。修法：例子改成不带引号的
   条目式列举。这条值得记住：**给判定者的例子会连同"排版习惯"一起被模仿**。
2. **"合法的 JSON"被当成"完整的判定"**：截断响应里最后一条断言没有 `supported`、
   `answered` 整字段消失，而汇总只是跳过没标记的条目——**分母静默变小**，报告上看不出
   异常。修法：形状校验（不合格记 `*_error`、不进分母、下次运行补判）+ 失败的那一半
   重试一次并附 re-ask 说明（instructor 式）+ **重试同样走过硬预算闸**。

- **口径不适用 36 条**：纪要条目是人确认过的结构化摘要，不是逐字引用，

- 判不了的引用（缺对照物/空引文）：0 条（单独计数，不算通过）
- 答案引用检索未返回过的编号（编编号）：0 条

**对照物是转写表的原始片段**（`/transcription/selectById`），不是检索结果本身——
引文本来就是从检索结果拷的，用它自查等于自己跟自己比。判据是产品契约层的
`evidence_locatable`（与纪要证据同一份定义）。这批数据覆盖了
切块 → 入库 → 检索 → 登记 → 答案这条完整链路，**但 n=27 轮、单一会议，
"100%" 只说明这条链路上没有系统性断裂，不能外推成"引用永远正确"**。

### 本轮真实运行暴露的产品缺陷（2026-10-16）

### 预注册：问答引用的两条零调用不变量（2026-10-16，先于任何抓取写死）

**假设**：产品落库的问答记录里，(a) 答案引用到的每一条引文都能在**它指向的内容**里
逐字定位；(b) 引用所属会议都在提问者当时的可见范围内（管理员不设限）。

**唯一主指标**：两条各自的比例（locatable / authorized），**不合成总分**。

**判定阈值**：两条都必须为 **100%**。(a) 是结构性不变量：引用是宿主按检索结果分配的
编号、引文取自该条内容本身，出现不可定位说明落库或渲染环节改动了引文；
(b) 是权限不变量：任何一条越权引用都是缺陷，没有"可接受的越权率"。

**样本量与功效**：样本 = 一次授权抓取的全部问答轮次（`judges/rag.py --ask`）。
功效说明：阈值是 100%，因此任何样本量下"发现一条违约"即可判定失败；
反过来，小样本通过**不能**证明不存在越权（只能说明这次没抓到）——这一限制如实写在
产出里（`chat_checks.summarize` 的 reading 与本节）。

**何为失败**：(a) 出现任一条不可定位引用；(b) 出现任一条越权引用；(c) 出现
`unknown_refs` 非零（答案引用了检索从未返回过的编号，说明模型在编编号）。
"判不了"（引用没带 source_text）不计为通过，单独计数。

**结果**：**已执行**（2026-10-16）。27 轮问答、107 条被引引用：两条不变量都是
**100%**（可定位 71/71，CI 94.9–100%；未越权 107/107，CI 96.6–100%），
编编号 0 条。36 条纪要条目引用判为"口径不适用"（不是逐字引用），
**这 36 条当前没有覆盖**——是缺口而不是通过。
**判定失败的路径没有出现**：样本量（27 轮、单一会议）不足以证明不存在越权或不可定位，
只能说这条链路上没有系统性断裂——这一限制写在 §一 轴5 的读数旁边。

**四处改动**：

1. **payload 索引**（5 个过滤字段）+ 把"索引就绪"上移到每条索引路径都过。

### 预注册：查询规划两臂（开/关），零调用尺子（2026-10-17，先于任何调用写死）

**背景**：查询规划（`KB_QUERY_PLAN_ENABLED`）已实现、默认关、效果未量。这一轮补上测量，
但**不回退用户此前"不做三臂 A/B"的成本决定**：只跑两臂（关 / 开），**不跑判定**

**假设**：规划（相对时间/指代改写 + 意图与建议工具 + 并列多问句分解）会让检索更对路，

它是"检索有没有把该给的东西给到"的直接读数，且不随判定模型/思考开关漂移
（这条口径在 P0/P1 复测里已经踩实）。

**判定阈值**：
1. 主指标：recall@k（开）**≥** recall@k（关）。持平或上升才算"不劣"；下降则如实登记为"有代价"。
2. 行为端点（任一不达标即判该臂不可用）：**轮级失败 = 0**；**首轮工具调用率 = 27/27**；
   引用可定位/未越权维持 100%。
3. 副读数只登记不判：MRR / nDCG@k、每轮 token、规划调用次数与延迟、

**样本量与功效**：同 27 组问题、同一批索引、同一份代码（两臂只差一个开关）。
n=27 对"轮级失败/工具调用率"这类结构性端点足够；对 3–5pp 的 recall 变化**检不出**，
因此第 1 条只作"不劣"的门，不宣称提升。

**何为失败**：(a) 规划臂出现轮级失败或首轮不检索；(b) 引用两条不变量出现违约；
(c) 规划调用把某一轮问答变成错误（增强不该有能力弄挂主链路）。

**结果**：**主指标通过**（recall@k 0.846 → **0.897**）；行为端点里"轮级失败"通过，

### q26 的根因查清了（三条行动项为什么还是缺）

逐环节看臂 P 的 q26：

1. 规划对"下午这场会"**低置信（0.4）**——按设计丢掉了工具建议、并要求按检索处理；
2. 模型自己 `list_facts(kind=recording)` 看录音清单，然后**猜了一个来源限定**
   `search_knowledge(source_ids=[6])`：而这场会的两段录音在元数据里的时间戳都是
   上午（10:29 / 10:30），**"下午"在元数据层面根本判不出来**；
3. 于是检索集一条都不覆盖金标片段（金标三条行动项在 task 7 的转写里），
   答案如实说"不存在'下午这场会'的区分"——**在元数据层面这是实话**。

**修法（已实现、有单测、效果未验证）**：把"猜出来的限定空了就自动放宽"从**只覆盖时间**
扩到**时间 + 来源**（会议范围/权威级/切片类型不放宽——那是用户或权限给的明确条件），
提示里同时写明"低置信度时不要用日期或来源缩小范围"。
这是同一条原则的延伸而不是补丁：**模型看不到语料布局，凡它自己生成的限定都要 fail-open**。

### 本轮抓到的第二个真缺陷：失败被换成"没检索"（已修 + 有测试）

臂 P 那 1 例"首轮没检索"的真相：模型的最后一次调用**挂住 122 秒后失败**
（`No streaming chunk received for 120.0s`），图抛异常 → `final_state` 是空的 →
`tool_calls` 读出来是 0 → 旧代码据此判定"这一轮没有检索知识库"，
**把真实原因（模型调用失败）覆盖掉了**。

这条恰好落在本仓反复强调的那句上：**失败被记成另一个原因，会污染失败率与归因**——
排查的人会照着"为什么没检索"查，而真因在流式超时。修法两条：
只有**图正常跑完**（拿到 LangGraph 的 output）且**还没有失败原因**时，才做"没检索"的推断。

### 复合边界规则的结果：**没起作用**（如实登记）

按"动作更稀缺的那一类"归类（跨来源 > 枚举 > 单点）之后，四类 F1：
single_fact 88%（94%→88%）、aggregation 79%（85%→79%）、cross_meeting 77%（持平）、
smalltalk 100%，**宏平均 88.9% → 86.2%**——n=100 下这个差检不出，方向上还略降。

**诊断（比数字重要）**：cross_meeting 那 3 条误判**不能从问题本身判定**——
"答案落在哪段录音"是**语料布局**信息，模型看不到（q88 只问"发布公告与对外通稿分别由谁负责"，
不知道这两件事分别记在两段录音里）。所以这个类的召回有结构性上限，继续调提示词是白费。

**处置**：保留规则（它编码"动作优先"这条原则、代价为零），但**不宣称提升**；
`cross_meeting` 在报告里**降级为诊断维度**——路由动作上与 aggregation 相同
（都建议多次检索 + 列表式回答），多来源由分解提示与 `source_ids` 在检索侧处理。

### 标准化 RAG 链路与评测口径（2026-10-17）

**背景**：按"不做学术式消融、只做标准化 + 公开标准评测"的口径重铺一次链路。
参数与依据见 `docs/RAG链路参数.md`；这一节只登记**改了什么、量到什么、以及三个真缺陷**。

**链路现状**（全部参数可配）：500 字窗口 / 2 行重叠（`KB_CHUNK_TARGET_CHARS`）→
稠密 `qwen3.7-text-embedding`（1024 维）+ 稀疏字符 bigram × **Qdrant 服务端 IDF**（BM25 词法口径）
→ RRF 混合（prefetch 24）→ **`qwen3.7-text-rerank` 专用重排** → 截断 **top-5**（`RERANK_TOP_K`）。
配置写进 `.env`：百炼专属端点的**对话模型未开通**（403 `AccessDenied.Unpurchased`，实测），
因此对话走公网 compatible；嵌入与 rerank 走专属端点（实测可用）。

**评测口径修正（会让旧数字不可比）**：`context_precision` 的 contexts 原先取**答案实际引用的
切片**，而 RAGAS 的定义是**检索到的全部切片**。已改成后者（判定包逐 case 记 `context_source`，
老产物缺检索集时退回引用集并标注）。因此本节的 precision 与历史各节的 precision **不可比**。

**27 条人工标注题、两族判定（关思考）**：

| 配置 | context_precision | context_recall | faithfulness 内容级 | answer relevancy | recall@k / MRR / nDCG |
|---|---|---|---|---|---|
| k=8（漏斗未截断） | 33.5% | 93.5% | 100% | 100% | 0.919 / 0.827 / 0.854 |
| **k=5（当前配置）** | **51.5%**（qwen）/ **53.0%**（deepseek） | **95.2% / 95.2%** | **97.0% / 94.5%** | **96.3% / 96.3%** | **0.956 / 0.846 / 0.879** |
| k=8 + 300 字窗口 | 37.3% | 91.9% | 99.3% | 100% | 0.889 / 0.796 / 0.799 |

**rerank 的质量/成本平衡（用户要求的唯一一项消融）**：`qwen3.7-text-rerank` 每次检索一次调用，
24 候选，实测 **平均 476ms、最大 2.35s、约 5.4k token/次**（27 问共 27 次调用、144,660 token）。
收益是**排序**：MRR 0.585→0.827、nDCG 0.689→0.854（同批答案、同批候选）；
代价是 top-8 时 recall@k 0.956→0.919（重排把部分"含金标片段但答不了问题"的窗口挤出前 8）；
改成 **k=5** 后 precision 33.5%→51.5%、recall 反而回到 95.2%——**漏斗截断比单纯加重排更重要**。
价格未配置（`ai_call_log.cost_micro=0`，按"未定价"如实显示）。

**金标可信度（零调用）**：新增 `gold/verify_gold.py` 机械核对——每条标准事实的数字必须全部
出现在它标注的片段里、字符 bigram 覆盖 ≥ 0.5。首轮 91/95 通过，未通过的 4 条**都是金标自己的
问题**（1 条片段号漏标、2 条改写过度、1 条 MySQL/my sql 大小写），修后 **95/95 通过**。
它证明"片段里说了这件事"，**不证明"这条问题值得问"**——人工标注仍是缺口。

**本轮抓到的三个真缺陷（都已修 + 有测试）**：

1. **`httpx.AsyncClient(max_retries=0)` 不存在这个参数**（那是 openai SDK 的）——
   重排客户端在真调用时直接 TypeError，而"失败退回原顺序"让它看起来像"重排没效果"。
   这类参数名错误本地打桩测不出来（桩不构造真 client）。
2. **内容指纹不含"嵌入模型与 collection"**：换模型/换库之后，MINUTES 来源被判
   "内容未变化，跳过重建"——新库里根本没有它的 23 条向量，**检索静默少一整个来源**。
   修法：指纹并入 `模型名:维度@collection`（与 payload 结构版本同一条理由）。
3. **`context_precision` 的分母与 RAGAS 不一致**（见上）。

**限制**：27 题 n 小，所有读数只作方向信号；300 字窗口那一行只用于参数校准，不构成"块大小"的
因果结论；faithfulness 两族差 2.5pp 是断言切分粒度差异（历史已知），不逐条比。

### 预注册：窗口大小 × 截断 k 的联合标定（任务 1，2026-10-17，先于任何调用写死）

**背景（已有证据，不重复测）**：同一批 27 题、同一份索引，500 字窗口下 k=8 → k=5 让
`context_precision` 从 33.5% 升到 51.5%（qwen）/53.0%（deepseek），`context_recall` 保持 95.2%；
300 字窗口只在 k=8 下测过（precision 37.3%、recall 91.9%）。**300×5、300×3、500×3 都没测过。**
这一轮不叫消融：目的是给生产配置选一个可解释的参数组合，四个臂各自与同一份金标对表。

**四个臂**（同一份代码、同一批索引、同一会话流程；每臂独立新会话）：

| 臂 | `KB_CHUNK_TARGET_CHARS` | `RERANK_TOP_K` | 是否重建索引 |
|---|---:|---:|---|
| A | 500 | 5 | 内容未变时自动跳过 |
| B | 500 | 3 | 不重建（块未变） |
| C | 300 | 5 | **重建**（正文变 → 指纹变 → 重嵌） |
| D | 300 | 3 | 不重建（块未变） |

**假设**：precision 是"窗口大小 × 截断 k"的函数——窗口越小、k 越小，单条上下文越可能
直接回答问题；代价是 recall 可能被截断伤到。预期 A 的 precision 与 53.0% 同量级，
B/D 的 precision 更高但 recall 可能下降，C 落在中间。**不预先指定赢家。**

**唯一主指标**：`context_precision`（RAGAS 口径：contexts = 该轮**检索到的全部切片**，
不是答案引用的那些）。判定族 **DeepSeek（deepseek-flash、thinking=off）**，新标签 **`f`**：
`f` 与 `d/e` 用同一份判定提示词，只表示"本轮标定家族"，不与历史标签混用。

**判定规则（先写死，按顺序执行）**：

1. **非劣门槛（硬门）**：每个臂必须同时满足
   - 判定式 `context_recall` **≥ 91.9%**（沿用 P0/P1 预注册的"不得退步"门）；
   - 零调用 `recall@k` **≥ 0.919**（重排开、未截断时的基线；低于它视为实质性召回损失）。
2. **成功阈值（主指标）**：赢家 `context_precision` **≥ 60.0%**。这是任务目标里的
   合格线；只在赢家上判，不给未选中的臂判"失败"。
3. **赢家选择**：在通过硬门的臂里取 `context_precision` 最高者。若前两名相差
   **< 2.0pp**（n=27 下 3 条事实≈4.8pp，2pp 远在噪声内），改取 `context_recall` 更高者；
   若仍相差 < 1.0pp，取 **k 更小者**（上下文更省、延迟更低）；k 相同则保留 500 字
   （不额外付重建与重嵌的代价）。
4. **描述性对照（只登记不判）**：`faithfulness_content`、`answer_relevancy`、
   MRR / nDCG、每轮 token、每轮检索条数（context_precision 的分母）、q26 三条金标是否命中。

**样本量与功效**：27 条人工题、62 条金标事实；四臂共 ≈108 轮问答。n=27 下
**3 条事实≈4.8pp**，任何 <4.8pp 的臂间差只作方向信号，不作因果结论；四臂各报
点估计与 Clopper–Pearson 95% 区间，**不合成加权总分**（宪法第 6 条）。

**何为失败（任一即判该臂无效，先修仪器/链路再谈数字）**：
(a) 轮级失败 > 0 或首轮工具调用 <27/27；(b) 引用可定位/未越权 <100%；
(c) 索引重建失败，或产物的 `captured_from.product_switches` 无法自证
`kb_chunk_target_chars` / `rerank_top_k`（无法证明这一臂跑的是什么配置）；
(d) 判定失败（形状校验/调用错误）>20%；(e) 零调用指标算不出来（缺 `retrieved`
或片段时间映射）。

**预算与产物**：每臂约 250k 产品 token、≈54–70 次判定调用；四臂合计约 1M 产品 token、
≤280 次判定调用（`--authorized-llm-calls 70`/臂）。产物：
`results/chat_answers_cal_{500x5,500x3,300x5,300x3}.json`、
`results/rag_packet_cal_*.json`（标签 f）、`results/retrieval_cal_*.json`。
**若某臂的产物缺自报字段，该臂作废并重跑，不用旧产物替代。**

**不能说的**：四臂之间的差异不是"块大小"或"k"的因果效应（整链重跑、模型自选检索词
会变）；300 字臂还同时改变了切片数与 RRF 候选的构成。本表只回答"哪个配置在本语料、
本模型、这 27 题上值得作为下一轮的起点"。

### 预注册与结果：同一轮内的重叠窗口去重（任务 2，2026-10-17，零调用反事实）

**背景**：27 题里有 7 轮（500×5）/10 轮（300×3）检索到同一段录音内时间窗重叠
>30 秒的切片；切块本身有 2 行重叠，重排又可能同时选中相邻窗口。

**假设**：这些窗口是"同一段话交了两遍"，去掉排序更低的一条应让
`context_precision` 的分母变小、precision 上升，而 recall 不受影响。

**规则（先写死，再算）**：同一 `source_id`、重叠 ≥ `KB_DEDUPE_OVERLAP_SECONDS`（30 秒）
**且**重叠占较短窗口 ≥ `KB_DEDUPE_OVERLAP_RATIO`（25%）判为重复；保留排序更靠前的一条
（重排分数更高）。只处理带时间轴的转写窗口；纪要条目与缺来源身份的切片不参与。

**验证方式（零调用，不花判定调用）**：在 D 臂（300×3）已判定的 84 条上下文上做反事实——
用判定者逐条的 `useful` 标签，重算去掉重复后的 precision 与检索侧指标。这是对
**同一批检索集**的确定性反事实，不是对模型后续行为的模拟（局限见下）。

**结果：假设被证伪，机制默认关。**
- 删掉 **10 条上下文，10 条全部被判"有用"**，0 条无用；分母 84→74。
- `context_precision` **81.0% → 78.4%（−2.6pp）**；`recall@k` **94.4% 不变**；
  MRR 0.870 不变；nDCG 0.886 → 0.888。
- 原因：相邻窗口共享一段话，但各自还带着只有自己才有的内容——它们不是重复噪声，
  而是"各含答案的有用上下文"。RAGAS 的 context_precision 不会因重复的有用上下文扣分，
  却会因为少了一条有用上下文而扣分。

**处置**：机制保留（`KB_DEDUPE_ENABLED`，默认 0；阈值可配），**不设为默认**。
只有"重叠比例接近 1"的切法（例如父子块里的小块重合）才值得打开。
**限制**：反事实没有跑真臂——模型看到更少的上下文后，检索词与答案可能变化；
本结论只支持"在本语料、本检索集上，去重不改善 precision"，不支持"去重永远无效"。
若将来有人开这个开关，须按同一预注册重跑一次 27 题。

### 预注册：Contextual Retrieval 的收益（任务 3，2026-10-17，先于重建与调用写死）

**背景**：当前标准配置 300×3 的 context_precision 是 81.0%（68/84）。
行业做法（Anthropic Contextual Retrieval）在索引时给每块加一句"这段在会里的位置/主题"
再嵌入，让小块在语义上自描述；本项目此前没做，理由是 61 个切片、收益未知。

**假设**：加入 LLM 生成的上下文句后，检索排序更准（尤其问题措辞与窗口原文不一致时），
`context_precision` 不下降、`context_recall` 不下降；代价是索引时每块一次模型调用。

**做法**：`embed_text = [会议/日期/录音/时间/说话人规则头] + [上下文] 一句 LLM 生成的
主题 + 原文`；只用于嵌入与稀疏编码，**引用回显仍用 `text`**（否则引用在转写里定位不到）。
上下文句存 `kb_chunk.embed_text`（重试复用，不重复付费）；生成失败退回规则头，索引不挂。
新 call_type `KB_CONTEXTUALIZE` 已登记 `CALL_TYPE_OWNERSHIP`（KB）与
`REASONING_BY_CALL_TYPE`（关推理）；上下文版本、生成模型与会议标题/日期哈希进内容指纹。

**唯一主指标**：`context_precision`（DeepSeek、label `f`、thinking=off、contexts=全部检索集）。

**判定规则（先写死）**：
1. 硬门：判定式 `context_recall` ≥ 91.9%；零调用 `recall@k` ≥ 91.9%；
   轮级失败 0、首轮检索 27/27、引用可定位/未越权 100%、编编号 0。
2. 成功：`context_precision` **≥ 81.0%**（不劣于 D 臂）。若同时 ≥ 85.8%
   （+4.8pp，本集 3 条事实的粒度），判为**方向性提升**；否则只判"不劣"。
3. 失败（任一即拒绝默认开）：precision < 81.0% 且差 > 4.8pp；召回低于硬门；
   上下文生成失败率 > 20%；索引重建失败；引用不变量违约。
4. 描述性对照：MRR / nDCG、每轮 token、`KB_CONTEXTUALIZE` 调用次数与耗时/成本、
   生成句的失败与截断情况。

**样本与预算**：同 27 题、同一批索引重建（61 片，约 61 次上下文调用 + 61 次嵌入）；
产品侧约 185k–220k token，判定 54 次。n=27 只作方向信号。

**产物**：`results/chat_answers_ctx.json`、`results/rag_packet_ctx.json`（label f）、
`results/retrieval_ctx.json`；产物必须自报 `kb_contextual_enabled=true` 与 300/3。

**不能说的**：即使 precision 提升，也不能归因到"上下文句"这一个因素——同时发生了
重新嵌入、切片向量变化与模型自选检索词变化；本表只回答"这个机制在本语料上值不值得默认开"。

### 预注册：q26 类"资料覆盖"缺口的检索路径（任务 4，2026-10-17，先于任何调用写死）

**背景**：q26「下午这场会定了哪些行动项和负责人」的三条金标（张涛/陈磊/刘颖）
连续多轮 0/3。根因已查清：它们只在转写 task 7 与草稿纪要里，而 `list_facts` 只读
已确认纪要；模型确实看懂了"确认纪要里没有"，但**没有回头检索转写**（D 臂），
或只检索了 task 6（Contextual 臂）——两段录音只搜了一段。source 限定的 fail-open
已实现，但模型这一轮根本没发起带来源的检索，所以它没有机会生效。

**改动（一处提示词，通用规则）**：系统提示词追加**代码持有**的【资料覆盖规则】
（`chat_service.SOURCE_COVERAGE_PROTOCOL`，管理员改模板不会弄丢）：
list_facts 的 source_coverage 有缺口时，「确认纪要里没有」≠「没发生过」；
行动项/决策/风险类问题在清单不完整时必须再用 `search_knowledge` 检索转写；
多段录音时对每段各检索一次（或一次不限来源）；"上午/下午"判不出来时检索所有相关录音、
如实说明，不猜一段。**不针对 q26 加词表或特例。**

**唯一主指标**：q26 的三条金标命中数（检索集覆盖），基线 **0/3**，目标 **≥1/3**。
其余为回归门，不作提升宣称。

**判定规则（先写死）**：
1. 主指标：q26 ≥ 1/3（逐条用检索侧时间窗-片段映射核对）。
2. 回归门：轮级失败 0、首轮检索 27/27、引用可定位/未越权 100%、编编号 0；
   `context_recall` ≥ 91.9%；`context_precision` ≥ **76.2%**（81.0 − 4.8pp 的噪声带下界）；
   零调用 `recall@k` ≥ 91.9%。

### 预注册：不可答负样（任务 5，2026-10-17，先于调用写死）

**背景**：现有 27 题都有答案，测的是"该找到的找到了没有"，测不到"检索到的东西会不会被
硬凑成答案"。新增 12 条负样（`gold/qa_seed.json` 的 n01–n12，`expected_facts: []`、
`unanswerable: true`；另存 `gold/qa_seed_negative.json` 供单独运行）：问的是语料里
完全没提的东西（预算/竞品/服务器/机房/专利/海外/投诉电话/加密/合同/法务/下次评审），
已用全文检索确认关键词零出现。

**唯一主指标**：**负样拒答率**（单列，**不并进四个质量指标**）。拒答 = 判定者的
`answered=false`（回答没有硬凑一个答案）；`answered=true` 记硬凑。配套单列：
负样上下文 `useful` 率（越低越好，暴露检索噪声）、负样 faithfulness（编造会表现为低支撑）。

**判定阈值**：**首测只登记基线，不设通过阈值**。理由与四指标首测相同：没有可比基线时
任何阈值都是拍出来的。**何为失败**：(a) 判定调用失败 >20%（先修仪器）；(b) 产品轮级
失败（stalled/空答案）>0；(c) 拒答率算不出来（没有 `answered` 字段）——报"判不了"，
不拿 0 或 1 填空。

**样本与预算**：12 题 × 2 判定 = 24 次调用；产品侧 12 轮。n=12 只作方向信号，
逐条答案要人工读一遍——拒答率高不等于"不会编"（可能只是答得含糊）。

**产物**：`results/chat_answers_negative.json`、`results/rag_packet_negative.json`
（label `f`）；摘要里的 `unanswerable` 一节是唯一读数来源，不合成总分。

#### 结果（2026-10-17）：拒答 12/12、编造 0/12；通用仪器把拒答全判成"已回答"

**产品行为**：12 条负样全部 `finished`（0 失败）、全部如实说"资料不足/未找到"，
没有一条给出预算、竞品、机房、专利、投诉电话等编造事实。引用不变量：

按它算会得到"拒答率 0%"，与逐条阅读的答案完全相反。**不能拿它当拒答检测器**。
给负样加了专用判定（`NEGATIVE_ANSWER_SYSTEM`，新标签 `g`）：`refused` = 明确说资料里
没有/无法回答；`fabricated` = 给出了上下文里不存在的具体事实。重判结果：

|---|---|---|

| 硬凑率 | **0%（0/12）** | `refused=false` |

### 预注册：P1 录音墙钟时间与检索路径收窄（2026-10-17，先于调用写死）

**背景**：当前标准（300×3 + 窄资料覆盖规则）precision 75.3%、q26 3/3，但
检索侧 recall@k/MRR/nDCG（0.944/0.830/0.855）都低于 500×5 基线。原因已定位：
① q26 靠"两段录音各检索一次"找到金标，7 条上下文里金标排第 5；
② q23 决策复述题被 `list_facts` 的覆盖提示带去额外检索（3 条上下文里 3 条无用）；
③ "下午这场"此前只能靠两段都查，因为 `create_time` 是上传时间、不能区分录音时段。

**改动（三项，都是通用机制）**：
1. `transcription_task.recorded_at`（录音实际开始时间，墙钟）：模型、`db/01-schema.sql`、
   aerich 迁移三处同步；创建接口接收可选值，未标注保持 NULL；种子两段录音回填
   09:00（上午）/14:00（下午）。`list_facts(kind=recording)` 返回 `recorded_at` 与
   `period`（上午/下午/晚上/未标注）。
2. `list_facts` 的"覆盖缺口→检索转写"明确提示**只给 pending_item**；decision/risk
   只保留"可酌情检索、不要仅为覆盖而检索"，修 q23。
3. 资料覆盖规则改为：行动项题**先做一次不限来源的检索**；只有 `recorded_at/period`
   明确指向某段录音时才用 `source_ids` 收窄。q26 应直接用 task 7（14:00，下午）。

**假设**：q26 仍 3/3，且上下文从 7 条降到 3 条左右；q23 不再额外检索；
precision ≥78%；检索侧三项回到 500×5 基线附近（recall@k ≥0.956、
MRR ≥0.846、nDCG ≥0.879）。

**判定规则（先写死）**：
1. 主指标：`context_precision` ≥ **78.0%**（比当前 75.3% 至少 +2.7pp，方向性）。
2. 非劣门：q26 ≥1/3；judged recall ≥91.9%；轮级失败 0；首轮检索 27/27；
   引用可定位/未越权 100%、编编号 0。
3. 检索侧：recall@k/MRR/nDCG **逐项与 500×5 基线比**；三项都 ≥ 基线才判
   "检索指标恢复"；只恢复 1–2 项则如实登记为部分恢复。
4. 失败（任一即回退本次改动）：q26 <1/3；precision <76.2%；q23 仍额外检索且
   无收益；引用不变量违约。

**样本与预算**：同 27 题、同一索引（`recorded_at` 是元数据，不触发重嵌）；
产品约 200k CHAT token，判定 54 次。n=27 只作方向信号。

**产物**：`results/chat_answers_p1.json`、`results/rag_packet_p1.json`（label f）、

**读法**：
1. **搜索路径本身没坏**：chunk 上下文 69.4% 有用，59 条带转写窗口的题检索侧
