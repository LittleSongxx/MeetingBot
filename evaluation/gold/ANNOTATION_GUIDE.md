# owner/deadline 金标标注指南（verification 协议）

配套文件：`annotation_owner_deadline.csv`（120 行待标）｜工具：`metrics/annotation.py --alpha`
预期成本：按众包中文文本分类 **$0.02–0.10/条**，120 条 × 3 人 × 2 字段 ≈ **$15–70**。

---

## 任务是什么

每一行是产品从真实会议里抽出的一条**决策/待办**，带着它建议的**负责人**与**期限**。
你的工作不是从零写答案，而是**核对**（verification）：对照转写原文，给两个候选各选一个标签。

> 为什么是核对而不是从零写：核对式标注的一致性显著更高。从零写测的是
> "标注者能否只看指南复现答案"，那不是我们需要的量。

## 标签（owner 与 deadline 各选一个，互斥）

| 标签 | 含义 | 判据 |
|---|---|---|
| `correct` | 候选**对**：转写里能找到这个负责人/期限 | 逐字或同义都算；"张经理" vs "老张"算对 |
| `wrong` | 候选**编造**：转写里没有依据，或归错了人/时间 | 转写明确说了别人，或根本没说 |
| `missing` | **该有但漏了**：转写里明确说了负责人/期限，候选却是空/"待确认" | 前提是转写里**确实说了** |
| `na` | 本条**不适用**：这类内容本来就没有负责人/期限可言 | 例如纯议题描述 |
| `unjudgeable` | 判不了：乱码、指代不清、转写片段不足以判断 | **宁选这个也不要猜** |

**`missing` 与 `wrong` 的分界**：`missing` = 候选为空但原文有；`wrong` = 候选非空但原文不支持。
这条分界是本研究的关键，拿不准时在 note 里写一句理由。

## 每行要看什么

1. 先读 `content`（这条决策/待办说了什么）；
2. 在**转写原文**里定位它讨论的位置（CSV 附带转写片段的定位信息）；
3. 只依据转写判断——**不要用你自己的领域知识补全**；
4. `owner_label`、`deadline_label` 两列各填一个标签；有疑问写 `note`。

## 质量要求（对齐发表惯例）

- **≥3 位标注者**独立标完全部行；不商量；
- 完成后计算 **Krippendorff's α**（工具已备好）：`annotation.py --alpha labels.json`；
- **α ≥ 0.7** 达到发表力度；**逐类别 α** 会一并输出——某一类低于 0.4 时该类结论只作探索；
- `unjudgeable` 的比例会单独报告，它高说明转写质量或候选呈现有问题，不是你的错。

## 汇总格式

每人一个 JSON：`{"od_001": {"owner": "correct", "deadline": "missing"}, ...}`，
三人三份，交给 `--alpha` 即得整体 α、逐类别 α 与 PABAK。

## 为什么做这件事

全领域**不存在**经过独立核验的 owner/deadline 公开金标（现有的是厂商自建 starter pack、
无 IAA 的 Kaggle 集、κ≈0.47 的学术标注）。这份标注完成后连同本指南与原始标注一起公开，
将是这个方向上第一个带 IAA 的中文基准。
